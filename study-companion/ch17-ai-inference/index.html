Every Token Pays a Setup

To write one word, a language model reads every one of its weights out of memory. That read is a setup, paid again on every step, and almost everything in this chapter is a way to shrink it, share it or spread it. Shrinking it is quantisation, and quantisation is measurement. Sharing it is batching, and batching is lot sizing against a takt time.

The chapter has five source files: quantisation, efficient architectures, serving and batching, edge inference, and scaling and deployment. This sheet covers all five at the level of one server. Sheet 18 takes up the plant: capacity planning across many servers, redundancy and system design. Sheet 16 covers the hardware underneath, and this sheet uses only one fact from it: reading memory, not arithmetic, sets the pace of generating text.

The headline is §14. Continuous batching, the scheduling method every modern server uses, runs at exactly the minimum lot size that meets takt, the quantity a production planner computes as setup time divided by (takt time minus time per piece). Nobody sets it that way. Little’s law forces it, and the same algebra gives the time per output token as \(t_w/(1-\rho)\), the queueing cliff of Sheet 13 part 2 §06 with no randomness in it. The second result is §06: the best-known weight quantiser, GPTQ, is a support-settlement problem, and the source prints its update with the wrong matrix.

01

Inference is a memory problem

src 01. quantisation ↗

Inference means running a trained model to get answers from it, as opposed to training it. A language model answers one token at a time; a token is a word or a piece of one. The source opens with the number that sets the whole chapter: a model with 70 billion weights, stored at 16 bits (2 bytes) each, needs 140 GB of memory. At 8 bits it needs 70 GB, at 4 bits 35 GB ([Ch17 s01]). One data-centre accelerator holds about 80 GB (reported), so the format decides whether the model fits on one device at all.

The second fact is the one this sheet is built on. Generating a token means pushing one vector through every layer, and every layer multiplies that vector by its weight matrix. Each weight is fetched from memory, used once, and not needed again until the next token. A memory system delivers a fixed number of bytes per second (its bandwidth), so the fastest possible rate is

$$\text{tokens per second} \;\le\; \frac{\text{memory bandwidth}}{\text{bytes of weights}}$$

The source’s own estimator in file 04 is exactly this bound. At 200 GB/s a 7B model gives 57 tokens per second at 4 bits and 29 at 8 bits; at 50 GB/s a 3.8B model gives 26 ([Ch17 s01]). Halve the bytes and the bound doubles, which is why the source can say quantisation gives “nearly linear speedups”. The arithmetic units sit mostly idle; Sheet 16 calls this being bandwidth-bound and draws it as a roofline.

✓The weight read is a setup

Read the bound as a production engineer would. Before a step can produce anything, every weight must come out of memory. That cost is the same whether the step produces a token for one user or for a hundred, because the hundred can all use the weights while they are on chip. A cost paid once per run and independent of how many pieces the run makes is a setup, and Sheet 14 part 1 §04 showed how a setup is shared over a lot.

The rest of the chapter sorts by what each technique does to this setup. Quantisation shrinks it (§§02–09). Efficient architectures cut the work around it (§§10–12). Batching shares it between users (§§13–16). Edge devices have one user and cannot share it (§17). Speculative decoding spreads it over several tokens of one user (§18).

!The source’s throughput ladder does not add up

File 01 says each halving of precision doubles arithmetic throughput, FP32 to FP16 to INT8 to INT4. Two lines later it quotes 989 TFLOPS for FP8 against 67 for FP32, a 14.8× ratio ([Ch17 s01]). The ladder gives 4× for two halvings. Both cannot be rates of the same kind of operation on the same chip. The usual explanation, reported and not derived here, is that 67 is the rate of the ordinary FP32 units and 989 is the dense FP16 rate of the matrix units, with FP8 twice that. For this chapter it hardly matters: decode is limited by bytes, not by FLOPs.

02

Integers are dial gauges; floats are significant figures

src 01. quantisation ↗

Sheet 13 part 1 §10 set up the bridge this section uses. A floating-point number has constant relative precision, a fixed number of significant figures at every magnitude. A fixed-point number, like a dial gauge, has constant absolute precision, the same smallest division everywhere. The source’s table of formats sorts into those two families, and the figures each one carries can be computed from its bit layout.

The integer rows need the qualifier “at full scale”. An INT8 tensor carries 2.41 figures for a value at the top of its range and 1.41 for a value a tenth as large ([Ch17 s02]), exactly as a dial gauge reading 0.08 mm on a 1 mm range has one useful figure. To use integers at all, every tensor (or every row, or every block) gets a scale, a float that converts counts back to values:

$$x_q = \operatorname{clamp}\!\Big(\operatorname{round}\big(x/s\big) + z,\; q_{\min},\, q_{\max}\Big), \qquad \hat x = s\,(x_q - z)$$

The scale \(s\) is the least count. The zero point \(z\) shifts the scale for one-sided data, as a gauge zeroed off the datum would. Symmetric quantisation sets \(z = 0\) and \(s = \max|x|/127\), which is ranging the gauge to the largest reading.

✓Block floating point is one range switch for a bank of channels

The source’s microscaling (MX) formats give a block of elements one shared 8-bit exponent and each element its own few mantissa bits. That is a multi-channel recorder with one range switch per bank: within a bank every channel reads on the same scale, and banks can sit on different ranges. GGUF’s Q4_0, in the source’s llama.cpp list, is the same idea with integers: 32 four-bit counts share one 16-bit scale (layout reported), so it costs 4.5 bits per weight. That is why the source’s own table lists Llama 3.1 8B at about 4.5 GB in “Q4”: \(8\times10^9 \times 4.5/8 = 4.5\) GB. The same accounting puts the 70B at 39.4 GB, not 35 ([Ch17 s02]).

!The MX table charges the same format two prices

The shared exponent adds 8 bits per block. With a block of 32 that is 0.25 bits per element, with 16 it is 0.5. The source lists MXFP6 at ~6.5, MXFP4 at ~4.5 and MXINT8 at ~8.5, which is the block-of-16 accounting, and MXFP8 at ~8. MXFP8 and MXINT8 both have 8 element bits and the same shared exponent, so they cost the same: 8.25 at a block of 32 (the standard’s block size, reported), 8.5 at 16 ([Ch17 s02]).

At the far end, BitNet restricts every weight to \(\{-1, 0, +1\}\). Three states carry \(\log_2 3 = 1.585\) bits, so a 70B model needs 13.9 GB, close to the source’s “~15 GB”. Multiplying by −1, 0 or +1 needs no multiplier: a ternary matrix product is a sum of some inputs minus a sum of others, which the script confirms to \(4\times10^{-15}\) ([Ch17 s07]). Whether such a model is as good as a 16-bit one is a training question this sheet cannot compute.
