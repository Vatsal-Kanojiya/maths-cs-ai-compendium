Everything That Branches

A bill of materials is a tree, and an indented BOM is a preorder traversal of it. The rule you learned for numbering the events of a CPM network is a topological sort. The method of joints is one too, until a compound truss stops it cold. And water in a pipe network does not take the shortest path.

Part 1 was about structures that are lines. This part lets them branch: trees, graphs, and the sorting and searching that make branching structures fast. It also pays the debts part 1 left. The CPM event numbering of part 1 §09 turns out to be Fulkerson’s rule, and Fulkerson’s rule is Kahn’s algorithm for topological sorting, checked on 500 random networks (§10). The 2-D rain water of part 1 §16 is Dijkstra’s shortest-path method with one symbol changed (§11). Quicksort gets built properly, and its best-known repair fails on an input the source never considers (§14). And the \(n\log n\) that part 1 treated as a speed turns out to be a floor no comparison sort can go below (§13).

The headline is §10. The method of joints is a topological sort of a truss: you repeatedly pick a joint with at most two unknown members, solve it, and move on. On a simple truss that never gets stuck. On a compound truss (a triangle joined to another triangle by three bars, still with \(m = 2j - 3\)) every joint has three unknowns from the start, and the procedure stops. That is the same wall a computer hits when a set of equations must be solved together, and §12 gives it its name.

01

A tree is the indented BOM

src 03. trees ↗

A tree is a connected graph with no loops. One node is the root; every other node has exactly one parent; nodes with no children are leaves. In a binary tree every node has at most two children, called left and right. The source’s key advice is that tree problems are solved recursively, because a tree is a root with smaller trees hanging from it.

There are four standard orders in which to visit every node, and three of them are procedures you already follow.

✓Identity: the indented BOM is a preorder traversal

Preorder visits a node, then each of its subtrees in turn. Write each item as you visit it, indented by its depth, and you have produced an indented bill of materials: pump, casing, bolt, gasket, impeller, motor, bearing, bearing ([Ch14p2 s01]). Every assembly appears directly above its components, which is what the format is for.

Postorder visits both subtrees first and the node last. That is the standard-cost roll-up: an assembly’s cost is its own labour plus the rolled-up cost of each component, so every component must be costed before its parent. For the small pump in the verification script it gives 3,160. Level order, visiting the root, then all its children, then all theirs, is how an MRP run takes a product structure level by level (part 1 §10).

!Where it breaks

The fourth order, inorder (left subtree, node, right subtree), has no BOM meaning. It exists for binary search trees, where it visits keys in sorted order (§03). And a real product structure is not quite a tree: a bearing used in both the motor and the gearbox has two parents. Part 1 §10 called that a directed acyclic graph and showed why MRP needs low-level codes for it. A tree view duplicates the shared part under each parent, which is fine for listing and wasteful for computing.

The source’s first traversals build each answer by gluing lists together: inorder(left) + [val] + inorder(right). It warns that this is \(O(n^2)\) because each join copies the lists. The warning is right in kind and overstated in size. Each element is copied once for every ancestor above it, so the total is the sum of all depths: 9,217 copies for a balanced tree of 1,023 nodes, close to \(n\log_2 n\), and 523,776 for a tree of the same size shaped like a chain ([Ch14p2 s01]). The \(n^2\) is the worst case, not the usual one. The fix the source gives, appending to one shared list, is still the right habit.

02

Recursion on a tree

src 03. trees ↗

Part 1 §06 showed that recursion is proof by induction run as a program. On a tree the induction is on subtrees: if the function is right for both children, the combining step makes it right for the node. The height of a tree is the smallest example. An empty tree has height 0, and any other tree has height \(1 + \max(\text{left}, \text{right})\).

The source’s hard problem shows where the pattern needs care. Maximum path sum asks for the largest total along any path between two nodes, with negative values allowed. At each node there are two different quantities, and the source is right that confusing them is the usual mistake:

  • the best path that bends at this node, using both children; it can be the answer but cannot be extended upward, because a path cannot fork;
  • the best path that continues upward, using at most one child; this is what the node reports to its parent.

The node records the first in a running best and returns the second. The source’s code agrees with a brute-force search over every pair of nodes on 300 random trees with negative values ([Ch14p2 s02]). A subtree whose best contribution is negative is treated as absent, which is the max(…, 0) in the code.

The lowest common ancestor code carries the caveat the source states: it assumes both nodes are in the tree. Ask it about a node that is absent and it returns the other node, as if that were the answer ([Ch14p2 s02]). A function that can return a plausible wrong answer should say so in its name or check its inputs.

03

Binary search trees, and the order of arrival

src 03. trees ↗

A binary search tree (BST) keeps every key in a node’s left subtree smaller than the node and every key in its right subtree larger. Searching compares with the root and goes left or right, one level per comparison, so a search costs the height of the tree. It is binary search (§15) stored in a shape that allows cheap inserts.

The cost is set by the height, and the height is set by the order in which keys arrive ([Ch14p2 s03]):

  • Inserted in sorted order, 1,000 keys make a tree of height 999. Every new key is larger than all before it and hangs off the right. The tree is a linked list, and a search is a linear scan.
  • Inserted in random order, the mean depth of a node is 11.01, against the theoretical \(2(1 + 1/n)H_n - 4 = 10.99\), where \(H_n\) is the harmonic number. A perfectly balanced tree has \(\log_2 1000 = 9.97\) levels. Random order costs about 10% more than perfect, which is almost nothing.
!Where the card-index picture breaks: the worst case is the usual one

A card index kept in part-number order is the picture a BST suggests, and in a plant it fails in a specific way. Part numbers are usually issued in sequence. A plain BST fed new parts as they are created receives sorted input, which is exactly its worst case. Real systems use balanced search trees (AVL trees, red–black trees, and the B-trees inside databases), which rotate nodes after each insert to keep the height near \(\log_2 n\) whatever the arrival order. Rotations have no counterpart in your training; the bridge table lists them as one to learn cold.

!The source’s insert and validate disagree

The source defines a BST with left keys smaller and right keys larger, which leaves no place for a duplicate. Its insert_bst sends an equal key to the right anyway. Its is_valid_bst, a page later, demands strictly larger keys on the right, so it rejects the tree its own insert built from the keys 5 and 5 ([Ch14p2 s03]). With distinct keys the two agree on all 300 trees tested. Pick one rule for duplicates (reject them, count them, or send them consistently to one side) and make every function use it.

04

Tries, and dialling codes

src 03. trees ↗

A trie (a prefix tree) stores strings one character per level. The root’s children are the possible first characters, their children the second characters, and so on; a node is marked where a stored string ends. Looking up a string of length \(L\) follows \(L\) edges, however many strings are stored, as the source says. Finding every string with a given prefix means walking to the prefix’s node and collecting everything below it.

✓Same structure: trunk dialling codes

India’s trunk codes have different lengths: 11 for Delhi, 22 for Mumbai, 80 for Bengaluru, and longer codes for smaller towns. An exchange must route a call while the digits are still arriving, so no code may be the beginning of another. A set of codes with that property is prefix-free, and it is exactly a trie in which every code ends at a leaf: the moment the digits reach a leaf, the call knows where it is going. The older electromechanical exchanges of the step-by-step type did this with one bank of switches per dialled digit (reported), which is a trie built from hardware. Hierarchical part-classification codes work the same way: every part whose code starts with the same digits is one family, one node of the trie.

The source’s hard problem, finding many words in a grid of letters, builds a trie of the words first and searches the grid once, abandoning any path whose letters are not a prefix of some word. It is part 1 §08’s pruning, with the trie as the check that fires early.

05

Union-find: which parts are one body

src 03. trees ↗

Union-find keeps track of which items belong together. Each group is stored as a small tree whose root represents it. find(x) climbs from \(x\) to its root; union(x, y) hangs one root under the other. Two repairs keep the trees flat: union by rank hangs the shorter tree under the taller, and path compression points every node it passes directly at the root. With both, a long sequence of operations costs so little per operation that it is constant for every practical size (the inverse Ackermann bound; reported, not derived here).

✓Identity in the count: welding parts, and redundant members

Start with \(n\) loose parts and weld them together one joint at a time. Union-find says, for each weld, whether the two parts were already one rigid body. A weld between parts of the same body closes a loop. The source’s “redundant connection” problem is that loop-closing weld. Over a whole assembly, the number of loop-closing joints equals \(m - n + c\) for \(m\) joints, \(n\) parts and \(c\) separate bodies at the end, on all 300 random cases checked ([Ch14p2 s05]). That count is the cyclomatic number, which Sheet 12 §07 showed is the number of redundant members of a spring network: each loop-closing member is one more force that equilibrium alone cannot find.

!The pitfall table blames the wrong omission

It says union-find without path compression costs \(O(n)\) per find in the worst case. Not if union by rank is kept. A tree only gains height when two trees of equal height merge, which needs twice as many items each time, so the height cannot exceed \(\log_2 n\). Merging 4,096 items in the worst possible order gives height exactly 12. Leave out both repairs and the same items form a chain of height 4,095 ([Ch14p2 s05]). The \(O(n)\) needs both omissions; either repair alone gives \(O(\log n)\).

The same structure drives Kruskal’s method for the cheapest network connecting a set of points, which the source mentions: take connections in order of cost and reject any that would close a loop. Laying out an air header to reach every machine with the least pipe is that problem, before anyone thinks about flow.

06

A Fenwick tree: a shear diagram whose loads change

src 03. trees ↗

Part 1 §18 showed that a prefix-sum array is a shear-force diagram, and that it answers any range query with one subtraction. The price appears when a load changes. Move one wheel load on a crane runway beam and every shear value to its right changes, so the array must be rebuilt: \(O(n)\) per change. Keeping only the loads is the opposite trade: \(O(1)\) to change a load, \(O(n)\) to add up a range.

Three ways to keep running totals when the loads keep changing.
StoredChange one loadSum over a range
The loads themselves\(O(1)\)\(O(n)\)
The prefix sums (the shear diagram)\(O(n)\)\(O(1)\)
A Fenwick tree\(O(\log n)\)\(O(\log n)\)

A Fenwick tree stores partial sums over blocks of carefully chosen lengths: entry \(i\) covers a block whose length is the lowest set bit of \(i\) in binary. A running total up to \(i\) adds a handful of blocks, stripping the lowest bit each hop; a load change updates the handful of blocks that contain it, adding the lowest bit each hop. Checked against brute force on 3,000 random changes and queries over 1,000 positions, it was right every time and never took more than 17 hops per operation, against a bound of \(2\lceil\log_2(n+1)\rceil = 20\) ([Ch14p2 s06]). For a 20-station beam you would simply recompute. The structure earns its keep when the positions number millions and the changes never stop, as with a stream of sensor readings.

A segment tree does the same for operations that cannot be undone by subtraction, such as the minimum or maximum over a range.

07

Storing a graph

src 04. graphs ↗

Sheet 12 treated a graph through its matrices: the adjacency matrix and the Laplacian. For algorithms the choice of storage matters more than the choice of matrix. An adjacency matrix has a row and a column per node, \(O(V^2)\) entries however few edges exist. An adjacency list keeps, for each node, only its neighbours: \(O(V + E)\).

You have met the difference in finite elements. A mesh of a million nodes, each joined to about ten neighbours, has \(10^{12}\) entries as a full matrix, eight terabytes in double precision, and about \(10^7\) nonzeros as a list, around a hundred megabytes ([Ch14p2 s07]). FE solvers store the stiffness matrix in sparse formats that are adjacency lists in disguise. The source’s advice, a list for almost everything, is the same advice.

!An overreach

The source says nearly every graph problem reduces to breadth-first or depth-first search. Many interview problems do. But this part’s own §11 needs a priority queue that neither provides, and the pipe network there is not a search at all: it is a linear solve. Treat BFS and DFS as the two tools to reach for first, not as the whole kit.

08

Breadth first, and the diamond-shaped offset

src 04. graphs ↗

Breadth-first search (BFS) explores a graph in waves. It holds the frontier in the queue of part 1 §21: take the oldest node out, put each of its unvisited neighbours in. Everything one edge from the start is finished before anything two edges away, so the wave in which a node is first reached is its distance in edges. That makes BFS the shortest-path method when every edge counts the same.

!Marking on dequeue is slower, not wrong

The source insists that a node be marked visited when it is put into the queue, because marking it when it comes out lets it be queued several times, “wasting time and potentially causing incorrect results”. Tested on 300 random graphs: marking on dequeue and skipping repeats gives the same distances every time, at a cost of up to 3.6× as many queue entries. Wrong answers appear only with a further mistake, writing a node’s distance each time it is queued, so that a later, longer route overwrites a shorter one: that version was wrong on 207 of the 300 graphs ([Ch14p2 s08]). The source’s rule is the right habit; its reason names the wrong risk.

Start the queue with many sources at once and BFS measures the distance to the nearest of them. The source’s rotting-oranges problem does this, and its answer matched a separate nearest-source search on every random grid ([Ch14p2 s08]). Counting islands on a grid is the same flood fill run once per island.

✓The distance to the boundary is what a pocketing toolpath follows

A contour-parallel pocketing toolpath is a set of curves at fixed distances inside the pocket boundary and outside any boss. Seed a multi-source BFS with every boundary cell of a gridded pocket, and each wave is one such offset. The structure is right: offsets are level sets of the distance to the nearest boundary.

!Where it breaks: a grid does not measure circles

A grid wave that steps to four neighbours measures \(|\Delta x| + |\Delta y|\), which overstates the true distance by up to \(\sqrt2 = 1.4142\) along the diagonals; one that steps to eight neighbours measures \(\max(|\Delta x|, |\Delta y|)\), which understates it by down to \(1/\sqrt2 = 0.7071\) ([Ch14p2 s08]). Its offsets around a drilled hole are diamonds or squares, never circles. A cutter following them would leave scallops or gouge. CAM systems offset geometry exactly, and image-processing codes correct grids with weighted or exact distance transforms (reported).

09

Depth first, and three colours for a loop

src 04. graphs ↗

Depth-first search (DFS) follows one path as far as it goes before backing up, using a stack: the call stack of part 1 §05 if it is written recursively. It is the tool for exhaustive search with backtracking (part 1 §08) and for detecting loops.

To find a loop in a directed graph (a course that is its own prerequisite, or a part that contains itself) the source gives each node three states: not yet visited, in progress (on the current path), and finished. Reaching an in-progress node means the path has come back on itself. Reaching a finished node means nothing. On 500 random directed graphs this test agrees with the topological sort of §10, which detects loops a different way ([Ch14p2 s09]).

✓Why two states are not enough: the shared part

A checker with only “seen” and “not seen”, treating anything seen before as a loop, reports a loop in the four-node diamond A→B, A→C, B→D, C→D, which has none ([Ch14p2 s09]). In BOM terms that diamond is a component D used by two sub-assemblies B and C: a shared part, the most ordinary thing in a product structure. A BOM that genuinely contains itself is a data error MRP software must reject. A checker that also rejects every shared part is useless, and the third state is what tells the two apart.

10

Fulkerson’s rule is a topological sort, and so is the method of joints

src 04. graphs ↗

A topological order of a directed graph lists its nodes so that every arrow runs from an earlier node to a later one. One exists exactly when the graph has no loops. The source gives Kahn’s algorithm for finding it: take any node with no arrows coming in, write it down, delete its outgoing arrows, and repeat. If nodes remain but none is free of incoming arrows, there is a loop.

✓Identity: this is Fulkerson’s rule

You learned a rule for numbering the events of an activity-on-arrow network: (1) number the initial event 1; (2) delete every arrow leaving a numbered event, which leaves new initial events; (3) number those next, and repeat until the end event is numbered. That is Kahn’s algorithm, step for step. On 500 random networks the two reach the same verdict on loops, and Fulkerson’s numbering is always a valid order ([Ch14p2 s10]). A GATE problem that asked you to number a network was asking for a topological sort.

The rule also produces something the source does not mention. The round in which an event gets its number equals the largest number of arrows on any path into it, checked on every one of those networks. And the rule exists for the reason part 1 §09 gave: the forward pass needs every \(TE_i\) before \(TE_j\) whenever \(i \to j\), which is step 4 of the DP recipe. Fulkerson’s rule is that step, done by hand.

The method of joints is the same procedure

Solving a truss by joints follows the same pattern. Find the reactions from overall equilibrium. Then repeatedly pick a joint with at most two unknown member forces, solve its two equilibrium equations, and mark those members known, which may leave another joint with only two unknowns. A joint becomes “ready” when its unknowns fall to two, as a node in Kahn’s algorithm becomes ready when its incoming arrows fall to zero.

On a simple truss this never gets stuck, and Sheet 13 part 1 §04 already holds the proof. A simple truss is built from a triangle by adding one joint and two members at a time. Run the construction backwards: the last joint added has exactly two members, so it can be solved first; remove it, and what is left is again a simple truss. By induction the whole truss solves joint by joint. Checked on Warren trusses of 2, 3, 5 and 8 panels: a ready joint was always available, and the forces matched a full matrix solve to \(10^{-9}\) ([Ch14p2 s10]).

!Where it stops: the compound truss

Take a triangle inside a triangle, joined by three bars: 6 joints and 9 members, so \(m = 2j - 3\) and the truss is statically determinate (its equilibrium matrix has full rank, 12 of 12). But every joint has three members. After the reactions, no joint has fewer than three unknowns, and the method of joints stops before it starts, with all 9 member forces unknown ([Ch14p2 s10]).

What unblocks it is a set of equations solved together. The six equations at the three inner joints contain exactly six unknowns (the inner triangle’s three members and the three connecting bars), and they can be solved as a block. After that, each outer joint has two unknowns and the rest goes joint by joint. The outer triangle’s joints give an equally valid block. You were taught the other way out: cut the three connecting bars with a section and take the inner triangle as a free body. That is a three-unknown block written with rigid-body equations. Either way, \(m = 2j - 3\) is necessary for a simple truss, not sufficient, and §12 names what the block is.

Shortest paths, and what water actually does

src 04. graphs ↗

When edges have lengths, BFS’s waves no longer mean distance. Dijkstra’s algorithm replaces the queue with the priority queue of part 1 §21: always expand the unfinished node with the smallest distance found so far, and relax its outgoing edges. It costs \(O((V+E)\log V)\) with a binary heap, and on 300 random graphs the source’s code agrees with the slower Bellman–Ford method ([Ch14p2 s11]).

The heap can hold stale entries, older and longer distances for a node that has since improved, and the source’s if d > dist[node]: continue skips them. That line saves work and changes no answer: without it the distances are identical on the same 300 graphs. On a hub reached by 40 successively shorter routes, the check cuts the edge scans from 1,680 to 120 ([Ch14p2 s11]).

!The negative-weight pitfall describes code the source does not print

The source warns that Dijkstra fails with negative weights. That is true of the textbook version, which declares a node finished the first time it leaves the heap: with edges A→B of 2, A→C of 3 and C→B of −2, it reports B at 2 when the answer is 1. The code on the page never declares anything finished. When a distance improves it pushes the node again, so it reports 1, and on 300 random graphs with negative edges and no negative loop it matched Bellman–Ford every time ([Ch14p2 s11]). The costs are real but different: that version can take exponentially long on adversarial graphs (reported), and with a negative loop it never stops. Here it was cut off after 200,000 heap pops.

Part 1’s spill level is Dijkstra with one symbol changed

Part 1 §16 promised that the 2-D rain-water level is found by a priority-queue search from the edges. Here it is: the same code, with the path cost \(d + w\) replaced by \(\max(d, h)\). The level at a cell is the lowest possible value of the highest point on a route to the edge, and on 150 random grids this search matches part 1’s independent relaxation method ([Ch14p2 s11]).

$$\begin{aligned}\text{shortest path:}\quad d_v &= \min_{u \to v}\big(d_u + w_{uv}\big)\\ \text{spill level:}\quad d_v &= \min_{u \to v}\max\big(d_u,\, h_v\big)\end{aligned}$$

What makes both work is the same property: a path’s cost never decreases as the path gets longer. Adding a non-negative length and taking a maximum both have it. A negative edge destroys it, and that is precisely why declaring a node finished becomes unsafe.

The bank said graphs are pipe networks

The bridge bank for this chapter paired graphs with pipe networks, and the structure is right: junctions are nodes, pipes are edges, and head loss along a route adds up like a path length. So Dijkstra finds the route of least resistance. In the six-junction network of the lab below, that is inlet–2–3–outlet, with a total resistance of 6.0; the next routes cost 6.5, 7.0 and 9.0 ([Ch14p2 s11]).

!Where it breaks: water does not choose a route

At steady state, flow into every junction equals flow out, and each pipe carries flow in proportion to the head difference across it (laminar flow, \(\Delta h = RQ\)). That is a linear system, and it is Sheet 12’s graph Laplacian with conductances \(1/R\) on the edges, not a search. Solved: water runs in all 8 pipes; the network passes a unit flow at a head drop of 3.004, about half the best single route’s 6.0; and more water enters pipe 0–1 (0.531), which is not on the least-resistance route, than pipe 0–2 (0.469), which is. Continuity holds at every junction to \(4\times10^{-16}\) ([Ch14p2 s11]).

With turbulent losses, \(\Delta h = RQ^2\), the split changes (it is the problem Hardy Cross iteration solves) but every pipe still carries flow. And the two answers behave differently as a pipe changes. Raise the resistance of pipe 2–3: the best route costs \(4 + R_{23}\) until \(R_{23}\) reaches 3, then jumps to a different route at 7.0, while the flow split moves smoothly. Shortest path answers “which single hose should I run?”. The network’s behaviour is a Laplacian solve.

Strongly connected components, and equations solved together

src 04. graphs ↗

In a directed graph, a strongly connected component (SCC) is a largest set of nodes in which every node can reach every other. Kosaraju’s algorithm, which the source outlines, finds them all with two depth-first passes, the second on the graph with every arrow reversed. It agrees with a brute-force test of mutual reachability on 300 random graphs ([Ch14p2 s12]). Shrink each component to a single node and what remains has no loops, so it has a topological order (§10).

✓Same structure: which equations must be solved together

Write a system of equations as a graph: an arrow from equation \(i\) to unknown \(j\) whenever \(j\) appears in equation \(i\). Each strongly connected component is a group of equations that depend on one another in a loop, so they must be solved simultaneously; the components themselves can be solved one after another in topological order. On 100 random sparse systems, solving component by component gave the same answer as solving the whole system at once ([Ch14p2 s12]). Sparse solvers use exactly this decomposition (reported). The compound truss of §10 is the mechanical version: the method of joints is the topological sort, and the six-unknown block is a component it cannot break.

Sorting, and the n log n floor

src 05. sorting and search ↗

Part 1 §02 said that proving a problem hard is much harder than proving an algorithm fast, and promised one proof that works. Here it is, and it is short. A sort that learns about its input only by comparing two items at a time gets one yes-or-no answer per comparison. Its possible runs form a binary tree of comparisons, and every one of the \(n!\) orderings of the input must end at a different leaf, or two different inputs would be rearranged the same way. A binary tree with \(n!\) leaves has some path at least \(\log_2 n!\) long, so some input needs that many comparisons:

$$\text{comparisons} \;\ge\; \lceil\log_2 n!\,\rceil \;\approx\; n\log_2 n - 1.443\,n$$

The bound holds for the average over all inputs too. Merge sort comes close ([Ch14p2 s13]):

!What the floor does not say

It counts comparisons and nothing else. Binary insertion sort, which finds each new item’s place by binary search, sorts 1,000 items with 8,590 comparisons, within 1% of the floor, and then shifts 252,216 items to make room: \(O(n^2)\) work that the bound never sees ([Ch14p2 s13]). The floor also does not apply to sorts that never compare. Counting sort reads each key as a number and drops it straight into a slot, \(O(n + k)\) for keys from a range of \(k\) values. Grading aggregate through a stack of sieves works the same way: nothing is compared with anything, each grain falls into its size class, and it only works because the classes are known in advance.

A sort is stable if equal keys keep their input order, which matters when you sort by one key and then another. The source’s merge takes from the left half on a tie (<=), which keeps it stable; with < it is not, as the source warns and a test confirms ([Ch14p2 s13]). The source’s table of algorithms is otherwise right, with one entry to read carefully: quicksort’s \(O(\log n)\) space needs the smaller-side-first recursion of part 1 §05.

Quicksort, built properly

src 05. sorting and search ↗

Quicksort picks a pivot, moves every item smaller than the pivot to its left and the rest to its right (the partition), then sorts the two sides the same way. The source’s partition is Lomuto’s: pivot on the last item, one pass, a swap for every item found smaller than the pivot. Its speed depends entirely on how evenly the pivot splits the items. Counting comparisons for 2,000 items ([Ch14p2 s14]):

The source’s advice fixes the famous case. On sorted input the last item is always the largest, every split is 1,999 against 0, and the cost is the full \(n(n-1)/2\); a random pivot or the median of three brings it down to about \(n\log_2 n\).

!The repair fails on repeated keys, which is what plant data looks like

The source says a random pivot or median-of-three “eliminates” the \(O(n^2)\) case. Not with repeated keys. When every key is equal, no item is smaller than any pivot, so Lomuto’s partition puts everything on one side whichever pivot is chosen: exactly 1,999,000 comparisons under all three rules. Two distinct values cost about a million. Sorting 2,000 parts by material grade, by a rounded dimension, or by a pass/fail flag is precisely this input. The repair is a three-way partition (the “Dutch national flag”): smaller, equal and larger in one pass, with the equal block never touched again. It sorts the all-equal input with 2,000 comparisons.

Two more properties complete the picture. Quicksort is not stable: a partition can swap equal keys past each other. And its recursion depth follows the splits, so the \(O(\log n)\) space of the source’s table needs the smaller-side-first rule of part 1 §05; the lab reports the depth alongside the count.

Binary search is bisection, again

src 05. sorting and search ↗

Sheet 13 part 1 §06 showed that binary search and the bisection method are one algorithm. The source’s templates are correct: the exact-match search and the lower_bound search (the first item not less than the target) agree with Python’s own bisect module on 2,000 random cases, and never probe more than \(\lceil\log_2(n+1)\rceil\) items ([Ch14p2 s15]).

The midpoint is written lo + (hi - lo) // 2 rather than (lo + hi) // 2, and the source’s reason is real. In languages with 32-bit integers, two indices above about a billion overflow when added: \((2^{30}+5) + (2^{30}+9)\) wraps to −2,147,483,634, and the search reads from a negative index ([Ch14p2 s15]). A bug of exactly this kind sat unnoticed for years in widely used library code (reported). Python’s integers do not overflow, so there the rewrite is a portable habit.

The source’s two harder searches check out. Searching a sorted list that has been rotated works because one half is always in order, and the source is right that the <= in nums[lo] <= nums[mid] matters: changed to <, it fails 100 times in 3,000 tests ([Ch14p2 s15]). The median of two sorted lists, found by searching for a split point rather than a value, agrees with the median of the merged list on 2,000 cases.

Binary search on the answer is balancing a serial line

src 05. sorting and search ↗

The source’s most useful search pattern searches over the answer. If you can test whether a candidate answer \(x\) is feasible, and feasibility is monotone (once feasible, larger \(x\) stays feasible), then bisect on \(x\). This is bisection with “feasible?” in place of “did the sign change?”, and it is how you would pick the smallest catalogue shaft that passes a stress check.

✓Identity: the shipping problem is line balancing with a chain of tasks

The source’s example: packages must ship in their given order within \(d\) days; find the smallest daily capacity. Read packages as tasks, days as stations and capacity as cycle time, and it is line balancing with a strictly serial precedence chain: the least cycle time that fits the line into \(d\) stations, which is the type-II line-balancing problem. The source’s bisection with a fill-in-order check agrees with a brute-force search over every way of cutting the sequence on 400 cases ([Ch14p2 s16]).

The check itself answers the type-I question. For a chain of tasks and a fixed cycle time, filling stations in order until the next task does not fit gives the fewest stations; brute force agrees on 400 cases. It takes one pass, so it is linear time, which is the case Sheet 13 part 1 §09 promised: a line with serial precedence is easy, and here is the algorithm.

!Where it breaks: general precedence

The fill-in-order check is exact only because a chain allows one order. With a general precedence diagram, finding the fewest stations for a given cycle time is the NP-hard problem of Sheet 13 §09, and part 1 §11 showed that even filling every station perfectly can lose one. Bisecting on the cycle time with a heuristic check inherits the heuristic’s error. The outer search is sound; the answer is only as good as the feasibility test inside it.

Greedy, when it is safe, and a slip-gauge rule that is optimal

A greedy algorithm takes the best-looking step and never reconsiders it. The source is right that this needs a proof each time; its two examples have one, and both agree with brute force (jump game on 1,000 cases, merging intervals on 500; [Ch14p2 s17]). Building a length from slip gauges is change-making: the gauges are the coins, the length is the amount, each block can be used once, and the aim is the fewest blocks, because every wrung joint adds a little error. The rule taught in metrology, clear the last decimal place first, is a greedy algorithm. For 41.125 mm with the M87 set it takes 1.005, then 1.12, then 9, then 30: four blocks.

It is optimal. Taking the M87 set as usually listed (1.0005; 1.001 to 1.009; 1.01 to 1.49; 0.5 to 9.5 in steps of 0.5; 10 to 90 in tens; reported), an exact search for the fewest blocks, each used at most once, was run for every length from 4 to 99 mm in steps of 0.001 mm: 95,001 lengths. The rule built every one of them and never used more blocks than the minimum ([Ch14p2 s17]). Most lengths need four blocks (72,765 of them), and 20,711 need three. The set is designed so that each decimal place has exactly one block that clears it, the same design that makes rupee denominations safe for greedy change and coins of 1, 3 and 4 unsafe.

Dynamic programming, briefly revisited

src 05. sorting and search ↗

File 05 repeats the DP material of file 00, which part 1 §§07–11 covered through the CPM forward pass. Three of its examples are worth a line each, and all three agree with brute force ([Ch14p2 s18]):

  • Coin change with unlimited coins: the fewest coins for each amount from 0 up, each built from a smaller amount. It is the exact method that the greedy rules of §17 either match or lose to.
  • Longest common subsequence of two strings: a table indexed by a prefix of each. Comparing two revisions of a drawing’s notes or a program’s text line by line is this problem, and classic file-comparison tools are built on it (reported).
  • 0/1 knapsack in one row instead of a table. The source’s warning is exact: sweep the capacities from right to left and each item is used at most once; sweep left to right and the same code solves the unbounded knapsack, because an item added early in the sweep can be added again later. Both claims hold on 300 cases.

Inserting into a sorted list shifts everything after the insertion point, \(O(n)\) each time; a plain search tree turns into a chain on sequential keys (§03). ✓The storekeeper was already running several indexes

The clerk’s answer had the same shape: bins for finding, an ordered ledger for listing, a where-used list, a job board. One set of records, several indexes over it, each chosen for a question. Databases work the same way (reported), and they pay the price the clerk paid: every new part must be entered in every index. That is §06’s trade-off table again, between the cost of changing the records and the cost of asking about them.

Question bank

both parts

Twenty-four prompts across the whole chapter, in three tiers. Answer before opening.

Tier 1 — recall
Define \(f = O(g)\). What does \(\Theta\) add, and which one is a scaling law?

\(f(n) \le c\,g(n)\) for all \(n \ge n_0\): an upper bound only. \(\Theta\) bounds from below as well, and that two-sided statement is what a scaling law like the square–cube law says.

What is amortised cost, and why must a dynamic array grow by a factor rather than by a fixed amount?

Total cost of a sequence divided by its length. Each resize copies everything on hand, so the setup grows with the stock; only geometric growth keeps copies per append bounded (by \(g/(g-1)\)). A fixed +100 slots makes the total quadratic.

State the DP recipe and map each step onto the CPM forward pass.

State \(TE_j\); recurrence \(TE_j = \max_i(TE_i + t_{ij})\); base \(TE_1 = 0\); order by Fulkerson’s numbering; recover the critical path by walking back along the maximising arrows.

Under linear probing at load factor 0.75, what does a hit cost and what does a miss cost?

Knuth: a hit \(\tfrac12(1 + 1/(1-\alpha)) = 2.5\) probes, a miss \(\tfrac12(1 + 1/(1-\alpha)^2) = 8.5\). At 0.9 the miss costs 50.5.

Which tree traversal is an indented BOM, and which is a standard-cost roll-up?

Preorder (the assembly above its components) and postorder (components before the assembly that contains them).

State Fulkerson’s rule and name the algorithm it is.

Number the initial event; delete arrows leaving numbered events; number the new initial events; repeat. It is Kahn’s topological sort, and stalling with events unnumbered means the network has a loop.

What is the lower bound for sorting by comparisons, and where does it come from?

\(\lceil\log_2 n!\rceil \approx n\log_2 n - 1.443n\). The comparisons form a binary decision tree with at least \(n!\) leaves, one per ordering, so some leaf is at least that deep.

What does a Bloom filter tell you with certainty?

That a key is absent. “Present” is only probable: at 10 bits per key and 7 hash functions, about 0.82% of absent keys look present.

Tier 2 — apply
Two parallel paths, each taking N(10, 2²) days, merge at one event. What does the forward pass on means say, and what is the expected merge time?

The forward pass says 10. The expected merge time is \(10 + 2/\sqrt\pi = 11.13\). PERT’s single-path estimate is optimistic wherever paths merge.

Tasks of 7, 7, 6, 4, 4 and 4 seconds, cycle time 12. Fill each station as full as possible. How many stations, and what is the optimum?

The only 100% station is {4, 4, 4}, which leaves 7, 7 and 6 needing a station each: 4 stations. The optimum is 3: {7, 4}, {7, 4}, {6, 4}.

A list has a tail of 10 nodes and a loop of 3. When do tortoise and hare meet, and does \(a + b = c\)?

At step 12, with \(b = 2\). So \(a + b = 12 = 4c\): a multiple of the loop, not the loop itself. The restart trick still finds the start because only the remainder matters.

Part numbers 1 to 1,000 are inserted into a plain search tree in the order issued. What is its height, and what would you do?

999: a chain. Use a balanced tree, which rotates to keep the height near \(\log_2 n\). Random order would give a mean depth about 10% above the balanced ideal.

In the six-junction pipe network of §11, which pipes carry flow, and does the least-resistance route’s first pipe carry the most?

All eight. No: pipe 0–1, which is not on the best route, carries 0.531 of the inflow against 0.469 in pipe 0–2, which is.

How many comparisons does the source’s quicksort make on 2,000 equal keys with a median-of-three pivot, and what fixes it?

1,999,000, the full \(n(n-1)/2\), whatever the pivot rule. A three-way partition sorts the same input with 2,000.

Build 41.125 mm from an M87 slip-gauge set. How many blocks, and can any combination use fewer?

1.005 + 1.12 + 9 + 30: four blocks. No: an exact search over the whole set finds nothing shorter, for this length or any of the 95,001 checked.

A 20-task serial line with a given cycle time: how do you find the fewest stations? And the least cycle time for 5 stations?

Fill stations in order until the next task will not fit: one pass, and optimal for a chain. For the least cycle time, bisect on the cycle time using that fill as the feasibility test.

Tier 3 — judge
The source says \(O(n^2)\) is optimal for Three Sum because “you must consider all pairs”. Is that a proof?

No. The two-pointer method itself discards pairs by the row without considering them. Whether Three Sum can be done in \(O(n^{2-\varepsilon})\) is an open conjecture. The only lower bound this chapter proves is sorting’s.

A colleague proposes Dijkstra’s algorithm to predict how cooling water divides in the plant’s pipe network. Your response?

It answers a different question: which single route loses least. Water divides over every path so that continuity holds at each junction. Solve the network: a Laplacian system for laminar losses, Hardy Cross or Newton for turbulent ones.

A BOM checker reports a loop at every part used by two sub-assemblies. What is wrong with it?

It uses two states, seen and unseen. A shared part is a diamond, not a loop. It needs the third state, in progress, and only reaching an in-progress part is a loop.

When is a greedy rule safe? Name one you would trust and one you would not, with evidence.

When there is a proof, an exchange argument or an exhaustive check. Trust Johnson’s rule (matched the best sequence on 300 shops) or the slip-gauge rule on M87 (optimal on 95,001 lengths). Distrust largest-candidate balancing (loses a station) or nearest-neighbour drilling (30% longer).

A linear-probing table at load 0.9 is slow. Rehash to 0.5, or switch to chaining?

Either fixes it. Rehashing to 0.5 cuts the miss cost from 50.5 probes to 2.5; chaining’s miss cost grows only as \(\alpha\). The planner’s rule applies: keep slack, because every system with interference has a cliff near full.

The method of joints stalls on a statically determinate truss. What does that tell you, and what do you do?

The truss is not simple: some equations must be solved together. Take a section through the connecting bars, or solve the coupled block of joint equations at once. \(m = 2j - 3\) is necessary for a simple truss, not sufficient.

The source says naive fib(50) takes “over \(10^{15}\) operations” and is infeasible. What is right and what is wrong?

The count is \(2F_{51} - 1 = 4.07\times10^{10}\), growing as \(\varphi^n\); the \(10^{15}\) is the loose bound \(2^{50}\). At the measured rate it takes about 0.8 hours, so it is slow rather than infeasible. The conclusion, memoise, stands.

Choose a structure for a million part numbers that must support exact lookup, family listings and sequential inserts.

A balanced ordered index: about 20 probes per lookup, two searches plus the members for a family, \(O(\log n)\) inserts in any order. A hash table is faster for lookups but cannot list a family; a plain search tree degenerates on sequential numbers.

The map, and what the chapter leaves out

beyond the chapter

One mechanism ties the two parts together. The searches of part 2 are the line structures of part 1 put to work: change the structure that holds the frontier and you change the algorithm.

What this chapter feeds

Sheet 15 (production software engineering) inherits §18’s longest common subsequence as the core of comparing two versions of a file, which the bridge bank pairs with drawing revision control, and part 1’s hashing as the way version-control systems name what they store (reported). Sheet 16 (SIMD and GPU) is where part 1 §12’s 4.5× memory-order penalty becomes the main cost, and where prefix sums and sorting reappear as parallel building blocks. Sheet 17 (AI inference) uses heaps to pick the most likely next tokens and part 1 §08’s pruned search as beam search. Sheet 18 (ML systems design) takes part 1 §13’s cliff near full load and makes it capacity planning.

What this chapter does not cover

Naming it honestly, so two parts do not imply completeness:

  • Network flow and matching. The transportation and assignment problems in your operations-research syllabus are exactly solvable in polynomial time; the assignment method matched brute force on 200 random cost matrices ([Ch14p2 s22]), and its \(O(n^3)\) running time is reported. That is the other half of Sheet 13’s lesson: you were given exact methods for those problems because they are easy, and heuristics for line balancing because it is not. Max-flow min-cut, which ties them together, is not in this chapter.
  • Computational geometry. Offsetting, intersection, convex hulls and point location are the algorithms inside CAD and CAM, the most mechanical part of the whole field, and they are absent. §08 only showed why a grid cannot stand in for them.
  • Proofs. Correctness is argued by induction or checked by brute force on small cases. Amortised analysis is done by accounting, not by potential functions. Balanced trees are named, not built.
  • Strings and randomness. No fast string matching, no suffix structures, and no randomised algorithm beyond hashing and a random pivot.
  • Memory and parallelism. Every cost here counts steps on one processor. External sorting of data that does not fit in memory, cache-aware algorithms and parallel algorithms are left to later sheets.
