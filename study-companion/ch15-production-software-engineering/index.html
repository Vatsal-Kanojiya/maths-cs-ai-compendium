Revisions, Gauges and Fixtures

Version control is drawing revision control, with two changes that matter: the names are computed from the content instead of issued by a registry, and the differences between revisions are computed instead of written on an ECN. Testing is gauging, and the chapter’s own test is a gauge that accepts a broken part. A container is a palletised fixture that leaves the machine bed behind.

This sheet covers the chapter’s five files: the command line, git, codebase design, testing, and deployment. It also pays two debts Sheet 14 part 2 left with you. Its §18 said that comparing two revisions line by line is the longest common subsequence problem, and marked that as reported; its §22 said that hashing is how version-control systems name what they store, also reported. Both are now computed. §06 runs real git diff and GNU diff on real revisions of this repository’s own files and finds the longest common subsequence sets a floor that every tool respects and only some reach. §§04–05 rebuild git’s names from SHA-1 by hand, and then say what a name computed from content can and cannot promise, which is not what a drawing number promises.

The headline is §15. The source’s first unit test checks that an image normaliser returns values between −1 and 1. Run as printed on 8-bit pixels, the normaliser maps black to +1.0 instead of −1.0, and the test passes. So does a normaliser with its sign reversed, and so does one that returns zeros. The test is a gauge whose limits are wider than the tolerance. Most of the rest of the testing material follows from that one observation and from Sheet 04’s producer’s and consumer’s risk.

01

The shell, and a pipe is a kanban loop

src 01. linux and CMD ↗

A shell is a program that reads a line you type, starts the programs it names, and connects them. Sheet 13 part 2 §01 called the operating system the plant coordinator; the shell is the dispatcher’s window. A command has the form command [options] [arguments]: ls -la /home/user runs the program ls with the options -l and -a on the directory /home/user. The source’s tables of navigation, file and search commands are accurate and are not repeated here. What deserves a mechanical reading is the thing the source calls the shell’s killer feature.

A pipe, written a | b, sends everything a writes into b as its input. The two programs run at the same time, and the kernel holds the bytes in between in a buffer of fixed size: 65,536 bytes on this Linux machine ([Ch15 s01]). When the buffer is full, a is made to wait. When it is empty, b waits.

✓Identity: a pipe is a kanban loop

A kanban loop between two stations holds a fixed number of containers. The upstream station may produce only while it holds an empty container; the downstream station pulls full ones. Sheet 13 part 2 §13 showed that a counting semaphore is exactly this card count. A pipe is the same loop with 65,536 one-byte containers. The upstream program cannot run ahead of the downstream one by more than the buffer, so a fast producer cannot flood a slow consumer, and work-in-process is capped by construction.

It is a pull system in the other direction too. yes prints “y” forever, yet yes | head -3 finishes at once: when head has its three lines it exits, and the next write by yes into a pipe nobody reads kills it with the signal SIGPIPE. Its exit status is 141, which is 128 + 13, the number of SIGPIPE ([Ch15 s01]). Demand stopped, so production stopped.

Not every station can pass work along one piece at a time. A producer that writes “b”, waits one second, then writes “a” was piped into four different stages, and the time to the first line out was measured ([Ch15 s01]):

Time until the first line leaves each stage. The producer pauses 1 s between its two lines.
StageFirst line outWhy
cat0.00 sPasses each piece on as it arrives: one-piece flow.
sort1.01 sCannot emit anything until it has seen everything, because the last line read might sort first. A process batch of the whole input.

That is the distinction between a process batch, which an operation needs in order to work at all, and a transfer batch, which is only how much is moved at once. sort is a process batch by its nature. grep’s 4 KiB lot is a transfer batch chosen for efficiency, and it is why tail -f train.log | grep loss can appear to hang: the lines are there, waiting for the container to fill.

The text tools compose because each does one thing. uniq -c counts consecutive repeats only: on the lines a, b, a it reports three groups, and after sort it reports two ([Ch15 s01]). That is why the source’s error report sorts before it counts. Run on a synthetic log of 416 lines with nine error types, the source’s pipeline grep "ERROR" app.log | awk -F': ' '{print $2}' | sort | uniq -c | sort -rn | head -10 returned exactly what a Python counter returns on the same file. One detail in the source’s comments is loose: grep -c counts matching lines, not occurrences, so a file holding “loss loss” and “loss” gives 2, not 3.

!Where the analogy breaks

A kanban container holds a part. A pipe holds bytes, with no idea of where one record ends and the next begins. “Line” is a convention each program applies for itself by looking for newline characters, and §02 shows a file whose last record a line counter does not see. A downstream station that misreads a record boundary gets garbled parts, and no buffer limit prevents that.

02

Small tools, exact meanings

src 01. linux and CMD ↗

Every program starts with three numbered channels: 0 is input, 1 is normal output, 2 is error output. > file points channel 1 at a file. 2>&1 points channel 2 wherever channel 1 points at that moment. The shell applies redirections left to right, so order matters:

  • cmd > f 2>&1: channel 1 goes to the file, then channel 2 follows it. The file gets both lines ([Ch15 s02]).
  • cmd 2>&1 > f: channel 2 copies channel 1’s current target, the screen, and only then is channel 1 moved to the file. The file gets one line and the error still lands on the screen.

The source’s version is the right one. Its cheat sheet has three lines that do not do what their comments say, each checked ([Ch15 s02]):

  • cut -d',' -f1 data.csv | sort -u | wc -l, “count unique values in column 1”, counts the header as a value: 4 for a file with three labels. cut also splits on every comma, including one inside a quoted field such as "Pune, MH", because it knows nothing of CSV quoting.
  • wc -l, “count rows”, counts newline characters. A file of two rows whose last row has no newline after it reports 1.
  • du -sh --max-depth=1 . is refused by GNU du: “summarizing conflicts with --max-depth=1”. -s asks for one total, --max-depth=1 for one line per subdirectory. Drop the -s.

Permissions are nine bits: read, write and execute for the owner, the owner’s group, and everyone else. Each group of three is one octal digit with r = 4, w = 2, x = 1, so -rwxr-xr-- is 754 and chmod 755 gives -rwxr-xr-x ([Ch15 s02]). The source says chmod +x adds execute permission for everyone. It does so only under the usual default mask: with umask 022 the result is -rwxr-xr-x, and with umask 077 the same command gives -rwxr--r--, owner only. When +x names no class, the bits the mask forbids are left alone.

There is no mechanical analogy here worth drawing, and none is offered. These are exact meanings to learn, like the symbols on a weld callout, and the cost of getting one wrong is the same: the instruction is carried out exactly as written. rm -rf deletes with no recycle bin and no confirmation, which is the source’s warning and a correct one.

03

A process gets a copy

src 01. linux and CMD ↗

A process is a running program (Sheet 13 part 2 §02). Every process carries a small table of named text values, its environment: CUDA_VISIBLE_DEVICES=0,1 tells a training job which GPUs it may use, PATH lists the directories searched for programs. The source calls these “accessible to all programs”. That is wrong in a way that costs real debugging time. A process receives a copy of its parent’s exported variables at the moment it starts, and nothing after ([Ch15 s03]):

  • a variable set but not exported is invisible to a child: it prints [];
  • after export, a child started from then on sees it: [1];
  • a child that changes it changes only its own copy. The parent still reads [1].
✓Same structure: the job traveller

A traveller is copied from the master route card when a job is released, and goes to the shop floor with the parts. A later change to the master does not reach travellers already issued, and a note scribbled on one traveller does not reach the master or any other job. That is the environment exactly, and it explains three things that puzzle new users: a variable exported in one terminal window is absent in another; a script that runs cd or export cannot change the shell that started it; and a long training job keeps the settings it was launched with even after you edit .bashrc, which only applies to shells started later.

Two more corrections to the source’s process section, both checked ([Ch15 s03]). kill %1 is labelled “kill last background job”. %1 is job number 1, the first started; the most recent is %% or %+. With two jobs running, %1 stops the wrong one. And nohup is said to detach a process from the terminal. What it does is set the hang-up signal, SIGHUP, to ignored before starting the program, so the signal sent when your SSH connection drops has no effect. The kernel’s own record shows it: bit 0 of the process’s ignored-signal mask is 1 under nohup and 0 without. tmux works differently: it keeps a terminal alive on the server, so nothing is hung up at all.

Secrets belong in the environment or in an uncommitted .env file, never in code, for the reason §09 measures: once committed, a secret stays in the history.

04

What git stores: snapshots named by their content

src 02. git ↗

Git keeps the history of a project as a chain of commits, each a complete snapshot of every tracked file. The source’s four places are right: you edit files in the working directory, git add copies chosen changes to the staging area, git commit records the staging area as a new snapshot in the local repository (the hidden .git/ folder), and git push sends commits to a shared remote. What deserves care is how a snapshot is stored and named, because that is the debt from Sheet 14.

Git stores three kinds of object. A blob is the bytes of one file. A tree is a directory listing: file names, each with the name of its blob. A commit is a short text naming one tree, the commit or commits before it (its parents), the author, the time and the message. Every object’s name is the SHA-1 hash of its own bytes, with a short header in front. Part 1 of Sheet 14 §13 used a hash to place a key in a table; here a hash is the name. Each claim below was checked by building small repositories with fixed author and time ([Ch15 s04]):

  • The file shaft dia 20 h7 is 16 bytes. SHA-1 of blob 16\0shaft dia 20 h7\n, computed by hand in Python, is 6c18c62c76ea…, and git hash-object gives the same.
  • Two files with identical content, committed together, produce three objects: one blob shared by both names, one tree, one commit. Identical content is stored once.
  • The commit’s name, 284d6dca863c…, is the SHA-1 of its own text. A second repository built independently with the same files, author, time and message produced the same name, without asking anyone.
  • Change one character, h7 to h6, and commit. The blob’s name changes, so the tree that lists it changes, so the commit that names the tree changes. The untouched file keeps its blob. The new commit carries its parent’s name inside its own text.
✓Same structure: drawing revision control

A drawing office never stores a revision as a list of changes. Revision C of a drawing is a complete drawing, and its revision block records what changed and why. A commit is the same: a complete snapshot, plus a message. The parent link is the revision history, and a branch (§08) is the note saying which revision is current.

The new thing is the name. A drawing number is issued; a commit name is computed. The consequence follows from Fig. 15.1: a commit’s name covers its tree, its tree covers every file, and its text covers its parent’s name, which covers its parent. Change any byte anywhere in the past and every name after it changes. A commit name therefore certifies the entire history behind it, which no drawing number does.

The source says that git “internally stores diffs for efficiency”. Measured, that is wrong in the way it is usually meant ([Ch15 s04]). A 1,000-line, 41,670-byte file was committed, one line changed, and committed again. Both revisions sat in .git/objects whole: each decompresses to 41,681 bytes, the file plus the 11-byte header blob 41670\0. Only when git later packs its objects (git gc) does it compress similar objects against each other, and then it kept the newer revision whole and stored the older one as a 17-byte delta against it. That is the opposite of a change list, and sensible: the newest revision is the one read most. A delta here is a sequence of copy and insert instructions on bytes, chosen between any similar objects, not a line-by-line diff between a commit and its parent. The diff you read in a review is computed when you ask for it, which is §06.

So a hash gives up the one thing a registry guarantees, uniqueness for certain, and gets back something no registry can give: two people working offline, on different continents, name the same content identically, and nobody can alter content without changing its name. How much uniqueness is given up is a calculation. If \(n\) objects get independent random names of \(b\) bits, the chance that no two share a name is a product, and its approximation is the birthday bound:

$$\begin{aligned}P(\text{some two share a name}) &= 1-\prod_{i=1}^{n-1}\Big(1-\frac{i}{2^b}\Big)\\ &\approx 1-e^{-n^2/2^{b+1}}\end{aligned}$$

The chance reaches one half at \(n \approx 1.1774\cdot 2^{b/2}\): the square root of the number of names, not the number of names. For git’s full 160-bit SHA-1 names that is \(1.42\times10^{24}\) objects, and among a billion objects the chance of any accidental collision is about \(3.4\times10^{-31}\) ([Ch15 s05]). The seven-digit short names git prints are another matter. Seven hex digits are 28 bits, and the chance that some two objects in a repository share a seven-digit prefix reaches one half at 19,291 objects. Git lengthens its abbreviations as a repository grows (reported), and always stores the full name. A short hash in a log or an ECN is a convenience, not an identity.

06

A diff is a longest common subsequence

src 02. git ↗

git diff shows what changed between two revisions as lines removed (-) and lines added (+). Sheet 14 part 2 §18 said this is the longest common subsequence (LCS) problem and marked it as reported. Here is why it is exact.

Call the old file \(N\) lines and the new one \(M\) lines. A diff is a way to turn one into the other by deleting some old lines and inserting some new ones. The lines it does not touch appear in both files, in the same order, so they form a common subsequence. A diff that keeps \(K\) lines makes \(N-K\) deletions and \(M-K\) insertions. The fewest edits therefore keep the most lines, and the most lines that can be kept is the LCS length \(L\):

$$D_{\min} = N + M - 2L$$
$$L_{i,j} = \begin{cases} L_{i-1,j-1}+1 & a_i = b_j\\ \max\big(L_{i-1,j},\,L_{i,j-1}\big) & \text{otherwise}\end{cases}$$

The second line is Sheet 14’s recurrence for the table. So the claim to test is not “tools use LCS” but something sharper: no correct diff can report fewer than \(N+M-2L\) changed lines, and a tool that reaches that number has found an LCS. ✓Identity, with an honest qualifier

Comparing two revisions of a drawing’s notes by hand, you find the longest run of notes that survive in order and mark the rest as deleted or added. That is the LCS, and the minimum diff is exactly \(N+M-2L\). What real tools do is aim at that minimum. Plain Myers-style search hit it on every random pair and missed it by six blank lines on one real file. Patience and histogram diffs anchor on lines that occur once in each file, which tends to give diffs that are easier to read, and on random files they pay for that with longer edit scripts. The exact table costs \(N\times M\) cells, 837,120 for the third pair; Myers’ method costs about \((N+M)\,D\), small when the revisions are close (reported). So the LCS is the specification, and the tools are fast approximations to it.

07

Three-way merge, and why a vault locks drawings

src 02. git ↗

Two engineers edit the same file at the same time. A drawing vault prevents this: one engineer checks the drawing out, everyone else can only read it until it is checked back in. That is a lock, the mutex of Sheet 13 part 2 §12, and it rules out the lost update by making everyone else wait. Git takes the opposite policy. Anyone edits anything, and the edits are combined afterwards by a three-way merge: git finds the last commit both sides share, the base, and compares each side to it.

  • A region neither side changed is kept.
  • A region one side changed takes that side’s version.
  • A region both sides changed is taken if the two changes are identical, and is a conflict otherwise, left in the file between markers for a person to decide.

The source says a conflict happens “when two branches modify the same line”. Five cases on an eight-line file, merged by real git, show the rule is a little wider ([Ch15 s07]):

Adjacent edits conflict because there is no unchanged line between them to show where one change ends and the other begins; one untouched line is enough. The markers need care too. The source says the block under <<<<<<< HEAD is “the current branch’s version”. HEAD is wherever you are standing. In a merge into main you stand on main, so HEAD is main. In a rebase of your branch onto main (§08), git stands on main and replays your commits one by one, so HEAD is main again and your line is the one under =======. Measured on a config file with learning_rate = 0.0005 on your branch and 0.002 on main: during the rebase the HEAD block held 0.002 ([Ch15 s07]). Read the commit names in the markers, not the word HEAD.

✓Two policies for one problem

A lock pays in waiting: Sheet 13 part 2 §16 showed contention capping a whole system. A merge pays in conflicts, only when edits overlap. Which costs less depends on how often two people touch the same region. Source code is many small regions, so overlaps are rare and the merge wins. A CAD model saved as one binary file is a single region, so every concurrent edit overlaps, and that is why engineering vaults lock and why Git LFS added file locking for such files (reported). The vault is not old-fashioned; it is the right policy for its file type.

!Where it breaks: clean is not correct

A merge with no conflict is only a merge with no textual overlap. If one branch renames a function and the other adds a new call to the old name, the edits touch different lines, git merges them silently, and the result does not run. Two drawing changes can each be right and still not fit together; checking the assembly is a separate step. In software that step is the automated test run after every merge, §18.

08

Branches, rebase, and bisect

src 02. git ↗

A branch is a pointer to a commit, as the source says, and the pointer is literal: a 41-byte file holding one commit name and a newline ([Ch15 s08]). Creating a branch writes 41 bytes, which is why the source can say “branch always”. When you commit on a branch, git moves the pointer to the new commit.

There are two ways to bring a branch up to date with main. A merge adds a commit with two parents. A rebase replays each of your commits on top of main’s latest commit. A replayed commit has a different parent, so by §04 it has a different name: in the check, all three replayed commits got new names and none was kept, while the changes they carry were identical, as compared by git patch-id, which hashes the change itself ([Ch15 s08]). The source’s rule “never rebase commits that have been pushed and shared” follows directly. Colleagues hold the old names; after the rebase those names belong to a history that is no longer on the branch. It is re-issuing released drawings under new numbers while the shop floor still works from the old ones.

git bisect finds the commit that introduced a fault. You mark one commit good and one bad; git checks out the commit halfway between, you test it, and git keeps the half that must contain the change. It is bisection, the method of Sheet 13 part 1 §06 and Sheet 14 part 2 §15, run on history. A repository of 300 commits with a fault introduced at commit 187 was bisected with an automatic test: git named commit 187 after 8 builds, against \(\log_2 299 = 8.22\) ([Ch15 s08]).

!Where it breaks

Bisection needs a single change of sign between the two ends. Bisect needs the same: every commit after the culprit must test bad and every one before it good. A fault that comes and goes, or a test that fails at random, breaks the assumption, and bisect then names a wrong commit with full confidence; §24 computes how often. The source says atomic commits make bisect possible. Bisect works on any history; small commits make its answer useful, because the culprit it names is then small enough to read.

A commit message has the job of the reason-for-change field on an ECN. The diff already records what changed, computed (§06); only a person can record why. The source’s conventions, a summary of 50 characters or fewer in the imperative mood and a body wrapped at 72, are conventions, and good ones. Three of the source’s practical warnings, each checked ([Ch15 s09]):

  • Ignoring a file after committing it does nothing to the past. A .env file holding KEY=abc123 was committed, then added to .gitignore. Git went on tracking it (git status showed it modified). After git rm --cached .env it was untracked, and git show HEAD~1:.env still printed KEY=abc123. A committed secret has to be treated as published and changed at its source. Rewriting history removes it but renames every later commit (§08).
  • Large files are stored by name. A Git LFS pointer, the small file committed in place of a large one, is 129 bytes naming the real file by the SHA-256 of its content and its size. Content addressing again, with a longer hash.
  • The source’s way of logging the commit is broken twice. subprocess.check_output(['git', 'rev-parse', 'HEAD']).strip() returns bytes, so a log line built from it reads commit b'8539e9…'; add .decode() or pass text=True. More seriously, HEAD names the last commit. Edit a file without committing and HEAD’s name does not change, so the logged hash no longer names the code that ran. Names, registries and interfaces

src 03. codebase design ↗

File 03 is about arranging code so that a change stays cheap as the project grows. Its project layout keeps importable code under src/my_project/, entry-point scripts under scripts/, tests under tests/ and settings under configs/. The reason it gives for the src/ folder is checkable: from the project root, with nothing installed, a flat layout imports the package and a src/ layout refuses ([Ch15 s10]). That refusal is the point. With a flat layout, Python quietly imports whatever folder sits in the current directory, so tests pass against your working copy even if the installed package is broken. The src/ layout forces you to install the package and test what you would ship, the way a first-article inspection takes a part off the production line rather than the prototype off the bench.

The source says naming is the single most useful habit, and shows a badly named update loop beside a well-named one. The advice is right. The well-named code does nothing:

  • With a weight stored as a Python number, {"w": 1.0}, and a gradient of 0.5, one step at learning rate 0.1 leaves the weight at 1.0. With the weight stored as a NumPy array it becomes 0.95 ([Ch15 s10]).
  • The reason: for name, param in parameters.items(): param -= … computes a new number and points the loop’s local name param at it. The dictionary still holds the old number. An array is changed in place by -=, so the dictionary sees the change. The badly named version has the same bug, and both read a global gradients they were never given.

It is a bug of exactly the kind file 04 says ML code hides: nothing crashes, the model quietly fails to learn. A test that checked the weight moved would have caught it, which is §15’s subject.

The design patterns the source lists are lookup tables and connections. A registry maps a name in the configuration file to the code that builds it: MODEL_REGISTRY["transformer"] returns the transformer class, and adding a model adds one line. That is a part catalogue: the order names a part number, the catalogue returns the part, and a number not in the catalogue is refused at once (here, with a KeyError). A callback is code the training loop calls at fixed events; the source’s early-stopping callback is correct, stopping five epochs after the best loss ([Ch15 s10]).

✓Same structure: an interface control drawing

Dependency injection means a component is handed the things it uses instead of building them itself: Trainer(logger) rather than a trainer that creates its own W&B logger inside. An interface control drawing specifies only the mating features of a part, so any supplier’s part that meets them will fit. A trainer that accepts any object with a log method can be tested with a fake one, which is a dummy part made to the interface drawing so the assembly can be checked without the real supplier.

The rest of the section (short functions, single responsibility, “extract it on the third copy, not the first”, named constants instead of bare numbers) is sound practice and judgment rather than anything computable. A named constant is the software form of a general note on a drawing, ALL FILLETS R2 UNLESS STATED: one place to read the value and one place to change it.

Packaging, pinning, and interchangeability

src 03. codebase design ↗

A package is code made installable, so that other code imports it by name. Its description lives in pyproject.toml: name, version, dependencies, and a [build-system] table naming the build backend, the program pip calls to turn the source into an installable file. The source names setuptools.backends._legacy:_Backend. In setuptools 68.1.2 that module does not exist; pip, given the source’s file, stops with BackendUnavailable (exit status 2). The standard backend, setuptools.build_meta, loads in the same project and answers pip’s first request ([Ch15 s13]). Copy the source’s file and nothing installs.

A dependency is declared with a version rule, and the rules mean different things ([Ch15 s13], checked with Python’s own packaging library): torch>=2.0 accepts 3.0; torch~=2.2 accepts 2.9 but not 3.0; torch==2.2.1 accepts 2.2.1 and nothing else.

✓Same structure: form, fit and function

A drawing office keeps a part’s number through a change that preserves form, fit and function, and only raises its revision; a change that breaks interchangeability gets a new part number. Semantic versioning, a convention most Python packages follow (reported), says the same with three numbers: MAJOR.MINOR.PATCH, where a new MAJOR number announces that something no longer fits.

Read the rules that way. >=2.0 is “revision 2 or any later one, including one that no longer fits”. ~=2.2 is “any later revision of the same part number”. ==2.2.1 is “this revision only”. The file pip freeze writes, every package at one exact version, is the as-built record of an environment.

!Where the analogy breaks

A change board enforces form-fit-function. Semantic versioning is a promise each package’s authors make about their own releases, and the source itself warns that a minor version can change numerical results. So the two jobs separate. A library declares a range, saying what it is compatible with; an experiment or a deployment pins exact versions, saying what it was built with. The source’s advice to pin is right for the second job and wrong for the first: a library that pins exactly cannot be installed beside any other library that pins differently.

Testing is not lot sampling, except when it is

beyond the source

Sheet 04 §06 showed that a hypothesis test is an acceptance-sampling plan, and §07 named its two errors producer’s risk and consumer’s risk. It is tempting to carry the whole apparatus over to software testing. Most of it does not carry, for a reason §04 has already measured: every copy of a program is bit-identical, down to its name.

Acceptance sampling exists because units from one process vary, and you cannot afford to inspect them all. A program has no unit-to-unit variation. Test one copy and you have tested every copy; run a fixed test twice on the same code and you get the same answer. Every software defect is therefore a design defect, and a test suite is not lot sampling but design verification: first-article inspection of the one article there is.

Sampling comes back in through a different door. A program is run on inputs, and the inputs are where the variation lives. Random testing (the industry name is property-based testing, which the source does not mention) draws \(n\) inputs at random and checks a property of each output. If a bug spoils a fraction \(\theta\) of all inputs, the chance that \(n\) random inputs all miss it is exactly the operating characteristic of a single sampling plan with acceptance number zero:

$$P(\text{all pass}) = (1-\theta)^n, \qquad \theta_{95} = 1-0.05^{1/n} \approx \frac{3}{n}$$

The second expression inverts the first: after \(n\) passing random tests, you can say with 95% confidence that \(\theta\) is below \(1-0.05^{1/n}\). That is the rule of three, and it is close: 0.0950 against 3/30, 0.00994 against 3/300, 0.00100 against 3/3000 ([Ch15 s16]). A bug that touches 1% of inputs is found by 300 random inputs with probability \(1-0.99^{300} = 0.951\); simulated, 0.949.

✓Identity: a zero-failure demonstration test

Reliability engineering has the same calculation as a hand procedure: to demonstrate reliability \(R\) at confidence \(C\) with no failures allowed, test \(n = \ln(1-C)/\ln R\) units. Put \(R = 1-\theta\) and \(C = 0.95\) and it is the rule of three. The formulas are the same and so is the sentence that goes with them: “we saw no failures in \(n\) trials, so the failure rate is probably below about \(3/n\)”.

!Where it breaks: bugs are not scattered at random

The formula assumes the bug is spread through the inputs like defectives through a lot. Bugs cluster at boundaries: zero, empty, the largest value, the first and last element. A bug triggered by exactly one 32-bit input is found by 1,000 random inputs with probability \(2.3\times10^{-7}\), and by one deliberate test of that input with certainty ([Ch15 s16]). So most of a good test suite is chosen, not drawn: boundary values first, which is what the source’s empty-input test is doing, and random inputs as a supplement that finds what nobody thought to choose.

The two risks do carry over, renamed. A test that sometimes fails on correct code is called flaky: it is producer’s risk, rejecting a good change. A bug that gets through is consumer’s risk. And a test suite is a series system in Sheet 05 §03’s sense, because a single red test stops the change. With \(N\) tests each flaky with probability \(f\):

$$\alpha_{\text{suite}} = 1-(1-f)^N$$

A thousand tests, each flaky one time in a thousand, turn a correct change red 63.2% of the time ([Ch15 s16]). That is why teams rerun failures. Rerunning once and passing if either run passes cuts the false-alarm rate to about \(1.0\times10^{-3}\), and a deterministic bug still fails both runs. But a bug that fails half the time now slips through each test with probability \(0.5^2 = 25\%\) instead of 50%. The same trade as Sheet 04 §07: with nothing else changed, lowering one risk raises the other; only better information, here a test that is not flaky, lowers both.

Tolerances, and tests with no teeth

src 04. testing and QA ↗

The source’s advice for testing ML code is sound: fix the random seeds, compare floating-point results within a tolerance, check output shapes, check that gradients reach every parameter, check that the model can memorise one batch, and validate the data. Its details need three corrections.

First, “exact comparison fails due to floating point” is true of most values and false of the one in its example. 0.5 is exactly representable in binary, and 0.25 + 0.25 == 0.5 is true; 0.1 + 0.2 == 0.3 is false ([Ch15 s17]; Sheet 13 part 1 §10 explains why). The habit of comparing with a tolerance is right either way.

Second, the tolerance is not where it appears to be. np.isclose(a, b) passes when

$$|a-b| \le \text{atol} + \text{rtol}\cdot|b|$$

with a default rtol of \(10^{-5}\) that the source’s call np.isclose(model_output, 0.5, atol=1e-5) does not mention. Its effective band is \(\pm1.5\times10^{-5}\), so it accepts \(0.5 + 1.4\times10^{-5}\) and rejects \(0.5 + 1.6\times10^{-5}\). And the band is built around the second argument only, so the comparison is not symmetric: with \(a = 1\) and \(b = 1 + 1.00001\times 10^{-5}\) and rtol=1e-5, isclose(a, b) is true and isclose(b, a) is false ([Ch15 s17]).

✓Same structure: tolerance on the nominal

A tolerance is stated about a nominal, not about a pair of measurements. 20 ±0.02 means the band sits around 20. np.isclose treats its second argument as the nominal and builds the relative part of the band from it, so put the expected value second, always. math.isclose, in Python’s standard library, uses the larger of the two magnitudes and is symmetric (reported).

Third, the determinism test. It sets the seed, runs the model, sets the seed again, runs it again, and checks the two outputs match. On a model with no randomness in its forward pass, which is every model in evaluation mode, the outputs match whether or not the seed is set: the test passes with set_seed removed entirely ([Ch15 s17]). It only has teeth when randomness is active, as with dropout in training mode, where the unseeded version does fail. Sheet 13 part 1 §03 called this vacuous truth, and an acceptance criterion that no part can fail is not inspecting anything.

The source’s other ML tests are good inspections. Overfit one batch is a capability check on the easiest possible job: a machine that cannot hold tolerance on one part will not hold it on a lot. The gradient-flow test can raise false alarms, since a parameter that a particular batch never uses (an embedding row for a word absent from the batch) legitimately has zero gradient. Mocking replaces an outside service with a stand-in that answers through the same interface, a dummy load on a test rig; the source’s rule to mock at the boundaries and test your own logic directly is right. And a pytest fixture, the setup a test needs, earns its name honestly: a test fixture holds the item in a known state before it is measured.

Continuous integration is jidoka

src 04. testing and QA ↗

Continuous integration (CI) means a server runs the checks automatically on every push and every pull request: the source’s workflow installs the package, runs the linter ruff, the type checker mypy and the tests. A linter checks code against rules without running it, as a checker reads a drawing against the drafting standard. A type checker confirms that values of the right kind flow into each place, which Sheet 13 part 3 §02 showed is dimensional homogeneity for programs.

✓Same structure: jidoka and poka-yoke

Jidoka is the Toyota principle that a machine stops itself when it makes a defect, so a defect is never passed down the line. CI with required checks is jidoka for code: a red check stops the merge, and the fault is fixed where it was made. A pre-commit hook, which runs the linter on your own machine before git will even record the commit, is poka-yoke at the operator’s station: the mistake is caught before it leaves the bench. The source’s review labels, blocking:, suggestion:, nit:, are defect classification: critical, major, minor.

The source says that if the tests fail, “the PR cannot be merged”. Read the workflow file: it runs the checks and reports the result, and contains no rule about merging. Blocking the merge is a separate setting on the repository that makes the check required (reported; GitHub calls it branch protection). Without that setting, a red check is an andon lamp that nobody wired to the line stop.

The order of the checks matters once you see that the pipeline stops at the first failure. A check costing \(c_i\) runs only if every check before it passed, so the expected cost is \(\sum_i c_i \prod_{j<i}(1-p_j)\), where \(p_j\) is the chance check \(j\) fails. Swapping two neighbours and comparing gives the rule: run checks in increasing order of \(c_i/p_i\). That is the classical result for sequencing inspections that stop at the first reject, and it matched an exhaustive search on 300 random pipelines, where “cheapest first” alone was worse in 196 ([Ch15 s18]). For a linter taking 5 s that fails 20% of the time, type checks taking 60 s that fail 5%, and tests taking 600 s that fail 10%, the rule gives the source’s order, with an expected 509 s per run against 658 s with the tests first.

A container is a palletised fixture

An image is a packaged file system, built from a recipe called a Dockerfile whose lines each add a layer: start from a base image, install system packages, install Python packages, copy in the code, name the command to run. docker run starts a container from the image.

✓Same structure: a palletised fixture

On a flexible manufacturing line the workpiece is clamped once onto a standard pallet, and the pallet locates on any machine with the matching zero-point receiver. Setup is done once, off the machine, and repeated identically everywhere. An image is that pallet: the program with everything it needs above the operating system, located on any host through one standard interface, the kernel’s system calls. “It works on my machine” becomes “it works on any machine with this receiver”.

!Where the analogy breaks, and a qualification to Sheet 13

Sheet 13 part 2 §10 said an image runs identically everywhere. Everything inside the image is identical; the machine is not in the image. The kernel belongs to the host, and so does the GPU driver: docker run --gpus all passes the host’s driver into the container (reported). An image built for one CUDA version can fail on a host whose driver is too old, exactly as a pallet locates perfectly on a machine whose spindle cannot reach the speed the job needs. The pallet brings the setup, not the spindle.

The source’s example Dockerfile would not run the program it names, for three reasons:

  • The command points at code the image does not have, or cannot import. File 03 put entry scripts in a top-level scripts/ folder; the Dockerfile copies only src/ and configs/ and runs src/scripts/serve.py. Even with the script there, a src/-layout package that was never installed cannot be imported: a mock of that tree, run the same way, stops with ModuleNotFoundError: No module named 'my_project' ([Ch15 s19]). The image needs a pip install . step, which is §10’s point arriving at deployment.
  • It installs Python 3.11 and then uses another Python. pip and python3 refer to the distribution’s default interpreter, which on Ubuntu 22.04 is 3.10 (reported), so the requirements are installed for 3.10 and 3.11 is never used.
  • The multi-stage example copies packages to a path stamped with a version. pip install --user writes into a folder whose name contains the interpreter’s version, here ~/.local/lib/python3.13/site-packages ([Ch15 s19]). Packages built in the python:3.11 stage are only found by a Python 3.11 in the final stage, and the CUDA runtime image it copies them into does not ship Python at all (reported). Build and run stages must use the same interpreter.

Layer order is “paint last”

src 05. deployment and devops ↗

Docker keeps every layer it has built. On a rebuild it reuses a layer if that line of the Dockerfile, the files it copies, and every layer before it are unchanged; once one layer changes, every layer after it is rebuilt. The cache key of each layer covers the key of the one before, the same chain as commit names in §04: change layer 4 of 5 and layers 1–3 are reused, 4 and 5 are not ([Ch15 s20], on a model of the chain). So the source’s advice is to put what rarely changes first and what often changes last: install the Python packages before copying in the code, so that editing one line of code does not reinstall everything.

✓Identity: delayed differentiation

A garment maker that dyes sweaters after knitting them, rather than knitting from dyed yarn, can change the colour mix without re-knitting anything. Do the common operations first and the variant-specific ones last, so a change to a variant reworks only the end of the route. A Dockerfile is a route, and the cache makes the economics the same.

“Rarely changing first” is the rule when every step costs the same. When costs differ it needs a correction, which a short derivation supplies. Let step \(i\) take \(c_i\) seconds and change on a given build with probability \(p_i\). Step \(i\) is rebuilt if it or any step before it changed, so the expected rebuild time per build is

$$E = \sum_i c_i\Big(1-\prod_{j\le i}(1-p_j)\Big)$$

Swap two neighbouring steps and compare the two totals; everything else cancels, and step \(i\) should come before step \(j\) exactly when

$$\frac{p_i}{c_i\,(1-p_i)} \;<\; \frac{p_j}{c_j\,(1-p_j)}$$

Sorting by that ratio gave the best of every possible order on 300 random Dockerfiles, checked against all permutations; ordering by change frequency alone was worse in 235 of them, by up to 1.72 times the optimum ([Ch15 s20]). It is the same adjacent-exchange argument that proves Johnson’s rule and the shortest-processing-time rule (Sheet 13 part 2 §04, Sheet 14 part 2 §17), and §18’s inspection order is its sibling. The ratio says: an expensive step that changes fairly often can still belong early, because rebuilding it is what you are trying to avoid.

Experiment tracking is traceability

src 05. deployment and devops ↗

An experiment tracker (the source names Weights & Biases and MLflow) records, for every training run, the configuration, the metrics as training proceeds, and the files produced. A model registry records which trained model is in which stage, from development to production, and what produced it.

✓Same structure: lot genealogy

A traceability record ties a finished part to the heat number of its bar stock, the machine, the program revision, the operator and the gauges used to pass it. The source’s reproducibility checklist is the same record for a model: commit (program revision), config (process settings), random seeds, data version (heat number), environment (machine and tooling), hardware. A model registry is the record of which lot is released to which customer.

The source’s W&B loop has a bug. It saves the model when val_loss < best_loss but never updates best_loss, so the condition compares every epoch with the starting value. For validation losses 0.90, 0.80, 0.85, 0.70, 0.75, 0.72 it saves at all six epochs; updating best_loss saves at epochs 0, 1 and 3 ([Ch15 s21]). File 03’s early-stopping callback, which does update its best value, is the correct version of the same logic.

The source then says the image hash is “a complete environment fingerprint” and that reproducing the image reproduces the training. Both halves overreach. An image’s digest names one built image, and rebuilding from the same Dockerfile later does not give that image back, because steps such as apt-get update fetch whatever is current (§20). Keep the image itself, by digest, not only the recipe: the route card is not the part. And the digest leaves out the kernel, the driver and the GPU (§19), while GPU arithmetic that adds numbers in a varying order gives slightly different sums (Sheet 13 part 1 §11). The digest is necessary for reproducibility, not sufficient.

Monitoring: tails and drift

src 05. deployment and devops ↗

A deployed model is watched for latency, throughput, error rate, accuracy where labels arrive, and drift, a change in the inputs (data drift) or in the relation between inputs and correct outputs (concept drift). Serving and capacity are Sheet 17’s and Sheet 18’s subjects; two things in the source need fixing here.

Percentiles. The p99 latency is the time that 99% of requests beat. The source says “a p99 of 500ms means 1 in 100 users waits half a second”. It means 1 in 100 requests takes at least half a second, possibly much longer, since p99 says nothing about the tail beyond it. And users are not requests. A page that makes \(k\) requests meets at least one slow one with probability

$$P(\text{page meets a slow request}) = 1-0.99^k$$

which is 9.6% for 10 requests and 63.4% for 100; a simulation with log-normal latencies gave 63.0% ([Ch15 s22]). It is the third appearance of the series-system formula on this sheet, after the random test in §16 and the flaky suite after it.

Drift scores. The source names the Kolmogorov–Smirnov test and the population stability index (PSI). PSI compares the fraction \(a_k\) of live inputs in each histogram bin with the fraction \(e_k\) seen in training:

$$\text{PSI} = \sum_k (a_k-e_k)\ln\frac{a_k}{e_k} = \mathrm{KL}(a\,\|\,e)+\mathrm{KL}(e\,\|\,a)$$

The identity, checked on 200 random histograms ([Ch15 s22]), says PSI is the Kullback–Leibler divergence of Sheet 05 §08 taken both ways and added, so it is symmetric in the two distributions. The usual alarm levels of 0.1 and 0.25 are rules of thumb (reported), not derived.

✓Same structure: a control chart

Drift monitoring is statistical process control (Sheet 04): limits set from a reference period, here the training data, and a statistic plotted against them. The source’s alert “if p99 exceeds 200 ms for 5 minutes” is a run rule: requiring the signal to persist trades a slower alarm for fewer false ones, the same producer’s and consumer’s risk as §16.

!Where it breaks

A control chart assumes the process should stay where it was during the reference period. Real inputs drift for legitimate reasons, seasons and new customers among them, so the reference goes stale and needs a policy for renewal. And concept drift cannot be seen in the inputs at all: the inputs can look exactly as they did in training while the right answers have changed. Only labelled outcomes reveal it, and they usually arrive late.

A pipeline is a precedence diagram, again

src 05. deployment and devops ↗

An orchestrator such as Airflow runs a pipeline of tasks (ingest, preprocess, train, evaluate, deploy) declared as a directed acyclic graph: each task names the tasks it must wait for. That is a precedence diagram, and the orchestrator starts a task when everything before it has finished, which is Fulkerson’s rule and Kahn’s topological sort, proved the same in Sheet 14 part 2 §10. A loop in the graph means the pipeline can never start, which is why the graph must be acyclic. The source’s example, preprocess >> train >> evaluate >> deploy, is a single chain, a serial line; real pipelines branch, and the critical path through them is Sheet 14 part 1 §09’s forward pass.

✓Same structure: gauge correlation

A feature store computes each input feature once and serves the same value to training and to the live model. The problem it solves, training-serving skew, is a supplier and a customer measuring the same feature by different methods and disagreeing about good parts. The cure in both trades is one agreed method, used at both ends.

The source’s guidance on when to adopt an orchestrator (more than a few steps, a schedule, several teams, automatic retries) is judgment and reads as sound. Where to go from here, designing whole systems around these pieces, is Sheet 18.

Worked example: which of 300 commits broke the model?

whole chapter

A model scored well at release v1.4. Today’s version scores badly. There are 300 commits in between. The regression check, a short training run and an evaluation, takes 20 minutes, and because GPU arithmetic is not perfectly repeatable, it fails a good build 5% of the time; a broken build always fails. Find the culprit and say how sure you are.

Solved as a quality engineer with a drawing history

The ECN log lists 300 changes. Testing them in order is linear search: 150 tests on average, 50 hours. Halving instead, testing the middle revision and keeping the half that must contain the change, needs \(\lceil\log_2 300\rceil = 9\) tests at most. Each test is an inspection with a 5% producer’s risk, and one false reject sends the search into the wrong half for good. The search only goes wrong on a revision that really is good, and on the way to the culprit you meet about four of those, so the chance of the right answer is about \(0.95^4 \approx 0.81\). The fix from §16 applies: call a revision bad only if it fails twice. The false-reject rate per test drops to \(0.05^2 = 0.0025\).

Solved with git

git bisect start <bad> <good>, then git bisect run ./regress.sh, where the script exits with failure only if the evaluation fails twice in a row. Git checks out each midpoint, runs the script, and names the first bad commit. git show on that commit prints its diff, computed as in §06, and its message, the ECN’s reason for change.

Question bank

whole chapter

Twenty-four prompts in three tiers. Answer before opening. The numerical answers in tier 2 are checked by [Ch15 s26].

Tier 1 — recall
What happens to the writer of a pipe when the buffer is full, and when the reader exits?

When the 65,536-byte buffer is full the writer waits. When the reader has exited, the writer’s next write kills it with SIGPIPE (exit status 141): demand stopped, so production stops.

Name git’s three kinds of object and say how each is named.

Blob (file bytes), tree (names to blobs and trees), commit (tree, parents, author, time, message). Each is named by the SHA-1 of its own bytes with a type-and-size header.

How is the length of the shortest diff related to the longest common subsequence?

\(D = N + M - 2L\). The untouched lines form a common subsequence, so the fewest edits keep the longest one.

In a three-way merge, when do two edits conflict?

When both sides change the same region relative to the common base and the changes differ. Adjacent lines count as one region; identical changes merge cleanly.

Why does the source’s error report run sort before uniq -c?

uniq -c counts only consecutive repeats. Sorting puts equal lines next to each other.

What is a flaky test in inspection terms, and how does a suite’s false-alarm rate grow with its size?

Producer’s risk: rejecting a good change. A suite is a series system, so \(\alpha = 1-(1-f)^N\).

State the rule of three.

After \(n\) passing random trials, the failing fraction is below about \(3/n\) with 95% confidence; exactly, below \(1-0.05^{1/n}\).

What does np.isclose(a, b) test, exactly?

\(|a-b| \le \text{atol} + \text{rtol}\,|b|\), with default rtol \(10^{-5}\). The band is built around b, so swapping the arguments can change the answer.

Tier 2 — apply
A repository holds 50,000 objects. What is the chance that some two share their first seven hex digits?

Seven digits are 28 bits. \(1-e^{-n^2/2^{29}}\) with \(n = 50{,}000\) gives 0.9905. Practically certain, which is why git lengthens short names in large repositories.

The old file has 120 lines, the new one 125, and their LCS is 110 lines. What does the shortest diff contain?

\(120 + 125 - 220 = 25\) changed lines: 10 deletions and 15 insertions.

How many builds does bisect need to search 1,000 commits?

\(\lceil\log_2 1000\rceil = 10\).

2,000 tests, each flaky 0.05% of the time. How often does a correct change go red, and with one automatic rerun of failures?

\(1-0.9995^{2000} = 0.632\). With a rerun the per-test rate is \(0.0005^2\), and the suite goes red with probability about \(5.0\times10^{-4}\).

500 random inputs all pass. What can you say about the fraction of inputs that fail?

With 95% confidence it is below \(1-0.05^{1/500} = 0.00597\), against the rule of three’s 0.0060. Nothing at all about a bug at one specific input.

CI checks: lint 10 s, fails 10%; unit tests 120 s, fail 30%; integration tests 900 s, fail 20%. Best order, and the expected time per run?

Sort by cost over failure probability: 100, 400, 4,500. So lint, unit, integration, with expected \(10 + 0.9\times120 + 0.9\times0.7\times900 = 685\) s.

Dockerfile step A takes 300 s and changes on 10% of builds; step B takes 5 s and changes on 50%. Which goes first?

A: its ratio \(p/(c(1-p))\) is \(3.7\times10^{-4}\) against B’s 0.2. Expected rebuild 32.75 s with A first, 167.5 s with B first.

A page makes 30 requests. How often does it meet a request slower than the p99?

\(1-0.99^{30} = 0.260\): about one page in four.

Tier 3 — judge
Your team wants to keep CAD part files in git and merge as the programmers do. Advise.

A binary part file is one region, so every concurrent edit conflicts and no line merge can combine them. Use a lock: a PDM vault, or file locking in Git LFS. The vault’s policy is right for its file type (§07).

“The test suite passed, so the function is correct.” What do you ask?

Can these tests fail? Feed them known-wrong versions and see. Range checks such as the source’s pass broken code; exact-value or round-trip tests do not (§15).

Should a library you publish pin torch==2.2.1?

No. A library states what it is compatible with, as a range; an application or an experiment pins what it was built with. A library that pins exactly cannot be installed next to another that pins differently (§13).

Is a commit hash a better identifier than a drawing number?

It is different. It needs no registry, gives identical content the same name, and makes silent edits impossible. It has no order, means nothing to a person, is unique only with overwhelming probability, and its short form collides in large repositories (§05).

CI is red on 40% of runs of unchanged code. Should failures be rerun automatically?

Reruns cut the false alarms but let intermittent bugs through and hide the flakiness. Fix or quarantine the flaky tests and track them; a rerun policy is a deliberate trade of producer’s risk for consumer’s, as in Sheet 04 §07.

“Keep the Docker image digest and the training is reproducible.” Agree?

Necessary, not sufficient. Kernel, driver and GPU are outside the image; GPU sums can vary with order; and rebuilding the Dockerfile later gives a different image, so keep the image itself (§§19–21).

When does random testing earn a place beside hand-picked boundary tests?

When the input space is large and the property is cheap to check. It bounds the failing fraction by about \(3/n\) and finds cases nobody thought to pick. It never replaces boundary tests, because bugs cluster where random draws rarely land (§16).

The bridge bank paired version control with drawing revision control. Where does that pairing most mislead?

On names and on merging. Names are computed from content and certify the whole history, but carry no order; differences are computed, not written; and git merges optimistically where a vault locks. A clean merge is not a checked assembly (§§04–07).
