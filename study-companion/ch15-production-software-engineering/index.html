Revisions, Gauges and Fixtures

Version control is drawing revision control, with two changes that matter: the names are computed from the content instead of issued by a registry, and the differences between revisions are computed instead of written on an ECN. Testing is gauging, and the chapter’s own test is a gauge that accepts a broken part. A container is a palletised fixture that leaves the machine bed behind.

This sheet covers the chapter’s five files: the command line, git, codebase design, testing, and deployment. It also pays two debts Sheet 14 part 2 left with you. Its §18 said that comparing two revisions line by line is the longest common subsequence problem, and marked that as reported; its §22 said that hashing is how version-control systems name what they store, also reported. Both are now computed. §06 runs real git diff and GNU diff on real revisions of this repository’s own files and finds the longest common subsequence sets a floor that every tool respects and only some reach. §§04–05 rebuild git’s names from SHA-1 by hand, and then say what a name computed from content can and cannot promise, which is not what a drawing number promises.

The headline is §15. The source’s first unit test checks that an image normaliser returns values between −1 and 1. Run as printed on 8-bit pixels, the normaliser maps black to +1.0 instead of −1.0, and the test passes. So does a normaliser with its sign reversed, and so does one that returns zeros. The test is a gauge whose limits are wider than the tolerance. Most of the rest of the testing material follows from that one observation and from Sheet 04’s producer’s and consumer’s risk.

01

The shell, and a pipe is a kanban loop

src 01. linux and CMD ↗

A shell is a program that reads a line you type, starts the programs it names, and connects them. Sheet 13 part 2 §01 called the operating system the plant coordinator; the shell is the dispatcher’s window. A command has the form command [options] [arguments]: ls -la /home/user runs the program ls with the options -l and -a on the directory /home/user. The source’s tables of navigation, file and search commands are accurate and are not repeated here. What deserves a mechanical reading is the thing the source calls the shell’s killer feature.

A pipe, written a | b, sends everything a writes into b as its input. The two programs run at the same time, and the kernel holds the bytes in between in a buffer of fixed size: 65,536 bytes on this Linux machine ([Ch15 s01]). When the buffer is full, a is made to wait. When it is empty, b waits.

✓Identity: a pipe is a kanban loop

A kanban loop between two stations holds a fixed number of containers. The upstream station may produce only while it holds an empty container; the downstream station pulls full ones. Sheet 13 part 2 §13 showed that a counting semaphore is exactly this card count. A pipe is the same loop with 65,536 one-byte containers. The upstream program cannot run ahead of the downstream one by more than the buffer, so a fast producer cannot flood a slow consumer, and work-in-process is capped by construction.

It is a pull system in the other direction too. yes prints “y” forever, yet yes | head -3 finishes at once: when head has its three lines it exits, and the next write by yes into a pipe nobody reads kills it with the signal SIGPIPE. Its exit status is 141, which is 128 + 13, the number of SIGPIPE ([Ch15 s01]). Demand stopped, so production stopped.

Not every station can pass work along one piece at a time. A producer that writes “b”, waits one second, then writes “a” was piped into four different stages, and the time to the first line out was measured ([Ch15 s01]):

Time until the first line leaves each stage. The producer pauses 1 s between its two lines.
StageFirst line outWhy
cat0.00 sPasses each piece on as it arrives: one-piece flow.
sort1.01 sCannot emit anything until it has seen everything, because the last line read might sort first. A process batch of the whole input.
grep .1.01 sCould pass each line on, but when writing into a pipe it collects output in 4 KiB lots before shipping. A transfer batch.
grep --line-buffered .0.01 sTransfer batch of one line.

That is the distinction between a process batch, which an operation needs in order to work at all, and a transfer batch, which is only how much is moved at once. sort is a process batch by its nature. grep’s 4 KiB lot is a transfer batch chosen for efficiency, and it is why tail -f train.log | grep loss can appear to hang: the lines are there, waiting for the container to fill.

The text tools compose because each does one thing. uniq -c counts consecutive repeats only: on the lines a, b, a it reports three groups, and after sort it reports two ([Ch15 s01]). That is why the source’s error report sorts before it counts. Run on a synthetic log of 416 lines with nine error types, the source’s pipeline grep "ERROR" app.log | awk -F': ' '{print $2}' | sort | uniq -c | sort -rn | head -10 returned exactly what a Python counter returns on the same file. One detail in the source’s comments is loose: grep -c counts matching lines, not occurrences, so a file holding “loss loss” and “loss” gives 2, not 3.

!Where the analogy breaks

A kanban container holds a part. A pipe holds bytes, with no idea of where one record ends and the next begins. “Line” is a convention each program applies for itself by looking for newline characters, and §02 shows a file whose last record a line counter does not see. A downstream station that misreads a record boundary gets garbled parts, and no buffer limit prevents that.

02

Small tools, exact meanings

src 01. linux and CMD ↗

Every program starts with three numbered channels: 0 is input, 1 is normal output, 2 is error output. > file points channel 1 at a file. 2>&1 points channel 2 wherever channel 1 points at that moment. The shell applies redirections left to right, so order matters:

  • cmd > f 2>&1: channel 1 goes to the file, then channel 2 follows it. The file gets both lines ([Ch15 s02]).
  • cmd 2>&1 > f: channel 2 copies channel 1’s current target, the screen, and only then is channel 1 moved to the file. The file gets one line and the error still lands on the screen.

The source’s version is the right one. Its cheat sheet has three lines that do not do what their comments say, each checked ([Ch15 s02]):

  • cut -d',' -f1 data.csv | sort -u | wc -l, “count unique values in column 1”, counts the header as a value: 4 for a file with three labels. cut also splits on every comma, including one inside a quoted field such as "Pune, MH", because it knows nothing of CSV quoting.
  • wc -l, “count rows”, counts newline characters. A file of two rows whose last row has no newline after it reports 1.
  • du -sh --max-depth=1 . is refused by GNU du: “summarizing conflicts with --max-depth=1”. -s asks for one total, --max-depth=1 for one line per subdirectory. Drop the -s.

Permissions are nine bits: read, write and execute for the owner, the owner’s group, and everyone else. Each group of three is one octal digit with r = 4, w = 2, x = 1, so -rwxr-xr-- is 754 and chmod 755 gives -rwxr-xr-x ([Ch15 s02]). The source says chmod +x adds execute permission for everyone. It does so only under the usual default mask: with umask 022 the result is -rwxr-xr-x, and with umask 077 the same command gives -rwxr--r--, owner only. When +x names no class, the bits the mask forbids are left alone.

There is no mechanical analogy here worth drawing, and none is offered. These are exact meanings to learn, like the symbols on a weld callout, and the cost of getting one wrong is the same: the instruction is carried out exactly as written. rm -rf deletes with no recycle bin and no confirmation, which is the source’s warning and a correct one.

03

A process gets a copy

src 01. linux and CMD ↗

A process is a running program (Sheet 13 part 2 §02). Every process carries a small table of named text values, its environment: CUDA_VISIBLE_DEVICES=0,1 tells a training job which GPUs it may use, PATH lists the directories searched for programs. The source calls these “accessible to all programs”. That is wrong in a way that costs real debugging time. A process receives a copy of its parent’s exported variables at the moment it starts, and nothing after ([Ch15 s03]):

  • a variable set but not exported is invisible to a child: it prints [];
  • after export, a child started from then on sees it: [1];
  • a child that changes it changes only its own copy. The parent still reads [1].
✓Same structure: the job traveller

A traveller is copied from the master route card when a job is released, and goes to the shop floor with the parts. A later change to the master does not reach travellers already issued, and a note scribbled on one traveller does not reach the master or any other job. That is the environment exactly, and it explains three things that puzzle new users: a variable exported in one terminal window is absent in another; a script that runs cd or export cannot change the shell that started it; and a long training job keeps the settings it was launched with even after you edit .bashrc, which only applies to shells started later.

Two more corrections to the source’s process section, both checked ([Ch15 s03]). kill %1 is labelled “kill last background job”. %1 is job number 1, the first started; the most recent is %% or %+. With two jobs running, %1 stops the wrong one. And nohup is said to detach a process from the terminal. What it does is set the hang-up signal, SIGHUP, to ignored before starting the program, so the signal sent when your SSH connection drops has no effect. The kernel’s own record shows it: bit 0 of the process’s ignored-signal mask is 1 under nohup and 0 without. tmux works differently: it keeps a terminal alive on the server, so nothing is hung up at all.

Secrets belong in the environment or in an uncommitted .env file, never in code, for the reason §09 measures: once committed, a secret stays in the history.

04

What git stores: snapshots named by their content

src 02. git ↗

Git keeps the history of a project as a chain of commits, each a complete snapshot of every tracked file. The source’s four places are right: you edit files in the working directory, git add copies chosen changes to the staging area, git commit records the staging area as a new snapshot in the local repository (the hidden .git/ folder), and git push sends commits to a shared remote. What deserves care is how a snapshot is stored and named, because that is the debt from Sheet 14.

Git stores three kinds of object. A blob is the bytes of one file. A tree is a directory listing: file names, each with the name of its blob. A commit is a short text naming one tree, the commit or commits before it (its parents), the author, the time and the message. Every object’s name is the SHA-1 hash of its own bytes, with a short header in front. Part 1 of Sheet 14 §13 used a hash to place a key in a table; here a hash is the name. Each claim below was checked by building small repositories with fixed author and time ([Ch15 s04]):

  • The file shaft dia 20 h7 is 16 bytes. SHA-1 of blob 16\0shaft dia 20 h7\n, computed by hand in Python, is 6c18c62c76ea…, and git hash-object gives the same.
  • Two files with identical content, committed together, produce three objects: one blob shared by both names, one tree, one commit. Identical content is stored once.
  • The commit’s name, 284d6dca863c…, is the SHA-1 of its own text. A second repository built independently with the same files, author, time and message produced the same name, without asking anyone.
  • Change one character, h7 to h6, and commit. The blob’s name changes, so the tree that lists it changes, so the commit that names the tree changes. The untouched file keeps its blob. The new commit carries its parent’s name inside its own text.
✓Same structure: drawing revision control

A drawing office never stores a revision as a list of changes. Revision C of a drawing is a complete drawing, and its revision block records what changed and why. A commit is the same: a complete snapshot, plus a message. The parent link is the revision history, and a branch (§08) is the note saying which revision is current.

The new thing is the name. A drawing number is issued; a commit name is computed. The consequence follows from Fig. 15.1: a commit’s name covers its tree, its tree covers every file, and its text covers its parent’s name, which covers its parent. Change any byte anywhere in the past and every name after it changes. A commit name therefore certifies the entire history behind it, which no drawing number does.

The source says that git “internally stores diffs for efficiency”. Measured, that is wrong in the way it is usually meant ([Ch15 s04]). A 1,000-line, 41,670-byte file was committed, one line changed, and committed again. Both revisions sat in .git/objects whole: each decompresses to 41,681 bytes, the file plus the 11-byte header blob 41670\0. Only when git later packs its objects (git gc) does it compress similar objects against each other, and then it kept the newer revision whole and stored the older one as a 17-byte delta against it. That is the opposite of a change list, and sensible: the newest revision is the one read most. A delta here is a sequence of copy and insert instructions on bytes, chosen between any similar objects, not a line-by-line diff between a commit and its parent. The diff you read in a review is computed when you ask for it, which is §06.

What a content name guarantees, and what a drawing number does

beyond the source

A drawing number and a commit name answer different questions, and the difference is worth stating precisely.

Two ways to name a revision.

Two identical drawingsCan carry different numbersAlways the same name
Two different drawingsNever the same number (by construction)The same name only by an accident whose odds are computed below
OrderB comes after ANone in the name; order lives in the parent links
Silent edit after releasePossible: the number does not changeImpossible: the name changes

So a hash gives up the one thing a registry guarantees, uniqueness for certain, and gets back something no registry can give: two people working offline, on different continents, name the same content identically, and nobody can alter content without changing its name. How much uniqueness is given up is a calculation. If \(n\) objects get independent random names of \(b\) bits, the chance that no two share a name is a product, and its approximation is the birthday bound:

$$\begin{aligned}P(\text{some two share a name}) &= 1-\prod_{i=1}^{n-1}\Big(1-\frac{i}{2^b}\Big)\\ &\approx 1-e^{-n^2/2^{b+1}}\end{aligned}$$

The chance reaches one half at \(n \approx 1.1774\cdot 2^{b/2}\): the square root of the number of names, not the number of names. For git’s full 160-bit SHA-1 names that is \(1.42\times10^{24}\) objects, and among a billion objects the chance of any accidental collision is about \(3.4\times10^{-31}\) ([Ch15 s05]). The seven-digit short names git prints are another matter. Seven hex digits are 28 bits, and the chance that some two objects in a repository share a seven-digit prefix reaches one half at 19,291 objects. Git lengthens its abbreviations as a repository grows (reported), and always stores the full name. A short hash in a log or an ECN is a convenience, not an identity.

!Where it breaks: accidents against adversaries

The birthday bound is about accidents: names that behave like random draws. It says nothing about someone who sets out to build two different files with the same name. For SHA-1 that has been done deliberately, in a public demonstration in 2017 (reported), and git has since added collision detection and a SHA-256 object format (reported). A content hash is an excellent check against mistakes and a weaker one against malice, which is a different property from a drawing number’s, not a better or worse one. Git LFS (§09) already names large files by SHA-256.

06

A diff is a longest common subsequence

src 02. git ↗

git diff shows what changed between two revisions as lines removed (-) and lines added (+). Sheet 14 part 2 §18 said this is the longest common subsequence (LCS) problem and marked it as reported. Here is why it is exact.

Call the old file \(N\) lines and the new one \(M\) lines. A diff is a way to turn one into the other by deleting some old lines and inserting some new ones. The lines it does not touch appear in both files, in the same order, so they form a common subsequence. A diff that keeps \(K\) lines makes \(N-K\) deletions and \(M-K\) insertions. The fewest edits therefore keep the most lines, and the most lines that can be kept is the LCS length \(L\):

$$D_{\min} = N + M - 2L$$
$$L_{i,j} = \begin{cases} L_{i-1,j-1}+1 & a_i = b_j\\ \max\big(L_{i-1,j},\,L_{i,j-1}\big) & \text{otherwise}\end{cases}$$

The second line is Sheet 14’s recurrence for the table. So the claim to test is not “tools use LCS” but something sharper: no correct diff can report fewer than \(N+M-2L\) changed lines, and a tool that reaches that number has found an LCS. The verification script generated 300 random pairs of files and ran six real tools on each ([Ch15 s06]):

The likely cause is a pass that sets very frequent lines aside before the search for matches begins; that is inferred from this measurement, not traced in git’s source. Either way the diff is still correct, since applying it gives the new file exactly. It is just not the shortest.

✓Identity, with an honest qualifier

Comparing two revisions of a drawing’s notes by hand, you find the longest run of notes that survive in order and mark the rest as deleted or added. That is the LCS, and the minimum diff is exactly \(N+M-2L\). What real tools do is aim at that minimum. Plain Myers-style search hit it on every random pair and missed it by six blank lines on one real file. Patience and histogram diffs anchor on lines that occur once in each file, which tends to give diffs that are easier to read, and on random files they pay for that with longer edit scripts. The exact table costs \(N\times M\) cells, 837,120 for the third pair; Myers’ method costs about \((N+M)\,D\), small when the revisions are close (reported). So the LCS is the specification, and the tools are fast approximations to it.

And a line diff is meaningless on a file that is not lines of text: two revisions of a CAD part file differ in bytes scattered through a binary format, and only a geometric comparison says what moved.

07

Three-way merge, and why a vault locks drawings

src 02. git ↗

Two engineers edit the same file at the same time. A drawing vault prevents this: one engineer checks the drawing out, everyone else can only read it until it is checked back in. That is a lock, the mutex of Sheet 13 part 2 §12, and it rules out the lost update by making everyone else wait. Git takes the opposite policy. Anyone edits anything, and the edits are combined afterwards by a three-way merge: git finds the last commit both sides share, the base, and compares each side to it.

  • A region neither side changed is kept.
  • A region one side changed takes that side’s version.
  • A region both sides changed is taken if the two changes are identical, and is a conflict otherwise, left in the file between markers for a person to decide.

The source says a conflict happens “when two branches modify the same line”. Five cases on an eight-line file, merged by real git, show the rule is a little wider ([Ch15 s07]):

What git did with two branches edited from the same base.
Edits on the two sidesResult
Line 2 on one side, line 6 on the otherclean
Line 3 on both sides, to different valuesconflict
Line 3 on both sides, to the same valueclean
Line 3 on one side, line 4 on the other (adjacent)conflict
Line 3 on one side, line 5 on the other (one line between)clean

Adjacent edits conflict because there is no unchanged line between them to show where one change ends and the other begins; one untouched line is enough. The markers need care too. The source says the block under <<<<<<< HEAD is “the current branch’s version”. HEAD is wherever you are standing. In a merge into main you stand on main, so HEAD is main. In a rebase of your branch onto main (§08), git stands on main and replays your commits one by one, so HEAD is main again and your line is the one under =======. Measured on a config file with learning_rate = 0.0005 on your branch and 0.002 on main: during the rebase the HEAD block held 0.002 ([Ch15 s07]). Read the commit names in the markers, not the word HEAD.

✓Two policies for one problem

A lock pays in waiting: Sheet 13 part 2 §16 showed contention capping a whole system. A merge pays in conflicts, only when edits overlap. Which costs less depends on how often two people touch the same region. Source code is many small regions, so overlaps are rare and the merge wins. A CAD model saved as one binary file is a single region, so every concurrent edit overlaps, and that is why engineering vaults lock and why Git LFS added file locking for such files (reported). The vault is not old-fashioned; it is the right policy for its file type.

!Where it breaks: clean is not correct

A merge with no conflict is only a merge with no textual overlap. If one branch renames a function and the other adds a new call to the old name, the edits touch different lines, git merges them silently, and the result does not run. Two drawing changes can each be right and still not fit together; checking the assembly is a separate step. In software that step is the automated test run after every merge, §18.

08

Branches, rebase, and bisect

src 02. git ↗

A branch is a pointer to a commit, as the source says, and the pointer is literal: a 41-byte file holding one commit name and a newline ([Ch15 s08]). Creating a branch writes 41 bytes, which is why the source can say “branch always”. When you commit on a branch, git moves the pointer to the new commit.

There are two ways to bring a branch up to date with main. A merge adds a commit with two parents. A rebase replays each of your commits on top of main’s latest commit. A replayed commit has a different parent, so by §04 it has a different name: in the check, all three replayed commits got new names and none was kept, while the changes they carry were identical, as compared by git patch-id, which hashes the change itself ([Ch15 s08]). The source’s rule “never rebase commits that have been pushed and shared” follows directly. Colleagues hold the old names; after the rebase those names belong to a history that is no longer on the branch. It is re-issuing released drawings under new numbers while the shop floor still works from the old ones.

git bisect finds the commit that introduced a fault. You mark one commit good and one bad; git checks out the commit halfway between, you test it, and git keeps the half that must contain the change. It is bisection, the method of Sheet 13 part 1 §06 and Sheet 14 part 2 §15, run on history. A repository of 300 commits with a fault introduced at commit 187 was bisected with an automatic test: git named commit 187 after 8 builds, against \(\log_2 299 = 8.22\) ([Ch15 s08]).

!Where it breaks

Bisection needs a single change of sign between the two ends. Bisect needs the same: every commit after the culprit must test bad and every one before it good. A fault that comes and goes, or a test that fails at random, breaks the assumption, and bisect then names a wrong commit with full confidence; §24 computes how often. The source says atomic commits make bisect possible. Bisect works on any history; small commits make its answer useful, because the culprit it names is then small enough to read.

09

The ECN, the ignore list, and the hash in the log

src 02. git ↗

A commit message has the job of the reason-for-change field on an ECN. The diff already records what changed, computed (§06); only a person can record why. The source’s conventions, a summary of 50 characters or fewer in the imperative mood and a body wrapped at 72, are conventions, and good ones. A pull request is the change review: a proposed set of commits, a description, reviewers who must approve before it merges. Keeping it small is the same advice as keeping an ECN to one change.

Three of the source’s practical warnings, each checked ([Ch15 s09]):

  • Ignoring a file after committing it does nothing to the past. A .env file holding KEY=abc123 was committed, then added to .gitignore. Git went on tracking it (git status showed it modified). After git rm --cached .env it was untracked, and git show HEAD~1:.env still printed KEY=abc123. A committed secret has to be treated as published and changed at its source. Rewriting history removes it but renames every later commit (§08).
  • Large files are stored by name. A Git LFS pointer, the small file committed in place of a large one, is 129 bytes naming the real file by the SHA-256 of its content and its size. Content addressing again, with a longer hash.
  • The source’s way of logging the commit is broken twice. subprocess.check_output(['git', 'rev-parse', 'HEAD']).strip() returns bytes, so a log line built from it reads commit b'8539e9…'; add .decode() or pass text=True. More seriously, HEAD names the last commit. Edit a file without committing and HEAD’s name does not change, so the logged hash no longer names the code that ran. Record git status --porcelain as well, or refuse to train from a modified tree.
✓Same structure: red-line mark-ups

Recording only the commit hash is recording the drawing number while the shop works from a copy with red-line mark-ups on it. The number is correct and the part made is not the part on the drawing. The fix is the same in both trades: either fold the mark-ups into a released revision before making the part, or record the mark-ups with the part.

10

Names, registries and interfaces

src 03. codebase design ↗

File 03 is about arranging code so that a change stays cheap as the project grows. Its project layout keeps importable code under src/my_project/, entry-point scripts under scripts/, tests under tests/ and settings under configs/. The reason it gives for the src/ folder is checkable: from the project root, with nothing installed, a flat layout imports the package and a src/ layout refuses ([Ch15 s10]). That refusal is the point. With a flat layout, Python quietly imports whatever folder sits in the current directory, so tests pass against your working copy even if the installed package is broken. The src/ layout forces you to install the package and test what you would ship, the way a first-article inspection takes a part off the production line rather than the prototype off the bench.

The source says naming is the single most useful habit, and shows a badly named update loop beside a well-named one. The advice is right. The well-named code does nothing:

  • With a weight stored as a Python number, {"w": 1.0}, and a gradient of 0.5, one step at learning rate 0.1 leaves the weight at 1.0. With the weight stored as a NumPy array it becomes 0.95 ([Ch15 s10]).
  • The reason: for name, param in parameters.items(): param -= … computes a new number and points the loop’s local name param at it. The dictionary still holds the old number. An array is changed in place by -=, so the dictionary sees the change. The badly named version has the same bug, and both read a global gradients they were never given.

It is a bug of exactly the kind file 04 says ML code hides: nothing crashes, the model quietly fails to learn. A test that checked the weight moved would have caught it, which is §15’s subject.

The design patterns the source lists are lookup tables and connections. A registry maps a name in the configuration file to the code that builds it: MODEL_REGISTRY["transformer"] returns the transformer class, and adding a model adds one line. That is a part catalogue: the order names a part number, the catalogue returns the part, and a number not in the catalogue is refused at once (here, with a KeyError). A callback is code the training loop calls at fixed events; the source’s early-stopping callback is correct, stopping five epochs after the best loss ([Ch15 s10]).

✓Same structure: an interface control drawing

Dependency injection means a component is handed the things it uses instead of building them itself: Trainer(logger) rather than a trainer that creates its own W&B logger inside. An interface control drawing specifies only the mating features of a part, so any supplier’s part that meets them will fit. A trainer that accepts any object with a log method can be tested with a fake one, which is a dummy part made to the interface drawing so the assembly can be checked without the real supplier.

The rest of the section (short functions, single responsibility, “extract it on the third copy, not the first”, named constants instead of bare numbers) is sound practice and judgment rather than anything computable. A named constant is the software form of a general note on a drawing, ALL FILLETS R2 UNLESS STATED: one place to read the value and one place to change it.

11

Configuration is a tabulated drawing

src 03. codebase design ↗

Hyperparameters, paths and model settings go in a configuration file rather than in the code, usually YAML: indented key: value lines. The source’s best practice is a base file holding every default plus one small file per experiment that overrides only what changes.

✓Same structure: a tabulated drawing

A tabulated drawing defines a family of parts once and lists, for each dash number, only the dimensions that differ. A base config with per-experiment overrides is the same document. The source’s rule “track every experiment’s config alongside its results” is marking the dash number on the part.

The source’s example YAML contains a bug that will not announce itself. Loaded with PyYAML, the most common Python reader, learning_rate: 3e-4 becomes the text '3e-4', not a number ([Ch15 s11]). PyYAML follows version 1.1 of the YAML rules, under which a number in exponent form must contain a decimal point and a signed exponent:

What PyYAML 6.0.1 makes of six ways to write a small number.
Written3e-41e-31.0e33.0e-42.1e-41.0e+3
Loaded astexttexttextnumbernumbernumber

What happens next depends on luck. 0.5 * lr raises a TypeError, which is the good outcome. lr * num_gpus with two GPUs silently gives the text '3e-43e-4', because multiplying text by a whole number repeats it. The same reader turns the key on in the source’s CI file (§18) into the value True, since the old rules read on/off and yes/no as true and false ([Ch15 s11]). GitHub reads its own workflow files with a parser that does not do this (reported), which is why the file works there. The remedies are to write 3.0e-4, or better, to check types when the file is loaded, which the Pydantic models of file 03’s API section do.

One more mismatch, found by reading rather than running: the source’s Hydra example overrides training.lr=1e-3, but its YAML calls the key learning_rate. An override must name a key that exists; Hydra refuses an unknown key unless it is marked as an addition (reported).

!Where the analogy breaks

A tabulated drawing is read by people who share the conventions of the drawing office; 3e-4 is a number to every one of them. A configuration file is read by a parser whose rules you did not write and may not know. The checker of a tabulated drawing would never think to ask whether a dimension will be read as a dimension; the checker of a config file has to.

12

Logging that actually logs

src 03. codebase design ↗

A log is the running record a program keeps of what it did. Python’s logging module gives each message a level (DEBUG, INFO, WARNING, ERROR, CRITICAL) so that routine messages can be filtered out in production, and sends messages to handlers that write them somewhere. The source’s reasons for preferring it to print are right. Its example, run exactly as printed, produces two lines ([Ch15 s12]):

The source’s logging example, run as printed.
CallPrinted
logger.info("Epoch %d: loss=%.4f, lr=%.6f", …)nothing
logger.warning("GPU memory >90%%, …")GPU memory >90%%, consider reducing batch size
logger.error("Failed to load checkpoint: %s", path)Failed to load checkpoint: ck.pt
logger.info("training_step", extra={"epoch": 5, …})nothing
  • The INFO lines vanish. setLevel(INFO) lets INFO messages through the logger, but no handler was ever attached, so Python falls back to a last-resort handler that prints WARNING and above only. The “normal operation” message, the one you most want in a training log, is the one that disappears.
  • The doubled percent sign stays doubled. %% becomes % only when the message is formatted, and it is formatted only when arguments are passed. This call passes none.
  • The structured fields never appear. extra= attaches the values to the log record, but nothing prints them unless the output format names them. Even with logging.basicConfig(level=logging.INFO), which brings the INFO lines back, the line reads training_step and nothing else. Machine-readable JSON needs a formatter that writes it.
✓Same structure: a data-acquisition channel

A test rig’s acquisition system has channels with thresholds and recorders assigned to them. Setting a channel’s threshold does nothing if no recorder is assigned; the signal passes the threshold and goes nowhere. The source’s logger is that channel. The fix is one line at program start, logging.basicConfig(level=logging.INFO, format=…), which assigns the recorder, and a check on the first run that the log file actually contains an INFO line.

The API material that follows in file 03 (REST endpoints, FastAPI, gRPC) is where a trained model becomes a service. Serving is Sheet 17’s subject; the source’s FastAPI example is a fair minimal sketch and is not repeated here. Its claim that gRPC is faster than REST for service-to-service calls is reported, not measured.

13

Packaging, pinning, and interchangeability

src 03. codebase design ↗

A package is code made installable, so that other code imports it by name. Its description lives in pyproject.toml: name, version, dependencies, and a [build-system] table naming the build backend, the program pip calls to turn the source into an installable file. The source names setuptools.backends._legacy:_Backend. In setuptools 68.1.2 that module does not exist; pip, given the source’s file, stops with BackendUnavailable (exit status 2). The standard backend, setuptools.build_meta, loads in the same project and answers pip’s first request ([Ch15 s13]). Copy the source’s file and nothing installs.

A dependency is declared with a version rule, and the rules mean different things ([Ch15 s13], checked with Python’s own packaging library): torch>=2.0 accepts 3.0; torch~=2.2 accepts 2.9 but not 3.0; torch==2.2.1 accepts 2.2.1 and nothing else.

✓Same structure: form, fit and function

A drawing office keeps a part’s number through a change that preserves form, fit and function, and only raises its revision; a change that breaks interchangeability gets a new part number. Semantic versioning, a convention most Python packages follow (reported), says the same with three numbers: MAJOR.MINOR.PATCH, where a new MAJOR number announces that something no longer fits.

Read the rules that way. >=2.0 is “revision 2 or any later one, including one that no longer fits”. ~=2.2 is “any later revision of the same part number”. ==2.2.1 is “this revision only”. The file pip freeze writes, every package at one exact version, is the as-built record of an environment.

!Where the analogy breaks

A change board enforces form-fit-function. Semantic versioning is a promise each package’s authors make about their own releases, and the source itself warns that a minor version can change numerical results. So the two jobs separate. A library declares a range, saying what it is compatible with; an experiment or a deployment pins exact versions, saying what it was built with. The source’s advice to pin is right for the second job and wrong for the first: a library that pins exactly cannot be installed beside any other library that pins differently.

14

Coding agents: drawn, checked, approved

src 03. codebase design ↗

File 03 closes with advice on AI coding agents: use them for boilerplate, tests, mechanical refactoring and first drafts; do not hand them architecture, security or code you cannot explain; read every line; let tests, type checks and linters catch what review misses. This is judgment, not something a calculation can confirm, and it is marked here as the source’s opinion. It is sensible. Its one piece of arithmetic is illustrative: 10 minutes generating plus 120 minutes debugging is 130 minutes, 4.3 times the 30 minutes of writing it by hand ([Ch15 s14]).

✓Same roles: the title block

A drawing’s title block has three signatures: drawn, checked, approved. The draftsman can be fast and junior; the checker answers for the drawing being right; the approver answers for it being the right drawing. The source’s mental model, “you are the senior engineer, the agent is the junior”, puts the agent in the first box and you in the other two. Nobody signs as checker for a drawing they have not read.

!Where it breaks

A junior draftsman’s mistakes tend to be consistent and explainable: the same misread convention, every time. An agent can produce fluent text that cites a function or an option that does not exist, which the source calls a hallucinated API, and nothing in the prose looks different. The source also says code that passes your tests is more likely correct. That holds only if the tests can fail, and §15 shows a test from this very chapter that cannot. This sheet was itself drafted by an AI agent; every number on it was then recomputed by running code, which is the source’s advice taken literally.
