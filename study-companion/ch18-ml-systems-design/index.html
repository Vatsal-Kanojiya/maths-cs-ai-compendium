The Plant Behind the Model

Every replica count in the source’s design examples is the load at which the queue never empties. Little’s law gives the mean; your inventory training gives the margin. Requests in service are Poisson, so spare capacity is safety stock, and it grows only as the square root of the load.

Sheet 17 built one inference server and found that its batch is set by Little’s law (Sheet 17 §14). This sheet starts where that one stops: many servers, daily peaks, failures, spare capacity, the network between machines, and the training cluster, which is the largest series system most engineers will ever meet. The source’s five files cover systems design fundamentals, cloud computing, large-scale infrastructure, ML systems design and seven worked designs. Read as a plant engineer reads a plant, they turn out to be capacity planning, reliability engineering and quality control, and most of their numbers can be checked by hand. They are, in §20.

The headline is §03. The number of requests being served at once is a Poisson count whatever the service-time distribution, so the servers you need are the mean plus \(z\) standard deviations of that count: \(c = a + z\sqrt{a}\), which is the reorder point of a Poisson-demand item. It explains why the source’s 50 replicas never catch up (§02), why a large plant can run hotter than a small one at the same delay, and how many of Sheet 17’s servers a growing help desk really needs (§21). Two other results carry the rest of the sheet. Redundancy is a reliability block diagram until a bad deploy makes every replica fail at once, and the β-factor model of common-cause failure puts a floor under it (§09). And a request that fans out to a hundred shards waits for the slowest one, which is PERT’s merge bias again (§12).

01

A server is a machine, and Little’s law sizes the shop

src 01. systems design fundamentals ↗

File 01 opens with the client–server pattern: a client sends a request, a server does the work and replies. A stateless server keeps nothing between requests, so any server can take any request, and adding capacity means adding identical servers behind a load balancer. A stateful server remembers a user’s session, so that user’s requests must go back to the same machine. In shop-floor terms a stateless pool is a group of identical machines that can each do any job, and session affinity ties a job to one machine. §04 shows what that tie costs.

The first sizing question for any such pool is how many machines are busy on average, and Sheet 13 part 2 §06 already gave the answer. Little’s law says the average number in a system equals the arrival rate times the average time each item spends there:

$$L = \lambda W$$

Apply it to the time a request spends being served, and \(L\) is the average number of requests in service at once. A replica that serves one request at a time is busy exactly when it holds one, so \(L\) is also the number of replicas that would be busy all the time. Queueing theory calls \(a = \lambda s\) the offered load, measured in erlangs. Every sizing in the source’s worked designs is this product ([Ch18 s01]):

Little’s law assumes nothing about distributions or scheduling, so a simulation of 50 servers with Poisson arrivals and fixed service times confirms it to the third figure: the time-average number in the system is 40.27 and \(\lambda W\) is 40.28 ([Ch18 s01]).

✓Identity: work in progress equals throughput times lead time

A shop that starts 12 jobs an hour, each spending 5 hours on the floor, carries 60 jobs of WIP. A plant that receives 12,000 posts a second, each spending 5 ms in a text classifier, keeps 60 classifiers busy. Sheet 17 §14 used the same law on one server and found its batch size; here it sizes every station in a plant. The law holds for averages, and it is silent about two things a plant engineer always asks next: how much the count varies, and how long items wait. Those are the next two sections.

02

Sized to the cliff

src 05. ML design examples ↗

The offered load is the number of servers that would be busy all the time. Provide exactly that many and utilisation \(\rho = a/c\) is 1. Sheet 13 part 2 §06 showed what happens to one server as \(\rho\) approaches 1: the queue grows as \(\rho/(1-\rho)\), without limit. A pool of \(c\) servers fed by one queue, with Poisson arrivals and exponential service times, is the M/M/\(c\) queue. The probability that an arriving request finds every server busy is the Erlang C formula, and the mean wait follows from it:

$$P_{\text{wait}} = C(c,a) = \frac{\dfrac{a^c}{c!}\,\dfrac{c}{c-a}}{\displaystyle\sum_{k=0}^{c-1}\frac{a^k}{k!} + \frac{a^c}{c!}\,\frac{c}{c-a}}, \qquad W_q = \frac{C(c,a)\;s}{c-a}$$

For the source’s user-embedding service, \(\lambda\) = 10,000 per second and \(s\) = 5 ms, so \(a = 50\) ([Ch18 s02]):

!The source computed the first number and stopped

“At 10K QPS, need ~50 model replicas to handle the load” is the offered load, which is the right place to start, and it is the load at which a queue never empties. The same is true of every count in the table in §01: the 20 ANN replicas (each “handles ~500 QPS”, which is one search at a time at 2 ms, busy 100% of the time) and the 60, 240 and 12 moderation servers. The moderation section adds “plus redundancy”, which points the right way. No plant engineer loads a line to 100% of its rated capacity, for the reason in Sheet 13 part 2 §06. §03 says how much to add.

!1,000 GPU-seconds per second is 1,000 GPUs

The ranking stage scores 1,000 candidates at about 0.1 ms each, 100 ms a request. The source writes “At 10K QPS, need 1000 GPU-seconds per second → ~10 A10G GPUs for ranking alone”. A GPU-second per second is one GPU kept busy, so the sentence’s own arithmetic says 1,000 GPUs. Ten GPUs can do it only if each one holds 100 requests (100,000 candidates) in flight at once, which by Little’s law is what “100 ms per request on 10 GPUs at 10,000 a second” requires. That is batching, which Sheet 17 §14 shows a GPU does well; the 0.1 ms per candidate must then be time per candidate at that batch, not time for one candidate alone. At the source’s own $1.00 an hour for an A10G, the difference is $7,300 a month against $730,000 ([Ch18 s02]).

03

Spare capacity is safety stock

beyond the chapter

How many to add? Start from a fact that needs no queueing theory. Let requests arrive as a Poisson stream at rate \(\lambda\), give each an independent service time \(S\) from any distribution with mean \(s\), and pretend servers are unlimited. A request that arrived \(t\) seconds ago is still in service with probability \(P(S > t)\). Thinning a Poisson stream by a probability leaves a Poisson count, so the number in service now is Poisson with mean

$$\lambda\int_0^\infty P(S>t)\,dt \;=\; \lambda s \;=\; a$$

whatever the shape of the service-time distribution. A simulation with fixed service times gives a mean of 50.20 and a variance of 48.38; one with log-normal service times gives 50.11 and 52.07 ([Ch18 s03]). Both are Poisson with mean 50, whose variance equals its mean. So the count of requests wanting service has a standard deviation of \(\sqrt a\), and a pool sized at the mean plus \(z\) standard deviations is

$$c = a + z\sqrt{a}$$
✓Identity: the reorder point of a Poisson-demand item

An item reordered at a fixed lead time is reordered at the mean lead-time demand plus safety stock, \(\text{ROP} = \mu + z\sigma\). For Poisson demand \(\sigma = \sqrt\mu\), so \(\text{ROP} = \mu + z\sqrt\mu\): for \(\mu = 50\) and a 95% service level (\(z = 1.645\)) it is 61.6, and the exact Poisson chance of demand above 62 is 4.2% ([Ch18 s03]). Replace stock on hand with servers on hand and lead-time demand with requests in service, and the formula does not change.

The service level you learned to choose is the same choice here. Halfin and Whitt showed (reported) that if \(c = a + \beta\sqrt a\), the chance a request waits settles to a fixed value as the plant grows, about 0.223 at \(\beta = 1\). Computed with Erlang C ([Ch18 s03]):

The margin grows as \(\sqrt a\) while the load grows as \(a\), so the fraction held in reserve falls as \(1/\sqrt a\). A cell of five machines at the same delay must run at 62%; a fleet of five thousand can run at 99%. That is why a fixed utilisation target is the wrong rule for both: 85% wastes capacity in a large plant and starves a small one. Risk pooling in inventory is the same fact seen from the stores: consolidating \(n\) warehouses cuts total safety stock from \(nz\sigma\) to \(z\sigma\sqrt n\).

Sheet 17’s server, with the spread put back

Sheet 17 §14 found that a continuous-batching server settles at the batch \(b = \Lambda t_w/(1-\rho)\), its minimum lot, and that each output token then takes \(t_w/(1-\rho)\). That batch is a count of requests in service, so it fluctuates. Its average follows Little’s law (simulated 56.7 against 56.3 at 1,800 tokens/s), but its spread is wider than Poisson, because a large batch makes every step slower, which keeps everyone in the batch longer. Measured, the variance-to-mean ratio tracks the same factor Sheet 17 found in the time per token ([Ch18 s03]):

It matters because Sheet 17’s server has a hard memory cap of 100 sequences, and its nameplate capacity of 2,500 tokens/s is the demand that puts the average batch at that cap. Simulated without the cap, the batch would exceed 100 sequences on 0.5% of steps at 2,000 tokens/s, 0.9% at 2,100, 3.6% at 2,200, 10% at 2,300 and 26% at 2,400. The cap is a reorder point, and the safety-stock rule with the measured spread, \(\bar b + 2.33\sqrt{\bar b/(1-\rho)} \le 100\), gives a planning capacity of 2,121 tokens/s per server, which the simulation brackets ([Ch18 s03]). §21 plans a fleet with it.

!Where it breaks

The Poisson count needs Poisson arrivals. Real traffic is burstier: retries after an outage, a link shared at once, a batch job hitting an online service. Its variance exceeds its mean, and \(\sqrt a\) understates the margin. Lumpy demand does the same to safety stock, and the fix is the same: use the measured standard deviation, not the Poisson one.

A server is also not a unit of stock. An idle server costs its full hourly rate, and a new one takes minutes to start and load its weights, which the source puts at about 2.3 minutes for 140 GB at 1 GB/s (§14). That start-up time is the replenishment lead time, and it is why the margin must cover the demand that can arrive while a replacement is starting.

One queue or many

src 01. systems design fundamentals ↗

A load balancer decides which server gets each request. If it picks at random, or by a hash of the user, each server receives its own Poisson stream and has its own queue: \(c\) separate M/M/1 queues. If idle servers take the next request from one shared line, the pool is a single M/M/\(c\) queue. Same servers, same load, very different waits ([Ch18 s04]):

The source lists four balancing rules. Simulated on 10 servers at 80% utilisation, the mean waits are 4.15 service times for random choice, 1.98 for round robin, 0.39 for least connections and 0.23 for one shared queue ([Ch18 s04]). Round robin halves the random wait because it spaces arrivals evenly at each server. Least connections, which sends each request to the server holding the fewest, recovers most of the pool, and it is the rule the source recommends when request lengths vary.

✓Identity: a common queue in front of identical machines

A group of identical machines fed from one queue keeps every machine working while any job waits. Assign jobs to machines on arrival and one machine can sit idle while another has a backlog. The numbers above are Erlang C against M/M/1, and the shop version is the same pair of formulas. The gap widens with the number of machines for the reason in §03: one pool needs a margin of \(\sqrt a\), while \(c\) separate machines each need their own.

!Where it breaks: some requests can only go to one machine

Pooling assumes any server can take any request. That holds for stateless replicas that load the same weights. It fails once a server holds something the request needs: a user’s session, a shard of the data, or a cached prompt prefix (Sheet 17 §16). The source recommends consistent hashing (§05) for exactly those cases, and that is a deliberate choice of dedicated machines. The cache hits it buys must pay for the pooling it gives up.

05

The ring, and a tolerance stack in it

src 01. systems design fundamentals ↗

To spread keys (users, cached items, database rows) over \(n\) machines, the simplest rule is shard = hash(key) % n. Its weakness appears when a machine is added: a key stays put only if its hash leaves the same remainder for \(n\) and \(n+1\), which happens for about one key in \(n+1\). So adding a fourth machine to three moves 75% of the keys, and adding the hundred-and-first moves 99% (measured 0.752, 0.909 and 0.990 for \(n\) = 3, 10, 100, [Ch18 s05]). For a cache that is a near-total flush.

Consistent hashing puts the machines at points on a circle and sends each key to the first machine clockwise from the key’s own point. A new machine takes over only the arc just before it, so the keys that move are the ones that now belong to it: on average \(1/(n+1)\) of them, and none move between old machines. Measured on one ring of ten machines, adding an eleventh moved 9.8% of keys against 9.1% predicted, all of them to the newcomer ([Ch18 s05]). This is the source’s “only ~1/n of keys need to move”, and it holds.

Balance is the cost. With one point per machine, the arcs are the gaps between \(n\) random points, and the longest gap is on average \(H_n = 1 + \tfrac12 + \dots + \tfrac1n\) times the fair share: 2.93 for ten machines, measured 2.91. One machine carries three times its share. The fix is virtual nodes: give each machine \(v\) points, so its share is the sum of \(v\) arcs. The spread of that sum is exactly computable, and it matched 400 random rings at every \(v\) tried ([Ch18 s05]):

$$\frac{\sigma_{\text{share}}}{\text{fair share}} = \sqrt{\frac{n-1}{nv+1}} \;\approx\; \frac{1}{\sqrt v}$$
✓Identity: a tolerance stack of \(v\) parts

Sheet 04 §05 showed that \(v\) independent parts stacked end to end have a tolerance that grows as \(\sqrt v\) while the nominal length grows as \(v\), so the relative spread falls as \(1/\sqrt v\): the RSS stack. A machine’s share of the ring is \(v\) arcs stacked end to end. Each arc’s spread equals its own mean (a random gap is close to exponential), so the relative spread of the sum is \(1/\sqrt v\): 10% at 100 virtual nodes. The exact formula above has the factor \(\sqrt{(n-1)/n}\) because the arcs must add up to the whole circle, a constraint a free stack does not have. Sheet 07 §08’s mixture-of-experts load balancing is the same problem of the most loaded of \(n\) bins.

!Where it breaks: the ring balances keys, not load

Virtual nodes even out how many keys each machine owns. They do nothing for a key that is far busier than the rest: a celebrity’s profile, or one system prompt used by every request of a popular product. That key hashes to one point and lands on one machine whatever \(v\) is. Hot keys need copies on several machines, which is the replication of §06, not hashing.

06

Shards, replicas, and Amdahl’s law again

src 03. large scale infrastructure ↗

Sharding splits data across machines; replication copies it. File 01 gives two ways to shard. Hash sharding spreads keys evenly and makes range queries impossible; range sharding keeps ranges together and creates hot spots wherever keys cluster. Both are the storekeeper’s choice from Sheet 14 part 1 §13 between bins chosen by a scrambled part number and a ledger in part-number order.

Sheet 12 promised that partitioning a graph is a systems problem. Here is why. Shard the nodes of a graph by hash over \(n\) machines and an edge stays on one machine only if both its ends land there, which happens with probability \(1/n\). So hashing over 8 machines cuts 87.5% of edges (measured 87.6%, [Ch18 s06]), and every cut edge is a network hop each time a graph network passes a message along it. A partition that follows the graph, such as the Fiedler-vector split of Sheet 12 §08, cuts far fewer.

Read replicas

File 03 says read replicas scale read throughput “linearly with the number of replicas”, because most workloads are 95% reads. Count the work. Give \(N\) machines a capacity of \(C\) operations each, and let a fraction \(w\) of operations be writes. Reads are shared among the \(N\) machines, but every write must be applied on every copy, or the copies drift apart. A total throughput \(X\) is feasible when each machine’s load fits:

$$\frac{(1-w)X}{N} + wX \;\le\; C \quad\Longrightarrow\quad \frac{X}{C} \;\le\; \frac{N}{(1-w) + Nw} \;=\; \frac{1}{w + \dfrac{1-w}{N}}$$
✓Identity: the write share is Amdahl’s serial fraction

The right-hand side is Amdahl’s law from Sheet 13 part 2 §16 with serial fraction \(w\), to \(5\times10^{-14}\) over 600 cases ([Ch18 s06]). Writes are the station that cannot be split: every replica must do all of them. At 5% writes 10 replicas give 6.90×, 20 give 10.3×, and no number gives more than 20×. If replicas apply writes more cheaply than the primary does, the ceiling stays, because the primary takes every write and saturates at \(X = C/w\). For a fixed write rate, as opposed to a fixed mix, each replica does add the same read capacity, which is presumably what “linearly” meant; but traffic usually grows with its mix intact.

An index is an order quantity

File 03 says an IVF vector index searches in \(O(n/k)\) per query: split \(n\) vectors into \(k\) clusters and search only the nearest. Finding the nearest cluster costs \(k\) comparisons as well, so the cost is \(k + n/k\), lowest at \(k = \sqrt n\). For 100 million vectors that is 10,000 clusters and 20,000 distance computations against 100 million for a flat search, 5,000 times fewer ([Ch18 s06]). It is the shape of Sheet 13 part 2 §05’s order-quantity cost, a term rising with \(k\) against one falling with it, and it has the same flat bottom: twice or half the best \(k\) costs only 25% more.
