Part 1 built the machine and part 2 shared it out. This part closes the chapter with the layer you actually touch — the language — and then, in §§11–14, pulls all three parts together with a worked example, a question bank and a map.

The bridge that matters most here is the simplest. A type is a unit. When a compiler refuses to add an integer to a float, it is doing exactly what you do when you refuse to add a length to a time — and the discipline of dimensional homogeneity that you apply without thinking is, formally, static type checking. That single correspondence makes the whole of §02 free, and it explains why weak typing feels so wrong to an engineer: a language that silently turns "3" + 5 into "35" has done the thing you were taught never to do.

The second is §07. A just-in-time compiler notices that a piece of code keeps running, stops, and builds a fast version of it. That is a machinist realising on the fortieth part that a jig would pay, and the break-even arithmetic is identical — \(n = C/(s_{\text{slow}} - s_{\text{fast}})\), which comes out at 421 iterations on the figures in §07. A JIT compiles only hot code for exactly the reason you do not make a fixture for a one-off.

!The worked example broke the claim it was written for

§11 was drafted to show that fixing a bottleneck beats buying hardware. Computed, it says the opposite at the scale it starts from: at one GPU, fixing the data loader buys 1.18× while a second GPU buys 1.74×. The true result is more useful than the one intended — the bottleneck moves, the loader goes from 15% of the step at one GPU to 59% at eight, and the value of fixing it peaks at four. That is Goldratt’s fifth focusing step, which is the one nobody remembers. The superseded claim is named in the provenance appendix rather than deleted.

01

Paradigms, and what purity buys

src 05. programming languages ↗

A paradigm is a style of organising code. Imperative describes a sequence of commands that change state — a process sheet. Object-oriented bundles data with the operations on it and hides the internals — a subassembly with a defined interface and no access to its internals. Functional treats computation as evaluating mathematical functions, with immutable data and no side effects. Logic programming states what must be true and lets the runtime find it.

A pure function is a capable process

A pure function returns the same output for the same input, always, and changes nothing else. That is the definition of a repeatable process: no hidden state, no dependence on what ran before, no effect on anything downstream except its own output. And the payoff is the same in both fields — a process with no shared state can be run on two lines at once without interference, which is exactly why the source says pure functions "parallelise safely". Part 2 §12 showed what happens when that condition fails: shared mutable state is precisely what produces a race condition.

Most modern languages are multi-paradigm, and the source’s closing line on this is worth keeping: the paradigm is a tool, not a religion. The same is true of manufacturing philosophies, and for the same reason — each one optimises something real, and none of them optimises everything.

02

A type is a unit

src 05. programming languages ↗

A type classifies values and says which operations are legal on them. That is the whole idea, and you have been applying it since your first year.

When you check that an equation is dimensionally homogeneous — that you are not adding a length to a time, that both sides of an energy balance carry \(\mathrm{M\,L^2\,T^{-2}}\) — you are running a type checker. A dimension is a type. Multiplication combines them (force times length is work); addition demands they match. Implemented as a few lines of code and run under [Ch13 s02], a dimension checker accepts \(\text{force} \times \text{length} \to (1,2,-2)\) and refuses \(\text{force} + \text{length}\) with the message cannot add (1,1,−2) to (0,1,0).

Set that beside a compiler refusing x + y because x is an i32 and y is an f64. Same refusal, same justification, one step earlier in the process.

!Where it breaks — weak typing is silent unit coercion

JavaScript evaluates "3" + 5 to "35": it reinterpreted the number as text rather than refusing. That is the software version of reading a number off a gauge and using it without checking what the gauge was calibrated in. One pound-force-second is 4.448 newton-seconds ([Ch13 s02]), so a mislabelled impulse is not slightly wrong, it is wrong by a factor of four and a half — and nothing in the arithmetic complains.

The honest limit of the bridge: a type system checks the kind of a quantity, not its unit. Most languages will happily let you add a value in millimetres to a value in inches, because both are floats. Getting real unit safety requires deliberately encoding units in the type — which some libraries do, and which is exactly the discipline of carrying units through a calculation rather than stripping them at the start.

03

The bench and the stores

src 05. programming languages ↗

Every program keeps data in two places, and the difference is one of discipline rather than of hardware.

The stack holds local variables and call frames. Allocation is moving a pointer; release is automatic when the function returns. It is strictly last-in-first-out and fixed in size — typically a few megabytes. That is your bench: what you put down last you pick up first, it is instantly to hand because it is always in cache, and it is small.

The heap holds anything whose size or lifetime is not known in advance. Allocation means finding a free block; release must be arranged somehow. That is the stores: much larger, addressable in any order, slower to reach, and it requires bookkeeping.

The consequence worth keeping is that the stack cannot leak. Its discipline makes the error impossible: the frame goes when the function returns, whatever the programmer intended. Every memory bug in §04 is a heap bug. That is the same argument as point-of-use storage against a central store — the tool you never booked out is the tool you cannot fail to return.

04

Tally, stocktake, ownership

src 05. programming languages ↗

Three strategies for getting heap memory back, and all three are tool-control policies you have seen work and fail.

Manual: book it out, book it back

In C you call malloc and you call free. Maximum control, and three failure modes with exact shop-floor twins: use-after-free is picking up a tool someone has already returned to stores; double free is booking the same tool back twice and corrupting the register; a memory leak is never returning it at all, so the stores slowly empties and one day there is nothing left to issue.

Tracing collection: the stocktake

A tracing garbage collector periodically walks everything reachable from the live roots and frees the rest. That is a stocktake, and it has the property a stocktake has: the shop stops while it runs. The pause scales with how much is live, not with how much is garbage — at roughly 40 ns per object, \(10^5\) live objects is a 4 ms pause and \(10^7\) is 400 ms ([Ch13 s04]). Counting takes as long as you have stock, however little of it is obsolete.

Generational collectors exploit the observation that most objects die young, so they scan the young region often and the old region rarely. That is cycle-counting the fast-moving lines weekly and the slow-moving ones annually, for exactly the same reason.

Reference counting: the tally, and its blind spot

Count the references to each object; free it the moment the count hits zero. No pauses, immediate release. And one failure that no amount of care prevents:

!Where it breaks — a tally cannot see a cycle

Let A hold a reference to B and B hold one to A, with the program holding A. Drop the program’s reference and the counts become \(A = 1\), \(B = 1\) ([Ch13 s04]). Neither reaches zero, so neither is freed — yet nothing reachable points at either. They are unreachable and immortal.

The shop version: two jobs each sign out a tool "for" the other. Both tallies read one, both jobs are long finished, and the tools never come back. No tally can detect this, because locally everything is correct. Only a stocktake can — which is why Python, whose primary mechanism is reference counting, also ships a cycle detector that is, precisely, a small tracing collector.

Ownership: enforce it at planning time

Rust takes a third route. Each value has exactly one owner, and when the owner goes out of scope the value is released. Values may be borrowed, under one rule:

That rule is part 2’s read-write lock, moved to compile time

Either one mutable reference, or any number of immutable references, never both. Part 2 §13 described exactly this as a read-write lock: many people may consult the drawing, one may revise it, and nobody consults it while it is being revised. The difference is when the rule is enforced. A lock checks at runtime and costs time; Rust’s borrow checker proves it at compile time and costs nothing at all — the program either satisfies the rule or does not build. That is inspection moved upstream into design, which is the oldest quality argument there is.

Compilation is process planning

src 05. programming languages ↗

A compiler turns source text into machine code in stages. Set them beside the stages of turning a drawing into a machined part and they line up one for one.

Two pipelines that are the same pipeline.

LLVM is STEP

LLVM defines one intermediate representation that many languages compile to, and many processors generate machine code from. Write a new language and you get every processor free; write a new processor backend and you get every language free. Without it, \(m\) languages and \(n\) targets would need \(m \times n\) compilers; with it, \(m + n\) pieces.

That is exactly why STEP and IGES exist. Every CAD package exports to the neutral format and every CAM package imports from it, so the industry maintains \(m + n\) translators rather than \(m \times n\). Same architecture, same arithmetic, same motivation — and the same weakness, which is that the neutral format has to be expressive enough for everyone and inevitably loses something at each boundary.

06

Optimisation passes are process improvement

src 05. programming languages ↗

The optimiser rewrites the program to run faster without changing what it does. The four the source names are four moves you would make on a route sheet.

  • Constant folding — compute \(3+5\) at compile time and write \(8\). That is pre-calculating a dimension on the drawing rather than leaving the operator to work it out at the machine.
  • Dead code elimination — remove what can never run. That is deleting a non-value-adding operation from the route.
  • Inlining — replace a call with the body of the function, removing the call overhead. That is combining two operations into one setup to avoid a changeover, and it carries the same cost: the route sheet gets longer, and if you inline everything the program no longer fits in cache — the exact analogue of a setup so large it will not fit on the machine.
  • Loop unrolling — do several iterations per pass to amortise the per-iteration overhead. That is batching, and it has the batching trade-off from part 2 §05: bigger batches amortise the fixed cost and cost you elsewhere.

The pattern across all four is the one you know: move work earlier, remove work that adds nothing, and amortise fixed costs over more units. A compiler engineer and an industrial engineer have the same toolbox.

07

The JIT break-even

src 05. programming languages ↗

There is a spectrum from executing source directly to compiling it fully in advance, and the choice is a familiar economic one.

An interpreter reads and executes as it goes: instant to start, slow to run, because every line is re-analysed every time. That is making a part by working straight from the drawing, re-reading it at each step. Ahead-of-time compilation analyses everything first and emits machine code: slow to start, fast to run. That is tooling up completely before cutting anything.

A JIT is a machinist deciding, mid-run, that a jig would pay

A just-in-time compiler starts by interpreting, watches which code runs repeatedly, and compiles only those "hot" paths to machine code. That is exactly the decision you make on the fortieth part: this is going to keep happening, stop, make a fixture, and run the rest quickly. Crucially, neither of you knows the quantity in advance — that is why the decision is deferred until the evidence arrives, and it is precisely the information a compiler running before the program starts does not have.

And the arithmetic is the jig break-even. With compilation cost \(C\) and per-iteration times \(s_{\text{slow}}\) and \(s_{\text{fast}}\):

$$n^{\ast} = \frac{C}{s_{\text{slow}} - s_{\text{fast}}}$$

On the figures in [Ch13 s07] — 1.00 ms interpreted, 0.05 ms compiled, 400 ms to compile — the break-even is 421 iterations. Below it the interpreter wins; above it the JIT does, and by 10,000 iterations it is eleven times faster.

That also explains JAX’s jax.jit, which compiles a function on its first call and caches the result: it is making the fixture on the first part and amortising it over the run. And it explains the standard complaint about it — that the first call is slow — which is the same complaint as "we lost the morning setting up".

08

Closures, matching, and contracts

src 05. programming languages ↗

Four features the source highlights, briefly, because the bridges are thinner here and it is better to say so.

A closure is a function that captures variables from where it was defined. Build a "make an adder for \(n\)" factory and you get back a function that remembers its \(n\). The closest honest analogue is a pre-set tool: the same drill, issued already set to a particular depth, carrying that setting with it wherever it goes.

Pattern matching branches on the shape of data rather than on equality. Algebraic data types let a value be one of several clearly enumerated variants — a result is either a success carrying a value or an error carrying a reason, never both and never neither. Together they let the compiler check that you have handled every case, which eliminates an entire family of bugs by construction. The nearest thing you have is a decision table whose completeness has been audited — every combination of conditions has a defined action, and the absence of one is caught at review rather than in service.

Traits and interfaces specify what a type must be able to do without specifying how. That is an interface specification: any part with this mounting pattern and this load rating will fit, and the supplier's internal design is theirs. The value is the same in both — you can substitute the implementation without touching anything that uses it.

09

You have already written a DSL

src 05. programming languages ↗

A domain-specific language trades generality for expressiveness inside one domain. The source lists SQL, regular expressions and shader languages. It misses the two you know.

G-code and GD&T are domain-specific languages

G-code is a language for machine motion. It cannot do general computation and it is not trying to; what it can express — a helical interpolation, a canned drilling cycle, a tool change — it expresses in a line, where a general-purpose language would need a page. That is exactly the SQL argument. GD&T is a language for tolerance specification, with a grammar, a symbol set and a formal semantics, and it exists because writing the same constraints in prose is ambiguous and unverifiable. Both are DSLs by any definition the source offers.

That makes the trade-off concrete rather than abstract. G-code’s narrowness is why a post-processor can verify a program and a controller can execute it deterministically; it is also why you reach for a macro language the moment you want a conditional. The source notes that PyTorch and JAX are "essentially DSLs for tensor computation embedded within Python", which is the same compromise — domain expressiveness where it matters, a general-purpose language underneath for everything else.

There is no best language

src 05. programming languages ↗

The source closes on trade-offs, and the framing that makes them obvious is material selection. There is no best material; there is a best material for a duty, given a budget. Language choice works the same way and along four axes:

Four trade-offs, and the material-selection question each resembles.
Trade-offThe two endsThe analogous question
Performance against safetyC lets you corrupt memory; Python will not let you near itStrength against toughness — you rarely get both at the top
Expressiveness against simplicityHaskell can state very precise constraints; Go deliberately cannotA specialised alloy against mild steel everyone can weld

The source’s own summary of the ML ecosystem is the clearest example: Python for experimentation because expressiveness wins when the GPU dominates the clock, C++ and CUDA for kernels because performance wins when it does not, Rust for infrastructure because safety wins when a failure is expensive. Three different duties, three different materials, one assembly.

!Where it breaks — “100× slower” is a claim with conditions

The source says Python is "~100x slower than C for compute-heavy code", and repeats similar figures for PyPy and the JVM. Treat all of these as reported rather than derived. They depend entirely on what is being measured: for a tight numeric loop in pure Python the figure is roughly right; for code that spends its time inside NumPy or PyTorch the Python overhead is close to irrelevant, because the work is happening in compiled kernels. The honest version is that interpreted overhead is per-operation, so it matters exactly in proportion to how many operations you execute in the interpreter — which is why the answer to "is Python fast enough?" is always "for which part of the program?", and why part 3’s worked example starts by measuring rather than assuming.

Solved as a line-balancing problem

One station (the loader) cannot be subdivided: it is a single Python thread, and part 2 §11 says the GIL prevents that work being shared. The other 212 ms is GPU work that more GPUs can share. That is exactly part 2 §16’s two-station line, so \(p = 212/250 = 0.848\) and the ceiling is

$$\frac{1}{1-p} = \frac{250}{38} = 6.58\times$$

No number of GPUs will ever make this step faster than 38 ms. That is the first useful fact, and you get it before spending anything.

Solved as a scaling question, which is where it gets interesting

The obvious move is to fix the loader — overlap it with compute by prefetching the next batch while the current one trains, so the step becomes \(\max(\text{loader}, \text{rest})\) instead of their sum. At one GPU that takes 250 ms to 212 ms: a gain of 1.18×. Meanwhile simply buying a second GPU gives 1.74×.

!This section was drafted to prove the opposite

The intended conclusion was the standard one: fix the bottleneck rather than buy capacity. Computed, it is false at one GPU — the hardware wins, 1.74× against 1.18× ([Ch13 s11]). The loader is only 15% of the step, and Amdahl cuts both ways: a stage that is a small share of the time cannot be worth much to fix, however serial it is.

But now scale up, and watch what happens to the same 38 ms:

The answer: the bottleneck moves, and it crosses at 5.58 GPUs

The loader overtakes the GPU work at \(n = 212/38 = 5.58\) ([Ch13 s11]). Before that it is a minor stage and fixing it is poor value; after that it is the constraint and everything else is wasted. And the gain from fixing it peaks at four GPUs (1.72×), then falls away again — because past the crossover the loader is most of a step that is already short.

So the correct plan is neither "fix the bottleneck" nor "buy hardware". It is: scale while the GPU work dominates, and fix the loader as you approach the crossover — around four GPUs, which is where the fix is worth most anyway.

This is Goldratt’s fifth focusing step, and it is the one everybody forgets. Identify the constraint, exploit it, subordinate to it, elevate it — and then, if the constraint has been broken, go back to step one. Optimising today’s bottleneck forever is how you end up with a perfectly balanced line that cannot go any faster, because every station is now the constraint at once.

Tier 1 — recall
Write down the pipeline efficiency formula and say what it is called on a shop floor.

\(\sum t_i / (n \max t_i)\) — line-balancing efficiency. Identical expression, and speedup equals \(n\) times it in both fields.

What is AMAT, and why is a 95% hit rate not a 95% result?

\(\text{AMAT} = h\,t_{\text{fast}} + (1-h)\,t_{\text{slow}}\). With L1 at 1 ns and RAM at 100 ns, 95% hits gives 5.95 ns — six times slower than L1, because the misses are 100× dearer. Rate times severity, not rate.

State Amdahl’s law and its asymptote.

\(S(n) = 1/((1-p) + p/n)\), tending to \(1/(1-p)\). Ninety-five percent parallel caps you at 20×, whatever you spend.

What are the four necessary conditions for deadlock?

Mutual exclusion, hold-and-wait, no pre-emption, circular wait. All four must hold at once, so breaking any one is sufficient prevention.

What does the cyclomatic number \(m - n + c\) count, mechanically?

The degree of static indeterminacy of the corresponding 1-DOF spring network — the number of redundant members. A tree is determinate.

Why does floating point have constant relative rather than constant absolute precision?

The exponent sets the magnitude and the mantissa carries a fixed number of figures within it. So the ulp grows with magnitude while ulp/x stays fixed — significant figures, in hardware.

What is a context switch, and what is it in manufacturing terms?

Saving one process’s state and loading another’s. It is a changeover: the work of switching produces nothing, so either make it cheaper or do it less often.

Give the compilation pipeline’s five stages and their process-planning equivalents.

Lexing (read the drawing), parsing (build the feature tree), semantic analysis (manufacturability review), optimisation (sequencing), code generation (post-process to G-code).

Tier 2 — apply
A 5-stage pipeline has stage times \(\{1,1,1,1,6\}\). What is the speedup, and what should you do?

Cycle time 6, total 10, so speedup \(10/6 = 1.67\) against an ideal of 5. Split the 6, not the 1s — splitting a non-bottleneck stage changes throughput not at all. Efficiency is \(10/30 = 0.33\).

You measure \(|\mu_2| = 0.80\) for a cache-like decay and a diameter of 12. Is a 12-layer design viable?

\(\ln(0.1)/\ln(0.8) = 10.3\) layers to lose 90%. Twelve layers are needed and about ten are affordable, so the window is closed — you need residual connections, a wider stencil, or a different topology.

Five jobs of 10, 4, 6, 2, 8 arrive together. Compute the mean flow time under FCFS and under SPT.

FCFS: completions 10, 14, 20, 22, 30 → mean 19.20. SPT (2,4,6,8,10): completions 2, 6, 12, 20, 30 → mean 14.00. A 27% cut, and SPT is provably optimal.

A critical section occupies 2% of each thread’s time. What is the maximum speedup on 128 cores?

\(p = 0.98\), so the ceiling is 50× and at 128 cores \(1/(0.02 + 0.98/128) = 36.2\times\). The lock, not the core count, is what you are buying.

Compilation costs 250 ms; interpreted 0.8 ms/iter, compiled 0.04 ms/iter. Where is the break-even?

\(250/(0.8-0.04) = 329\) iterations. Note the denominator is the saving, not the interpreted time — the jig does not make the operation free.

A server runs at 90% utilisation. Your manager wants 95%. What are you buying and paying?

\(L\) goes from 9 to 19 and \(W\) from 10 to 20 service times. You buy 5.6% more throughput and pay with a doubling of queue time. On a latency-sensitive service that is a bad trade, and it is the same trade as loading a plant to 95%.

Why does \(\text{force} + \text{length}\) fail while \(\text{force} \times \text{length}\) succeeds?

Addition requires identical dimension vectors; multiplication adds the exponents. \((1,1,-2) + (0,1,0)\) is refused; \((1,1,-2)\times(0,1,0) = (1,2,-2)\), which is energy. A type checker does exactly this.

A training step is 30 ms serial and 270 ms parallel. What is the ceiling, and where does the bottleneck flip?

\(p = 0.9\), ceiling 10×. The serial part overtakes at \(270/30 = 9\) workers. Below nine, scale; approaching nine, fix the serial stage.

Tier 3 — judge
Part 3 §11 was drafted to prove that fixing a bottleneck beats buying hardware, and the arithmetic said otherwise. What should you conclude?

Not that the maxim is wrong, but that it is conditional on the bottleneck being a large share of the time — Amdahl cuts both ways. The valuable finding was the one nobody was looking for: the constraint moves as you scale, so the right question is not "what is the bottleneck" but "what will the bottleneck be at the scale I am heading for". A claim that survives being computed is worth more than one that was never tested, and a claim that fails usefully is worth more than either.

Both the source’s float demonstration and its GIN demonstration in Sheet 12 print the opposite of their captions. What does that tell you?

That conclusions get reviewed and examples do not. In both cases the stated conclusion was correct and the demonstration was broken, which is exactly the combination that survives indefinitely — a reader who agrees with the conclusion has no reason to run the code. The practical rule: run every example, and be more suspicious of demonstrations than of theorems.

SPT is provably optimal and unusable in an OS. Is the theorem worth teaching?

Argue both. Against: an unusable optimum can mislead, and multilevel feedback queues — which are what real schedulers use — have no optimality guarantee at all. For: knowing the optimum tells you what you are giving up, and the reason it is unusable (you cannot know the future) is itself the useful lesson, connecting directly to undecidability. The strongest position is that the theorem is worth teaching with its impossibility, and that teaching it alone is what produces engineers who look for a rule that cannot exist.

Part 2 §13 measured that capping WIP costs 2.4% of throughput at ten cards and 44% at one. How should that change how you read lean advice?

It converts a slogan into a sizing problem. "Reduce WIP" is right in the region where the cap sits above the working queue length and actively harmful below it, and nothing in the slogan tells you which side you are on. The honest reading is that the advice encodes an assumption about where you are starting — usually far above the cliff — and that the assumption should be checked rather than inherited.

This chapter claims a very high transfer rate between manufacturing and computing. Is that evidence, or eagerness?

Be sceptical. The defence is that the identities are numerically checked and scope-bounded, and that both fields are solving genuinely the same problem — allocating scarce resources among competing demands — so convergence is expected rather than surprising. The concern is real: a frame that explains everything explains nothing. The test is whether the bridge ever predicted something, and here it did twice: the EOQ form of the quantum optimum and the moving constraint in §11 were both found by taking the correspondence seriously, not by reading the source.

Undecidability has no mechanical counterpart. Was it worth a full section?

Yes, and precisely because it has none. A series built on correspondences has a standing bias toward finding them, and the discipline that keeps it honest is naming the places where there is nothing to find. It also has a practical payoff: an engineer who confuses "no closed form" with "undecidable" will keep looking for a perfect deadlock detector or a perfect optimiser, and the distinction is what stops that search.

Part 1 §09 argues your heuristics are heuristics because the problems are NP-hard. Does knowing that change anything you do?

Three things, concretely. You stop looking for the exact method. You start asking what guarantee your heuristic carries — "within 11/9 of optimal" and "works well in practice" are very different claims to defend. And you look for special structure, because NP-hardness is a worst-case statement and your instance may not be the worst case. What it should not change is your confidence in the heuristic: it was optimal on 98.8% of measured instances.

Which of the three parts would you drop if the chapter had to be shorter, and what would be lost?

A defensible answer is part 3, since languages are the most replaceable knowledge and the compilation pipeline is the least load-bearing bridge. What would be lost is the chapter’s only end-to-end example, the types-as-units correspondence — which is the single cheapest thing here for an engineer to adopt — and the worked example whose failure produced the moving-constraint result. Arguing for a different part is equally legitimate; the useful move is to notice that the three parts are not equally about computing. Part 1 is mathematics, part 2 is operations research, and only part 3 is really about software.

The map, and what the chapter leaves out

beyond the chapter

Three parts in one picture. Read it as a stack: the mathematics under the machine, the machine, the sharing of it, and the language you write it in — with one law running vertically through all of them.

What this chapter feeds

Sheet 14 (data structures and algorithms) takes part 1 §06’s recurrences and part 1 §09’s complexity classes and does them properly — the source says so itself. Sheet 16 (SIMD and GPU) inherits part 2 §11’s SIMT model and part 1 §15’s memory hierarchy, and it is where the bus bottleneck of part 1 §17 becomes the whole subject. Sheet 17 (AI inference) is part 1 §10’s number formats applied in anger — quantisation is choosing how many significant figures you can afford. Sheet 18 (ML systems design) takes part 2’s Little’s law, its scaling laws and its container material and makes them the architecture.

What this chapter does not cover

Naming it honestly, so the three parts do not imply completeness:

  • Proofs. The halting problem argument is sketched, not rigorous. NP-completeness is stated without a reduction. SPT’s optimality is verified exhaustively on small instances rather than proved by exchange argument.
  • Real assembly language and real ISAs. Part 1 §12 describes what an instruction set is and shows none. You could not read a disassembly after this chapter.
  • Caches in any depth — no cache-oblivious algorithms, no false sharing, no prefetching, no NUMA, and no actual measurement on real hardware.
  • Distributed systems. Part 2 stops at one machine. Consensus, replication, partial failure, and the CAP trade-off are absent, and they are most of what makes distributed computing hard.
  • Security beyond a paragraph. Part 2 §08 names the mechanism and stops. No threat modelling, no cryptography, no side channels.
  • Writing a compiler. Part 3 §05 describes the stages; it would not let you build one, and parsing alone is a term’s work.
  • Any hands-on work at all. No profiler output, no perf, no strace, no container built, no code written. Every number here is either the source’s or computed in a verification script.

What the three parts do claim is that the correspondences are correct and scope-bounded, and that every numerical statement across all three can be reproduced by running one script.

✓If you take three things from the whole chapter

The bottleneck law is one law. Line balancing, Amdahl and the theory of constraints are the same statement, and the fifth focusing step — go back to step one — is the part that keeps being forgotten in both fields. Rate times severity, not rate. A 95% hit rate, 95% branch accuracy and 95% first-pass yield are all worse than they sound, by the same arithmetic. Your heuristics are heuristics for a reason, and the reason is NP-hardness, which is worth knowing because it tells you to stop looking for the exact rule and start asking what guarantee you have instead.
