Smaller, Not Cheaper

The last part of Chapter 16 leaves the data centre. One vector loop runs on any width of machine; one shader runs on any vendor’s GPU; one model runs on a chip that costs a dollar. Each works the same way: write to the smallest machine you are guaranteed, and ask the real one what it has. The same two laws as parts 1 and 2 price every step.

This part covers source file 06 (RISC-V and embedded systems) and file 07 (Vulkan compute and cross-platform GPUs), and closes the chapter with its worked example, question bank, a map of all three parts and its own Appendix A. Part 2 §19 listed six calculations this part owes. They are paid in §02 (RISC-V’s vector loop), §07 (Vulkan subgroups as lanes), §08 (file 07’s reduction tree), §09 (its tiled matmul, priced), §04 (energy per FLOP) and §14 (the chapter map).

The headline is §04, and it comes from the source’s own table of a server GPU, a smartphone and a microcontroller. Divide each one’s compute by its power: 0.70, 0.50 and 1.00 picojoules per FLOP. Across a 700,000-fold range of power, the energy per operation moves by a factor of two, and the cheapest is the phone. The edge is smaller, not cheaper. Part 1’s cube law would have predicted the microcontroller at 4.6 femtojoules, 219 times less; part 1 §03 warned that the law ignores leakage, and the table shows how much that matters at the bottom.

The other exact result is §02. RISC-V’s vsetvl lets the hardware choose how many elements each pass of a loop handles, and even lets it split the last two passes evenly. Checked for every array length up to 3,000 at seven widths, the number of passes is always \(\lceil n/\text{VLMAX}\rceil\): part 1’s drilling head, with the spindle count read off the machine.

No RISC-V board, emulator or GPU was available. The source’s vector loop was compiled for RISC-V with clang and read; its three C++ tasks were compiled and run on the x86 build machine; all six GLSL shaders in file 07 were compiled to SPIR-V with glslang (its WebAssembly build). Hardware figures are the source’s or marked as reported. Checks are tagged [Ch16p3 sNN] in verify_claims.py.

01

RISC-V: an instruction set as an open standard

src 06. RISC-V ↗

An instruction set architecture (ISA) is the contract between software and a processor: the list of instructions, registers and memory rules that any chip of that family must honour. x86 and ARM are licensed contracts. RISC-V, started at Berkeley in 2010, is an open one: anyone may build a chip to it without a fee. It is modular. A small base (RV32I or RV64I) is extended by letters: M for multiply and divide, A for atomic operations, F and D for floating point, C for compressed instructions, V for vectors. A chip carries only the letters it needs, the way a part drawing calls up only the standards that apply to it.

The base has 32 general-purpose registers, x0 to x31, with x0 wired to zero; the source counts these correctly, where part 1 §09 caught it miscounting ARM’s ([Ch16p3 s01]). Instructions are a fixed 32 bits, with 16-bit forms in the C extension, and only loads and stores touch memory. The source’s “just 47 instructions” for the base is reported; the ratified base specification is reported to list 40, the difference being instructions since moved into separate extensions. Its gate counts (about 10,000 for a minimal core against 12,000 for an ARM Cortex-M0) and its list of adopters are reported too.

02

One loop for any width

src 06. RISC-V ↗

Debt 1 of 6. The V extension gives RISC-V vector registers whose width, VLEN, the hardware chooses: any power of two from 128 to 65,536 bits. Code is written without knowing it. The source’s vector addition is a strip-mining loop:

$$\texttt{vl} = \texttt{vsetvl}(n_{\text{left}}), \quad \text{process } \texttt{vl} \text{ elements}, \quad n_{\text{left}} \leftarrow n_{\text{left}} - \texttt{vl}, \quad \text{repeat while } n_{\text{left}} > 0 .$$

The program asks for \(n_{\text{left}}\) elements and the hardware answers with how many it will take this pass. The most it can take is

$$\text{VLMAX} = \frac{\text{VLEN} \times \text{LMUL}}{\text{SEW}},$$

where SEW is the element width in bits and LMUL the number of registers ganged together. For 32-bit floats and LMUL = 1 that is 4 lanes at VLEN 128 and 2,048 at VLEN 65,536. Compiled for RISC-V with clang, the source’s loop is 11 instructions per pass: vsetvli, two vector loads, one vector add, one vector store, and six to move pointers, count down and branch ([Ch16p3 s02]). At VLEN 128 that is 2.75 instructions per float; at 65,536, 0.0054. The binary is the same; only the number of passes changes.

The source says vsetvl returns \(\min(n, \text{VLMAX})\). The vector specification is reported to allow more: when \(n_{\text{left}}\) lies between VLMAX and \(2\,\text{VLMAX}\), the hardware may return anything from \(\lceil n_{\text{left}}/2 \rceil\) to VLMAX, so it can split the last two passes evenly instead of leaving a scrap for the last one. Simulated both ways for every \(n\) from 1 to 3,000 at seven values of VLMAX, the pass count is the same and equal to

$$\text{passes} = \left\lceil \frac{n}{\text{VLMAX}} \right\rceil ,$$

and every element is processed exactly once. For 1,000 floats at VLEN 512 that is 63 passes, the last holding 8 of 16 lanes (or two passes of 12 when balanced), with 99.2% of lane-passes doing work.

✓Identity: part 1’s drilling head, with the spindle count read off the machine

Part 1 §05 counted \(\lceil n/W \rceil\) strokes for \(n\) holes on a \(W\)-spindle head, with the spare drills of the last stroke removed. Part 1 §09 met SVE, where svwhilelt builds the mask for a head of unknown width, and part 2 §11 met the same mask in Triton. vsetvl goes one step further: there is no mask in the loop at all, because the machine tells the program how many spindles carry drills on each stroke. The stroke count is the same expression in all four. The balanced tail is the furnace operator’s rule of evening out the last two loads rather than running one full and one nearly empty: the number of loads is unchanged and neither is wasteful.

LMUL gangs registers. With LMUL = 8 one instruction covers eight registers’ worth of elements, and the 32 vector registers become 4 groups, as the source says: 32, 16, 8 and 4 groups at LMUL 1, 2, 4 and 8. It is ganging several heads on one slide: more holes per stroke, fewer separate heads to hold the work in progress.

!Where it breaks

A pass count is not a time. Each pass still has its fixed 11 instructions, and a wide machine is only as fast as its memory can feed it, which is part 1’s roofline again: a vector add does one FLOP per 12 bytes on any VLEN. Fewer registers per group at high LMUL also means fewer independent accumulators, which part 1 §08 showed is what keeps a chain of dependent operations busy. The loop is portable; its speed is not.

03

TinyML, with the source’s three tasks run

src 06. RISC-V ↗

TinyML is machine learning on microcontrollers: kilobytes of memory, a clock in the tens or hundreds of megahertz, a power budget in milliwatts. The source’s example framework, TensorFlow Lite Micro, keeps the model as a constant array in flash and does all its work in one arena, a block of RAM reserved at compile time. Nothing is allocated while the program runs, so nothing can run out halfway through an inference. It is a fixture plate with every pocket machined before the first part arrives; the price is that the plate must be sized for the busiest moment of the job.

The source gives three C++ tasks and says to compile them with g++. All three were compiled and run on the build machine ([Ch16p3 s03]).

Task 1 describes a 784→64→10 network with 8-bit weights. It prints a model size of 50,890 bytes, which fits the 256 KB flash it checks, 74 bytes of activations in a 32 KB arena, and output logits that are all 1, because the mock weights are all 1. Then it prints its latency, 4.9 µs here, and converts that to “~783 cycles” of a 160 MHz microcontroller (825 on a second run).

!The cycle count is the build machine’s time in someone else’s clock

The network does \(784 \times 64 + 64 \times 10 = 50{,}816\) multiply-adds per inference. The printed figure is the x86 machine’s time multiplied by 160 MHz, which says how many microcontroller ticks pass while the desktop works, not how many the microcontroller needs. A microcontroller doing one multiply-add per cycle, an assumption, needs at least 50,816 cycles: 317.6 µs at 160 MHz, 65 times the printed figure. A unit slip of this kind survives because the printed number has the right units.

Task 2 quantises 100,000 weights to 8-bit integers with one scale. It prints a scale of 0.00292623, a largest error of 0.499995 steps (“should be <= 0.5”, and is) and a mean absolute error that works out to 0.2496 steps. Replayed in float32, the root-mean-square error is 0.2884 steps.

✓Identity: the reading uncertainty of a graduated scale

Sheet 17 §03 showed that rounding to a step \(\Delta\) leaves an error spread evenly over \(\pm\Delta/2\), whose standard deviation is \(\Delta/\sqrt{12} = 0.2887\,\Delta\), the rectangular uncertainty of a scale reading. The mean of its absolute value is \(\Delta/4\). The source’s task measures 0.2496 and 0.2884 against 0.25 and 0.2887. Its “4x” compression is 400,000 bytes against 100,004 including the scale.

Task 3 times an 8-bit matrix product against a float one, both 128×128, and prints the speedup. Across runs here it printed 0.94, 0.98 and 1.46×. The source says 8-bit is “2–4x faster on integer-only hardware”; on this machine both loops walk down a column of \(B\), 512 bytes apart in float and 128 in 8-bit, and wait on the same delivery station whatever the arithmetic (part 1 §07). On a microcontroller without floating-point hardware, where every float operation is done in software, the gap would be real (reported). The 4× saving in memory, 32 KB against 128 KB, holds on any machine.

The source’s list of edge optimisations points to the rest of the series: quantisation (it says chapter 18; the compendium’s quantisation file is chapter 17’s, Sheet 17 §§02–07 here), pruning and distillation (Sheet 17 §12), and fusion, which part 1 §01 and part 2 §12 priced. “Even more critical when you have 256 KB of RAM”, it says of fusion, and the arena is why: an intermediate result that is never written needs no pocket.

Power runs over a factor of 700,000 from top to bottom. Energy per FLOP, power divided by compute, moves by a factor of two, and the cheapest operation is the phone’s. Per dollar of hardware the server is cheapest and the microcontroller dearest by a factor of 33. By the source’s own figures, the edge does not compute more cheaply. It computes less, in a smaller package, on a smaller budget.

Part 1 §03 gave a reason to expect otherwise. Dynamic power is \(P \propto CV^2 f\), and if voltage can fall in proportion to frequency, energy per operation falls as \(f^2\). Scale the server’s 0.70 pJ at 1.98 GHz down to a 160 MHz microcontroller (task 1’s clock):

$$0.70\ \text{pJ} \times \left(\frac{0.16}{1.98}\right)^{2} = 4.57\ \text{fJ per FLOP},$$

against the table’s 1 pJ, 219 times more. Part 1’s break box said why the law fails at the bottom: voltage cannot keep falling once it nears the transistor’s threshold, and leakage, which flows whether or not anything is computed, takes over. The table puts a number on that warning. Its microcontroller row is also generous: 1 GFLOP/s at 160 MHz is 6.25 floating-point operations per cycle, a vector unit’s rate, and real microcontrollers are reported to spend more per operation, not less. That would only widen the gap.

✓Same structure: specific fuel consumption, and why it rises at part load

Energy per FLOP is a specific consumption, like an engine’s grams of fuel per kilowatt-hour: energy in per unit of useful work out. A large engine and a small one can have similar figures; what differs is the rating. And both rise at part load for the same reason. An engine’s friction and pumping losses do not shrink with output; a chip’s static power does not shrink with work done. With a share \(s\) of full power that is fixed, energy per operation at utilisation \(u\) is

$$\frac{E(u)}{E(1)} = \frac{s + (1-s)\,u}{u},$$

which with \(s = 30\%\) (an assumption, not the source’s) is 1.3× at half load and 3.7× at 10%. An edge chip that wakes for a few milliseconds and sleeps the rest pays exactly this unless it can switch its static power off, which is why sleep modes matter more than peak rates at the edge.

!Where it breaks, and what the edge does win

A FLOP is not the same work everywhere: the phone’s 10 TFLOPS is likely an 8-bit rate from its neural unit, not float32 (reported), and the table mixes formats. And energy per FLOP is the wrong figure of merit for the edge. A sensor on a coin cell needs 1 mW, not 700 W; a microcontroller costs $1 per device; its data never leaves the device and never waits for a network (§05). Those are the edge’s gains, and none of them is efficiency per operation. Sheet 17 §17 found the same from the other side: the edge runs at batch one by necessity, and pays for it.

05

The control core, and the edge’s budgets

src 06. RISC-V ↗

Many AI accelerators, the source says, use RISC-V not to run the model but to run the chip. Its diagram puts a RISC-V control core beside a custom matrix unit (a systolic array, part 2 §10) and an on-chip SRAM buffer. The control core loads weights, schedules layers, moves data between units and talks to the host; the matrix unit does the arithmetic. That is part 1 §01’s split between the planner and the floor, built into one chip. RISC-V suits the planner’s job because it is free to license, small, and open to added instructions. The companies the source names are reported.

The source’s edge constraints are budgets, and two of them are arithmetic. A battery device with 100 mW in all, running a 50 mW model, leaves 50 mW for its sensors, radio and display. And latency: a wake word must answer within about 200 ms, a driving perception stack within about 30 ms, while a round trip to the cloud takes 50–200 ms. The perception budget is exceeded by the network alone, by 20 ms at its very best, before any computing is done; the wake word keeps between 0 and 150 ms for itself ([Ch16p3 s06]). Privacy and offline operation are the other two reasons the source gives, and neither is a number.

✓Same structure: the planner and the floor, on one die

A control core is small because the planner’s work is small: it issues orders and the floor does the work. Where it breaks: on one chip the planner and the floor share the same clock and memory, so a slow planner stalls the floor directly. An accelerator’s control core must keep its matrix unit fed, which is part 2 §05’s problem of keeping enough work in flight, now on the planner’s desk.

Vulkan, counted

src 07. Vulkan ↗

CUDA runs on NVIDIA’s GPUs only. Vulkan, from the Khronos Group, is a GPU interface that every major vendor implements, and the source’s route to phones, AMD and Intel GPUs, and (through WebGPU) the browser. Its price is explicitness. Where CUDA’s driver quietly creates contexts, allocates memory and orders work, a Vulkan program does each step itself: create an instance, pick a device, allocate memory of a chosen type, create buffers, describe how they bind to the shader, build a pipeline, record commands into a command buffer, submit it to a queue and wait on a fence. The source argues this keeps drivers thin and lets the program synchronise only where it must.

The GPU code itself is a compute shader, written in GLSL and compiled to SPIR-V, a portable binary that each vendor’s driver translates for its own hardware. All six compute shaders in file 07 (vector add, ReLU through shared memory, the reduction, the tiled matmul, softmax, and Kompute’s inline add) were compiled to SPIR-V here with glslang’s WebAssembly build: 6 of 6 compile ([Ch16p3 s07]). The C++ host program needs the Vulkan SDK and a device, and neither is in the build container, so it was read, not run.

✓Same structure: a drawing standard any shop can make the part to

SPIR-V is a drawing in a standard form: any conforming shop can make the part, with its own machines and its own process plan. Where it breaks: a drawing fixes the part’s geometry, so every shop delivers the same thing; SPIR-V fixes the result, and every driver compiles it again for its own hardware, so the speed of the same shader differs by vendor. Correctness travels; performance does not, and §09 shows that even correctness travels only within the standard’s guaranteed limits.

The source says this costs “~200 lines for vector addition” against CUDA’s “~30”. Counted, its Vulkan program is 223 lines of code (288 with blank lines and comments) against 32 (54) for its own CUDA vector_add: 7.0 times as much ([Ch16p3 s07]). Reading those 223 lines turns up two faults.

!The memory-type test accepts the wrong memory

The program wants memory the CPU can write and the GPU then sees without further action: host-visible and host-coherent. Its test is flags & (HOST_VISIBLE | HOST_COHERENT), which is true if either bit is set. A memory type that is visible but cached and not coherent passes, and the program never flushes its writes, so the GPU may read stale data. The test must be (flags & (VISIBLE | COHERENT)) == (VISIBLE | COHERENT); with the real flag values the first test accepts both a visible-but-not-coherent type and a coherent-only one, and the second rejects both. Nor does the program check a single return value: on a machine with no Vulkan device the count comes back 0 and devices[0] reads past the end of an empty vector.

The source’s cure for the verbosity is a wrapper library. Kompute shrinks the program to a dozen lines. Its shader, though, declares local_size_x = 1, which §07 prices.

Subgroups are lanes

src 07. Vulkan ↗

Debt 2 of 6. The source maps Vulkan’s vocabulary onto CUDA’s. One level is missing from its table, and it is the level that matters for speed. Vulkan 1.1 calls the hardware’s warp a subgroup and lets a shader read its size, gl_SubgroupSize, and use subgroup operations (reported; the source does not mention subgroups). Its size depends on the vendor: 32 on NVIDIA, 64 or 32 on AMD, and from 4 to 128 elsewhere (reported).

Divergence follows the head, whatever its size. A workgroup of 256 invocations is 8 subgroups of 32 or 4 of 64, and part 2 §06’s count applies with \(s\) lanes in place of 32. A branch that a fraction \(q\) of invocations take at random is run by the whole subgroup with probability

$$P = 1 - (1-q)^{s} \;=\; 27.5\%,\ \ 47.4\%,\ \ 72.4\% \quad \text{for } q = 1\%,\ s = 32,\ 64,\ 128 .$$

With the rare path costing 100 and the common one 10, a subgroup spends 3.44, 5.27 and 7.56 times the per-lane average. Even/odd branching diverges in every subgroup at any size; a first-half/second-half split diverges in none, if the boundary falls on a multiple of the subgroup size ([Ch16p3 s08]).

✓Identity: the zero-acceptance plan with the sample size set by the vendor

Part 2 §06 found that a warp runs a rare branch with the rejection probability of Sheet 15’s \(c = 0\) sampling plan, sample 32. A subgroup is the same plan with sample \(s\). Doubling the sample nearly doubles the chance of catching one defective at small \(q\), which is good for an inspector and bad for a shader: on a 64-lane GPU the same branch costs the rare path in almost half of all subgroups.

!Kompute’s shader runs one drill per head

local_size_x = 1 makes every workgroup a single invocation, and a workgroup never shares a subgroup with another. Each invocation occupies a whole subgroup with one live lane: 3.1% of a 32-lane subgroup, 1.6% of a 64-lane one. The example’s 5 additions occupy 5 subgroups, 160 or 320 lane-slots. A size of 64 or 256 with a bounds test, as in the source’s own add.comp, fills the head. And since the subgroup size can differ between devices, and is reported to vary between shaders on some, portable code reads gl_SubgroupSize instead of assuming it: vsetvl’s lesson from §02 again.

The whiffletree: file 07’s reduction, counted

src 07. Vulkan ↗

Debt 3 of 6. The source’s reduce_sum.comp sums 256 values per workgroup. Each invocation loads one value into shared memory; after a barrier, invocations below 128 add the value 128 places above theirs; after another barrier, those below 64 add the value 64 above; and so on to 1. Thread 0 writes the workgroup’s total, and a second dispatch reduces those totals the same way. Counted ([Ch16p3 s09]):

  • Barriers: 9 per workgroup, one after the load and one after each of the 8 halvings.
  • Additions: 255, which is \(n - 1\), the same as a single running total; the tree changes the order and the depth (8 levels), not the work.
  • Lane-slots doing an addition: 255 of \(8 \times 256\), 12.5%. Most lanes sit idle at most steps.
  • Subgroups that must issue at each step, with 32 lanes: 4, 2, 1, 1, 1, 1, 1, 1. Inside those, 66.4% of lanes work. With 64 lanes: 2, 1, 1, 1, 1, 1, 1, 1, and 44.3%. The last 5 steps (6 at 64 lanes) run inside a single subgroup with most of its lanes switched off: part 2 §06’s divergence.

Vulkan’s subgroup operations (reported) let each subgroup add its own values in one instruction. Each subgroup then writes one partial sum, one barrier follows, and one subgroup adds the partials: 1 barrier instead of 9. The order inside that instruction belongs to the implementation (reported).

✓Same structure: a whiffletree of balance beams

A whiffletree combines loads in pairs: each beam takes two forces and passes their sum to the beam above. Spread a load over 256 points and it takes 255 beams in 8 levels, the tree in file 07 to the beam. Windscreen-wiper arms and the multi-point supports of telescope mirrors are built this way. Where it breaks: a whiffletree acts all at once, every level in equilibrium together, and its sums are exact. The GPU’s levels happen one after another, a barrier between each, and every addition rounds.

Does it repeat bit for bit? Yes, on one device. Every addition’s operands are fixed by the invocation’s index, not by timing, and the second dispatch is the same fixed tree. Run on part 2’s 65,536 numbers in float32, the two dispatches land 0.8 ulp below the exact sum, with the same bits every time. Part 2 §14 combined the same 256 block totals by atomic adds in arrival order and got 14 different totals in 200 runs. The tree is also the better tolerance stack: its worst case is 16 levels of rounding, \(16u = 9.5 \times 10^{-7}\) of the sum of magnitudes, against \(3.9 \times 10^{-3}\) for a running total. A different GPU may still give different bits, through a different subgroup size or compiler.

The portable kit

src 07. Vulkan ↗

Debt 4 of 6. File 07’s tiled matrix multiply is, as it says, “the same tiling algorithm as the CUDA version”: TILE_SIZE 16, one output per invocation, two 16×16 tiles in shared memory, a barrier before and after each step. So it carries part 2 §08’s price: \(b/4 = 4\) FLOP per byte, 2 KiB of shared memory, 256 invocations per workgroup, and on part 2’s reference GPU (66.9 TFLOP/s, 3.3 TB/s) 13.2 TFLOP/s, 19.7% of the roof. Delivery binds, as it did in CUDA.

Portability adds a second constraint. Vulkan does not promise every device the limits of a data-centre GPU. Its guaranteed minimums are reported to be 128 invocations per workgroup and 16 KiB of shared memory. The source’s 16×16 workgroup is 256 invocations, so it is not guaranteed to run everywhere. The largest one-output square tile within the minimum is 11×11, 121 invocations, at \(11/4 = 2.75\) FLOP/B, which reaches 9.07 TFLOP/s on the reference GPU. Shared memory alone would allow \(8b^2 \le 16{,}384\), so \(b \le 45\); the invocation count is the binding limit ([Ch16p3 s10]).

On the smartphone the source’s figures stop short: it gives 10 TFLOPS but no memory bandwidth. Taking a reported LPDDR5 figure of 51.2 GB/s, the phone’s ridge is about 195 FLOP/B, nearly ten times the reference GPU’s, and the 16-tile reaches 0.205 TFLOP/s, 2.0% of the phone’s peak. A phone has the arithmetic of a small GPU and the memory of a laptop, so on a phone every kit is far too small.

✓Same structure: designing to the minimum guaranteed strength

A part designed to the minimum specified yield strength is safe with any heat of steel that meets the specification, though most heats are stronger. A shader that stays within Vulkan’s minimum limits runs on any conforming device, though most devices allow more. Where it breaks: steel cannot be asked its strength before use, but a device can. A program reads the real limits at run time and picks its tile to suit, which is what part 2 §11’s autotuning and §02’s vsetvl both do. Portable code is written to the minimum and tuned to the machine.

Small jobs, softmax and the browser

src 07. Vulkan ↗

The softmax shader. Coding task 2 computes a softmax with two shared-memory trees, one for the maximum and one for the sum: 19 barriers per workgroup. It reduces within a workgroup only, so it is a softmax of a row of at most 256 values. Simulated on 256 values it matches the textbook softmax. On 512 it runs two workgroups, each of which normalises its own half, and the outputs sum to 2.000 instead of 1 ([Ch16p3 s11]). A longer row needs a second pass over the workgroups’ partial results, which is part 2 §13’s online softmax.

The WGSL kernel. WebGPU, the browser’s GPU interface, runs on top of Vulkan, Metal or Direct3D 12 and has its own shading language, WGSL. The source’s WGSL vector add drops the bounds test its GLSL twin has (if (idx < n)). For 1,000 elements its dispatch of \(\lceil 1000/256 \rceil = 4\) workgroups starts 1,024 invocations, 24 past the end. WebGPU is reported to confine out-of-range accesses to the buffer, which prevents damage elsewhere but does not make them correct.

!Task 3 cannot measure bandwidth: the job is smaller than the pipe

Task 3 asks for the achieved bandwidth of the 1,024-element vector add. That dispatch moves 12,288 bytes. Part 2 §05 found that a GPU with 3.3 TB/s and a 400-cycle latency needs 666,667 bytes in flight to run at full rate. This whole job is 1.8% of that. Even if every byte flew at once, with no launch cost at all, it would take one round trip, 202 ns, for 60.8 GB/s, 1.8% of the bandwidth. Launch and synchronisation overheads (reported, microseconds) bring the measured figure far lower. To measure bandwidth, the job must be many times larger than bandwidth × latency: Little’s law again.

The source closes with a table of when to use Vulkan: not for training or for NVIDIA inference, yes for AMD and Intel GPUs, Android and cross-vendor libraries, WebGPU in the browser, Metal on Apple devices. Those are judgements about tools and are reported, as are the libraries it names (vk-bootstrap, VMA, Kompute, ONNX Runtime Web, Transformers.js).

Worked example: a wake word on a RISC-V microcontroller, solved twice

src 06. RISC-V ↗
The problem

Run task 1’s 784→64→10 network, with 8-bit weights, on a 160 MHz RISC-V microcontroller with the source’s table figures: 256 KB of RAM, 1 MB of flash, 1 mW. (a) Does it fit? (b) On a scalar core doing one multiply-add per cycle, how long and how much energy per inference, and what share of the time is it busy at ten inferences a second? (c) With the vector extension at VLEN 128 and at VLEN 1,024, 8-bit elements, how many passes, what share of lanes used, and how long at one pass per cycle? (d) Against the source’s 200 ms wake-word budget, what limits the design? The per-cycle rates are assumptions for the example, not the source’s.

Solved as a drilling head

The work is 74 rows of holes: 64 rows of 784 (the first layer’s dot products) and 10 rows of 64, 50,816 holes in all. A single spindle drilling one hole per cycle takes 50,816 cycles, 317.6 µs at 160 MHz, and at 1 mW uses 0.318 µJ. A 16-spindle head (VLEN 128 holds sixteen 8-bit values) drills a 784-row in exactly 49 strokes and a 64-row in 4: \(64 \times 49 + 10 \times 4 = 3{,}176\) strokes, every spindle cutting, 19.9 µs. A 128-spindle head (VLEN 1,024) needs 7 strokes per 784-row, the last carrying 16 drills of 128, and 1 half-filled stroke per 64-row: 458 strokes, 86.7% of spindle-strokes cutting, 2.9 µs. Eight times the spindles buys 6.9 times fewer strokes, because 784 is a multiple of 16 and not of 128.

The parts fit their stores easily. The weights are 50,890 bytes in a megabyte of flash (4.9%); the activations are 74 bytes in task 1’s 32 KB arena. Ten inferences a second keep even the scalar core busy 0.32% of the time.

Solved as an RVV program

Each dot product is §02’s strip-mining loop with SEW = 8. At VLEN 128, VLMAX = 128/8 = 16 and a row of 784 takes \(\lceil 784/16 \rceil = 49\) passes, all full; at VLEN 1,024, VLMAX = 128 and \(\lceil 784/128 \rceil = 7\), the last with \(784 - 6 \times 128 = 16\) live lanes. The counts are the head’s, exactly, and the same binary runs on both chips ([Ch16p3 s13]). Real 8-bit kernels also widen their sums to 32 bits and pay the loop’s fixed instructions per pass, so these times are floors.

What limits the design (d). Not the arithmetic: 317.6 µs is 0.16% of the 200 ms budget even without vectors. The energy per inference at ten a second averages 3.2 µW. If 30% of the chip’s 1 mW is static, as in §04’s illustration, it draws 300 µW whether or not it computes, about 94 times the computing. The design is decided by how deeply the chip can sleep between inferences, which is §04’s part-load curve: the specific consumption of an engine that idles most of the time.

The two solutions are one count. The head gives the picture (spindles, strokes, the last stroke part-filled); the program gives the instruction that makes the count portable. And the lesson the series has been building to is in part (d): once the arithmetic is fast enough, the constraint moves to whatever station is left, here the standby power.

Question bank

24 prompts

Eight to recall, eight to apply, eight to judge; the last judge question spans the chapter. Answer before opening. The numerical answers are recomputed by the verifier under [Ch16p3 s16].

Recall

01What does vsetvl return, and what does the loop do with it?

The number of elements the hardware will process this pass, at most VLMAX. The loop processes that many, advances its pointers, subtracts from the count and repeats until nothing is left. No mask and no clean-up loop.

02Give VLMAX in terms of VLEN, SEW and LMUL.

\(\text{VLMAX} = \text{VLEN} \times \text{LMUL} / \text{SEW}\): register bits times registers ganged, over element bits.

03What is TinyML’s static arena, and why use one?

A block of RAM reserved at compile time for all activations and scratch. Nothing is allocated while running, so nothing runs out halfway through an inference, and the peak need is known before the chip ships.

04Name Vulkan’s invocation, subgroup and workgroup in CUDA’s terms.

Thread, warp and block. The subgroup is 32 lanes on NVIDIA and 64 or 32 on AMD (reported); a shader reads gl_SubgroupSize.

05What is SPIR-V?

The portable binary a GLSL shader compiles to. Each vendor’s driver translates it for its own hardware, so correctness travels and speed does not.

06How many barriers and additions does file 07’s 256-value reduction use?

9 barriers (one after the load, one per halving) and 255 additions, \(n-1\), in 8 levels.

07What does it mean to write a shader to Vulkan’s minimum limits?

To stay within what every conforming device must allow, reported as 128 invocations per workgroup and 16 KiB of shared memory, so the shader runs everywhere; larger choices are made only after reading the device’s real limits.

08Why does file 07’s reduction repeat bit for bit when part 2’s atomic sum did not?

Every addition’s operands are fixed by invocation index, so the order never changes. Atomic adds take block totals in the order the blocks finish, which changes from run to run.

Apply

09VLEN 256, 16-bit elements, LMUL 2. VLMAX, and passes for 100 elements?

\(256 \times 2/16 = 32\); \(\lceil 100/32 \rceil = 4\) passes, the last holding 4 elements.

10A branch taken by 0.5% of invocations at random, on 64-lane subgroups. What share of subgroups must run it?

\(1 - 0.995^{64} = 0.274\), about the same as 1% on 32 lanes.

11File 07’s tree widened to 512 values: barriers and additions?

9 halvings plus the load: 10 barriers; 511 additions.

12An accelerator draws 40 W at 20 TFLOP/s. Energy per FLOP, against the source’s three devices?

\(40/20 \times 10^{12} = 2.0\) pJ: worse than all three of the table’s 0.50–1.00 pJ.

13A device guarantees only 64 invocations per workgroup. Largest one-output square tile and its intensity?

8×8, at \(8/4 = 2\) FLOP/B.

14Static power is 40% of full power and the chip runs at 25% utilisation. Energy per FLOP against full load?

\((0.4 + 0.6 \times 0.25)/0.25 = 2.2\) times.

151,000 floats with VLMAX 64: passes, and lanes in the last?

\(\lceil 1000/64 \rceil = 16\) passes; the last takes \(1000 - 15 \times 64 = 40\).

164,096 floats move in a single 400-cycle trip at 1.98 GHz. Best possible bandwidth?

16,384 bytes in 202 ns: 81 GB/s, 2.5% of 3.3 TB/s. The job is too small to fill the pipe.

Judge

17Is the edge greener per operation?

Not by the source’s own table: 0.70, 0.50 and 1.00 pJ per FLOP for server, phone and microcontroller. The edge wins on absolute power, cost per device, latency and privacy, and loses again at part load unless it sleeps well.

18Task 1 prints “~783 cycles” for the microcontroller. Use it?

No. It is the desktop’s time in 160 MHz ticks. The network does 50,816 multiply-adds, so a one-per-cycle core needs at least 317.6 µs, 65 times more.

19Should portable GPU code assume 32 lanes?

No. Read gl_SubgroupSize, as RVV code reads vsetvl. On 64 lanes a 1% branch is run by 47.4% of subgroups, not 27.5%, and tree steps that fit in one subgroup change.

20Should a phone kernel reuse the source’s 16×16 tile?

It may not even be guaranteed to run (256 invocations), and with the phone’s ridge near 195 FLOP/B (reported bandwidth) it reaches 2% of peak. Fewer bytes per element (quantisation) and larger reuse, within the device’s real limits, matter more than the arithmetic.

21Vulkan or CUDA for an Android app’s inference?

Vulkan, or a framework built on it: CUDA does not run there. The source’s own table says the same. Expect to tune per device, since only correctness is portable.

22You replace file 07’s nine-barrier tree with subgroup adds. What changes?

One barrier instead of nine, and fewer idle lanes. But the order inside a subgroup add is the implementation’s, so the total’s last bits may differ between vendors, while still repeating on one device (reported).

23A colleague times a 1,024-element Vulkan dispatch at 2 GB/s and calls the GPU slow. Respond.

The job is 12 KB against the 667 KB the GPU needs in flight. Even with no launch cost it cannot exceed 61 GB/s. Measure with a job many times larger than bandwidth × latency.

24Across Chapter 16, which two results would you keep if you kept only two?

A line runs at its slowest station (the roofline, with two stations on a CPU, three on a GPU, and a ridge that moves with every change of machine), and work in process equals rate times lead time (accumulators, warps, prefetch distance, the size of a job that can fill the pipe). Kitting raises the intensity the first law needs; the drilling head counts the strokes on every machine.
