Two Shop-Floor Laws Run the Core

Every speed limit inside a processor is one you have already solved on paper. A line runs at the rate of its slowest station. Work in process equals throughput times lead time. The first law is the roofline. The second tells you how many partial sums a dot product must keep in the air, and why one core cannot use its own memory bandwidth.

Chapter 16 is split in three at its natural seams. This part is the CPU: why Python hands its arithmetic to C++ (source file 00), how a modern core executes and what limits it (file 01), and vector programming on ARM (file 02) and x86 (file 03). Part 2 is the GPU, part 3 portability and the edge. Sheet 02 introduced matrix multiplication as an operation on paper; this is where it meets the machine, and §07 shows that the trick every fast matmul uses is staging material at the machine.

The headline is §08. Industrial engineering has a two-line result for a closed line with \(w\) jobs in it, a raw process time \(T_0\) and a bottleneck rate \(r_b\): throughput can never exceed \(\min(w/T_0,\ r_b)\). It follows from Little’s law, which Sheet 13 used. The build machine obeys it twice over, at scales a million times apart. A chain of fused multiply-adds with \(K\) independent accumulators rose as \(K/4\) per cycle and flattened at 2, with the knee at \(K = 4 \times 2 = 8\). A chase through memory with \(K\) independent pointers rose as \(K/(210\ \text{ns})\) and flattened near 15 lines in flight. The roofline of §06 is the \(r_b\) half of the same inequality.

The bridge bank said “SIMD is multi-spindle machining”. That holds only for one member of the family. A multi-spindle drilling head (one feed, many identical tools) is SIMD, masks and all. A multi-spindle automatic lathe indexes each part through stations, which is a pipeline, Sheet 13’s other bridge (§05).

Measured on the build machine: a 4-vCPU virtual machine on an Intel Xeon of the Cascade Lake class (family 6, model 85), running at about 3.17 GHz, 32 KiB of L1 data cache per core and 33 MiB of L3. Two results were taken on a second container of the Sapphire Rapids class (model 207, with AMX), and say so. Your numbers will differ. The laws should not.

The planner and the machines

src 00. why C++ ↗

Every np.dot, torch.matmul and jnp.matmul in the earlier sheets ran in compiled C, C++ or CUDA. Python described the work; something else did it. The source draws the stack as a ladder: your Python code, the framework’s Python API, a dispatcher or compiler (torch.compile, XLA), a C++ kernel library (ATen, BLAS), a hardware back end (MKL, cuBLAS, oneDNN), and the hardware.

The reason for two languages is the reason a shop has a planning office and a floor. The planner works fast in a flexible medium and changes the plan often. The floor works in a rigid medium that is set up once and then runs at the rate of the machine. Python is quick to write and slow to run, roughly a hundred times slower than compiled code per simple operation. C++ is slow to write, gives control over every byte, and reaches the vector units.

The source’s example is a \(4096 \times 4096\) matrix product. Each of the \(n^2\) outputs is a dot product of length \(n\): \(n\) multiplies and \(n-1\) adds, conventionally counted as \(2n\) floating-point operations (FLOPs). So

$$2n^3 = 2 \times 4096^3 = 137{,}438{,}953{,}472 \ \text{FLOP},$$

the source’s “~137 billion”. Its timings are another matter. It says pure Python takes about 30 minutes and optimised C++ about 10 ms, a ratio of \(1800/0.010 = 180{,}000\). The arithmetic is right; the 10 ms is not plausible for a CPU.

$$\frac{137.4\times10^{9}\ \text{FLOP}}{0.010\ \text{s}} = 13.7\ \text{TFLOP/s}$$

Using the source’s own peak formula, corrected in §06 to count a fused multiply-add as two operations, one AVX2 core at 4 GHz peaks at 128 GFLOP/s. Ten milliseconds would take 107 such cores, or 54 AVX-512 cores, every one at 4 GHz and 100% of peak. On the build machine NumPy took 0.35 s in float32 on 4 cores (395 GFLOP/s, through its BLAS). A pure-Python triple loop timed at \(n = 64\) and \(n = 128\) and scaled by \(n^3\) extrapolates to about 55 minutes. The real ratio on this machine is near 9,300, which is still the point: no amount of Python cleverness closes it.

!NumPy’s elementwise arithmetic is not multithreaded

File 01’s second task labels c = a * b “Parallel (NumPy, uses SIMD + multithreading internally)”. The way to check is to compare CPU time with wall-clock time: a program using four threads accumulates four CPU-seconds per second. For a * b on 20 million floats the ratio was 1.00. For a 2048 matmul it was 3.9 on 4 CPUs. NumPy’s elementwise operations (its ufuncs) use SIMD on one thread; only calls that reach BLAS fan out across cores ([Ch16 s01]).

Fusion is done-in-one machining

The source’s strongest reason to write a custom kernel is fusion. A layer such as relu(layernorm(matmul(x, W) + b)) runs as separate kernels by default. Each one reads its input array from main memory and writes its output back, so the intermediate result makes a round trip to memory between every pair of operations. A fused kernel keeps the intermediate values in registers and writes only the final answer.

✓Same structure: parts that go back to stores between operations

An unfused pipeline is a part that returns to the stores after every operation and is issued again for the next one. Fusion is done-in-one machining on a mill-turn centre: one setup, every operation, one trip out. The traffic count is exact. After the matmul writes its output once, each of \(k\) elementwise steps reads and writes that output-sized array again, so unfused traffic is \((1+2k)\) arrays against 1 fused. For the source’s three steps (bias, layer norm, ReLU) that is 7 against 1.

!Where it breaks

A done-in-one machine needs a fixture that holds every feature at once. A fused kernel needs every intermediate value to fit in registers or on-chip memory at once, and layer norm needs a whole row before it can normalise any element of it. So fusion is easy for a chain of elementwise steps and hard across a reduction. The source also says fusion turns “three memory-bound operations into one compute-bound operation”. It removes their traffic; whether the fused kernel is compute-bound depends on the matmul inside it, which §06 shows is not automatic.

The rest of file 00 is plumbing, summarised here and not re-run: pybind11 wraps a C++ function as a Python module; PyTorch C++ extensions compile one on the fly with torch.utils.cpp_extension.load; JAX uses XLA custom calls or, more conveniently, Pallas (part 2). Neither pybind11 nor PyTorch is installed on the build machine, so those two examples are reported, not run. Write custom code only for an operation the framework lacks, a fusion it misses, a memory saving, or new hardware.

C++ in shop terms

src 00. why C++ ↗

You need enough C++ to read a kernel, not to write a library. Four ideas carry most of it.

Explicit types. int is a 32-bit integer, float a 32-bit floating-point number, double a 64-bit one. A variable cannot change type, and the compiler checks every use, which is Sheet 13 part 3’s point that a type is a unit and type checking is dimensional homogeneity.

Pointers. A pointer is a variable holding a memory address. float* ptr = weights; stores where the array starts; ptr[42] means “the float 42 places along”, and the machine computes its address as

$$\text{address} = \text{base} + 42 \times 4\ \text{bytes}.$$

That is the fixed-pitch calculation of Sheet 14 part 1 §12: an array is a row of equal bins, so any bin is one multiplication away. A pointer is a bin location written on a requisition slip. The danger is the same as with a slip: nothing stops you writing a location past the end of the rack, and C++ will fetch whatever is there.

Stack and heap. Small, short-lived arrays go on the stack, typically 1–8 MB per thread, created when a function starts and cleared when it returns. Large arrays go on the heap, booked out with new and returned with delete. The stack is the workbench, cleared at the end of every job. The heap is the stores, where material booked out and never returned is a memory leak. std::make_unique attaches the return slip to the job, so the material goes back automatically when the job ends.

✓Same structure: a template is a tabulated drawing

A tabulated drawing shows one geometry and a table of dash numbers, each a real part with its own dimensions. A C++ template such as template <typename T> T add(T a, T b) is one piece of code with the number type left open; the compiler produces a separate, fully specified function for each type you actually use (add<float>, add<int>). This is how ATen writes one kernel and gets float16, float32 and float64 versions. Where it breaks: each dash number really is separate code in the program, so a template used with many types makes the program larger, which a drawing sheet never does.

The source’s first program, run

Task 1 fills ten million floats with \(0.001\,i\) and adds them into a float accumulator. It prints Sum 4.83701e+10. The exact sum of the same stored values is \(4.99999974\times10^{10}\), so the program is 3.26% low. This is Sheet 13’s floating-point lesson at scale: a float carries a constant relative error, so once the running total reaches \(10^{10}\) its spacing is 1,024, and each addend of a few thousand is rounded to that spacing before it is added. A double accumulator, or adding in a tree of partial sums, fixes it ([Ch16 s02]).

The program also prints a “Throughput” of about 2.3 GB/s. That is not a memory speed. The loop is one long chain in which every addition waits for the previous result, and a floating-point add on this core takes 4 cycles. Ten million of them at 3.17 GHz take \(10^7 \times 4 / 3.17\times10^9 = 12.6\) ms; the loop measured 12.7 ms when timed on its own (16–17 ms single-shot, as printed). The compiler is not allowed to split the chain, because float addition is not associative (Sheet 13 again), and §08 shows what splitting it buys.

Task 3 sums a \(4096 \times 4096\) matrix of ones. That is \(2^{24} = 16{,}777{,}216\) ones, exactly the last integer a float can count to one at a time: \(2^{24} + 1\) rounds back to \(2^{24}\). Both of its sums print correctly by the luck of the size. One more row and both would be wrong. §07 returns to what that task measures.

Why clocks stopped: the cube law

src 01. hardware fundamentals ↗

Until about 2005 a new processor ran old programs faster because its clock was faster. Then clocks stopped near 4 GHz, and every gain since has come from doing more things at once: more cores, wider vector units, GPUs. The source gives the reason as the dynamic power of switching transistors,

$$P \propto C\,V^{2} f,$$

with \(C\) the switched capacitance, \(V\) the supply voltage and \(f\) the clock frequency. A transistor switches faster at a higher voltage, so raising \(f\) means raising \(V\). Over the range where voltage tracks frequency, \(V \propto f\), and

$$P \propto f^{3}, \qquad \frac{\text{energy}}{\text{operation}} = \frac{P}{f} \propto f^{2}.$$
✓Same exponents: the affinity laws

For a fan or a centrifugal pump at speed \(N\): flow \(Q \propto N\), head \(H \propto N^2\), power \(P \propto N^3\), so the energy per cubic metre delivered goes as \(N^2\). A processor under \(V \propto f\) has operations per second \(\propto f\), power \(\propto f^3\), and energy per operation \(\propto f^2\). The exponents match term for term, and the practical rule matches too: a pump or a chip run a little slower saves a lot of energy per unit of output. The physics differs. The pump’s cube comes from fluid similarity; the chip’s comes from charging a capacitance to a voltage, \(\tfrac12 CV^2\) per switching event.

The source then says “a 4-core chip at 3 GHz uses similar power to a single core at 4.5 GHz but can do 4× the parallel work.” Under its own cube law the power ratio is

$$\frac{4 \times 3^{3}}{4.5^{3}} = \frac{108}{91.1} = 1.185,$$

which is fair to call similar. The work is not 4×. Four cores at 3 GHz do \(4 \times 3 = 12\) units of clock-work per nanosecond against 4.5 for the single core: 2.67×. At exactly equal power each core runs at \(4.5/4^{1/3} = 2.835\) GHz and the total is \(4^{2/3} = \mathbf{2.52\times}\). Doubling a 4 GHz, 100 W core to 8 GHz would take \(2^3 = 8\times\) the power, 800 W, which is the source’s “impractical cooling” in numbers ([Ch16 s03]).

The trade has a condition attached, and it is Sheet 13’s Amdahl’s law. If a fraction \(s\) of the work cannot be split, \(n\) equal-power cores, each at \(f_n = 4.5/n^{1/3}\) GHz, deliver, relative to the one fast core,

$$R(s) = \frac{n^{-1/3}}{s + (1-s)/n}, \qquad R > 1 \iff s < s^{*} = \frac{n^{-1/3} - 1/n}{1 - 1/n}.$$

For two cores \(s^* = 0.587\); for four, 0.507; for sixteen, 0.357. More cores lower the bar, because each one is slower.

!Where the analogy breaks

\(V \propto f\) is a fit over the normal operating range, not a law. Below a threshold voltage the transistor stops switching cleanly, and at low voltage the leakage current, which flows whether or not anything switches, becomes a large share of the power. So the cube law overstates the saving at the slow end, just as the affinity laws mislead when a pump is slowed below the speed at which it can still meet the system’s static head. The serial fraction plays the part of that static head: no number of slow units in parallel gets past it.

Inside one core

src 01. hardware fundamentals ↗

Sheet 13 part 1 built a processor that fetches, decodes and executes one instruction at a time. A modern core does three more things, all automatically.

Superscalar execution. The core has several execution units (integer, floating-point, load, store) and can start four to six independent instructions in the same cycle. It is a cell with several machines.

Out-of-order execution. The core looks a few hundred instructions ahead and starts any instruction whose inputs are ready, wherever it sits in the program. Results are then committed in program order. In shop terms it is a dispatcher who starts any job whose material has arrived, while the shipping dock still releases orders in order-book sequence; the holding area between them is the reorder buffer.

Branch prediction and speculation. An if or a loop test is a fork: the core does not know which way to go until the condition is computed, many cycles later. Rather than wait, it guesses and starts work down the guessed path. A correct guess costs nothing. A wrong one means the speculative work is discarded and the right path started: about 15 cycles, the source says.

✓Same structure: making to forecast

Speculation is making to forecast before the order is confirmed. A good forecast hides the lead time; a bad one scraps the work in process, and the scrap is the pipeline flush. The cost model is the expected-value calculation you would do for a forecast: \(\text{cost per branch} = \text{miss rate} \times \text{penalty}\). At the source’s 5% and 15 cycles that is 0.75 cycles per branch. On the build machine a branch that went either way at random cost 3.7 ns more per element than the same branch on sorted data, about 24 cycles per misprediction (29 on the second container), so the source’s 15 is the floor, not the typical cost ([Ch16 s04]).

The simplest useful predictor keeps a 2-bit counter per branch: states 0 and 1 predict “not taken”, 2 and 3 predict “taken”, and each outcome moves the counter one step toward itself, stopping at the ends.

✓Identity: the 2-bit counter is a hysteresis band

It takes two wrong outcomes in a row to flip the prediction, as a thermostat with a dead band needs the temperature to cross the band, not just touch the set point. The payoff is on loops. A loop that runs nine times and exits has one surprise in ten. A 1-bit predictor (remember the last outcome) misses twice per loop, at the exit and again on re-entry: 20%. The 2-bit counter rides through the single exit: 10%. The same hysteresis can also lock in the worst case. Fed T, N, T, N… it misses 50% if it starts weakly taken and 100% if it starts weakly not-taken ([Ch16 s04]). Real predictors add a history of recent outcomes and learn such patterns; that refinement is reported, not built here.

Sheet 13 part 1 showed that a pipeline’s cycle time, throughput and latency are the assembly line’s, the same expressions. All of this is instruction-level parallelism, found automatically among independent instructions. Doing the same operation to many numbers at once is data-level parallelism, and it needs the vector units of §05.

src 01. hardware fundamentals ↗

SIMD (single instruction, multiple data) applies one instruction to several numbers at once. The numbers sit side by side in a wide vector register, each in its own lane. Instead of four scalar additions, _mm_add_ps(va, vb) adds four pairs of floats in one instruction. The lane count is the register width divided by the number’s width:

The bank’s entry was “SIMD ↔ multi-spindle machining”. That names a family, and Sheet 12 taught the move: when a bridge names a category, ask which member and why. There are two common multi-spindle machines and they are opposite kinds of parallelism.

✓Same structure: the multi-spindle drilling head

A drilling head with \(W\) spindles on one gearbox, fed by one slide, cuts \(W\) holes in one stroke. One feed is one instruction; the spindles are the lanes; the fixed spindle pitch is the fixed spacing of consecutive floats in memory. A stroke takes the same time whether one spindle carries a drill or all of them do, which is why a short job wastes the head. With 10 holes on an 8-spindle head you need \(\lceil 10/8\rceil = 2\) strokes and only \(10/16 = 62.5\%\) of the spindle-strokes cut metal; on a 4-spindle head, 3 strokes and 83.3% ([Ch16 s05]). Taking the drills out of the spare spindles is a mask: AVX-512’s mask registers and SVE’s predicates switch lanes off so the last stroke cuts only the holes that exist, instead of a separate scalar “cleanup loop”.

!Where the bank’s wording breaks: the multi-spindle automatic

A multi-spindle automatic lathe indexes six or eight spindles round a drum. At any moment each spindle holds a different part at a different station, so the machine does different operations on different parts simultaneously and finishes one part per index. That is a pipeline, Sheet 13 part 1’s assembly line, not SIMD. Same name on the machine, opposite kind of parallelism.

Divergence. Suppose some holes need a deeper cut. A head cannot feed two depths in one stroke, so a group of holes containing both kinds takes two strokes, each with the other kind’s drills removed. SIMD does exactly this with an if: it computes both branches for every lane and selects per lane with the comparison mask (vbslq_f32 on NEON, _mm256_blendv_ps on AVX2, a mask register on AVX-512). The cost of a group is the sum of both branches whenever both occur in it. That count is exact, and part 2 meets it again as warp divergence on a GPU.

Pallets: alignment. Memory reaches the core in fixed 64-byte cache lines, 16 floats each, the way stock arrives in pallets of fixed size. A vector load of \(W\) bytes that starts at an address that is not a multiple of \(W\) will sometimes straddle two lines and need both pallets. Over a long array the fraction of such split loads is exactly

$$\text{split fraction} = \frac{W}{64}: \quad 16\ \text{B (SSE, NEON)} \to 25\%, \quad 32\ \text{B (AVX)} \to 50\%, \quad 64\ \text{B (AVX-512)} \to 100\%,$$

and zero when the start is a multiple of \(W\) ([Ch16 s05]). Whether it costs anything depends on which station binds, and §10 measures both cases.

Reductions have no spindle

A drilling head has no path from one spindle to another. Neither does a vector unit, mostly: it is built for vertical operations, lane 0 with lane 0. Summing or taking the maximum across the lanes needs shuffles that move values between lanes. The source’s AVX2 maximum does it in two steps on four lanes, with the immediates 0b01001110 and 0b10110001. Decoded, the first moves lane \(i\) to lane \(i \oplus 2\) (swap halves) and the second to \(i \oplus 1\) (swap neighbours), where \(\oplus\) is bitwise exclusive-or. After each step every lane keeps the larger of itself and its partner, so after \(\log_2 4 = 2\) steps every lane holds the maximum. Partners at \(i \oplus 2^s\) are the butterfly of Sheet 09’s FFT.

!A shuffle is a permutation matrix only sometimes

The source says shuffling lanes “is the hardware equivalent of multiplying by a permutation matrix”. For these two immediates it is, and the verifier checks both are orthogonal. But _mm_shuffle_ps may pick the same source lane twice: immediate 0 copies lane 0 into all four, a 0/1 matrix of rank 1, which is a selection, not a permutation ([Ch16 s05]).

!Where the drilling head breaks, and one place it holds

The head drills one part, so feeding it is one part per stroke whatever the spindle count. Every SIMD lane needs its own numbers delivered, so doubling the width doubles the demand on the delivery station. That is the source’s remark that “you can compute faster than you can feed data”, and §06 makes it a formula. One correspondence survives where you might not expect it: more spindles draw more spindle power, and a head at its motor limit must be fed more slowly. Wider vectors draw more power, and many Intel cores lower their clock under heavy AVX-512 load. On the build machine AVX-512 chains delivered 164–165 GFLOP/s per core against AVX2’s 87–101 in separate runs, 1.6–1.9× rather than 2× (1.5–1.7× on the second container). This measurement cannot separate a clock drop from other limits ([Ch16 s10]).

The roofline is a two-station line

src 01. hardware fundamentals ↗

The roofline model rates a piece of code against two limits of the machine. The peak compute rate, in floating-point operations per second, is

$$\text{Peak} = \text{cores} \times f \times \text{lanes} \times \text{FMA units} \times 2 .$$

The 2 is there because a fused multiply-add (FMA), \(c \leftarrow c + a\times b\), is two operations. The source writes \(4\times10^9 \times 8 \times 2 = 64\) GFLOPS for a 4 GHz AVX2 core with two FMA units, which leaves it out. Its own matmul count, \(2n^3\), counts the multiply and the add separately, so the consistent peak is 128 GFLOP/s. Mixing the two conventions halves every ridge point computed from them.

The peak bandwidth is how many bytes per second memory can deliver: the source’s “50 GB/s” is a whole-chip figure (one core of the build machine streamed 9–12 GB/s; §08 says why). A kernel’s arithmetic intensity \(I\) is the FLOPs it performs per byte it moves. Then

$$\text{attainable} = \min\left(\text{Peak},\ \text{BW} \times I\right), \qquad I^{*} = \frac{\text{Peak}}{\text{BW}} .$$
✓Identity: a two-station serial line

Station 1 delivers material at BW bytes per second. Station 2 machines it at Peak FLOPs per second. The product mix \(I\) converts station 1’s capacity into station 2’s units: BW bytes per second feed \(\text{BW}\times I\) FLOPs per second of work. A serial line runs at the rate of its slower station, so its output is \(\min(\text{Peak}, \text{BW}\times I)\), which is the roofline formula. The ridge point \(I^*\) is the product mix at which the line is balanced. Below it the delivery station is the constraint (memory-bound); above it the machining station is (compute-bound). With the corrected peak and 50 GB/s, \(I^* = 128/50 = 2.56\) FLOP/B; the source’s figures give 1.28.

!Where it breaks: the line assumes the stations overlap

\(\min\) is the rule for a line whose stations work at the same time on different items. If the core waited for each delivery before computing on it, the times would add, as in a one-operator cell, and the rate would be the harmonic combination \(1/(1/\text{Peak} + 1/(\text{BW}\,I))\), exactly half the roof at the ridge point. Real cores overlap through out-of-order execution and hardware prefetching, so they sit close to the \(\min\) when prefetching works and drop toward the sum when it cannot (random access, §08). The lab shows both.

Staging the material: where Sheet 02’s matmul lands

src 00. why C++ ↗

Memory is a ladder of stores, each smaller and closer than the last. On the build machine: registers at the spindle; a 32 KiB L1 cache per core, the rack beside the machine; a 1 MiB L2 per core, the cell’s buffer; a 33 MiB shared L3, the shop stores; and main memory (DRAM), the warehouse, about 210 ns away (§08). The cache keeps whatever was used recently and evicts the least recently used line when it is full (LRU); the programmer does not move material by hand, but chooses an order of work that keeps the right material close.

Use the whole pallet. File 00’s third task sums a \(4096\times4096\) float matrix stored row by row, first along rows, then down columns. Along a row, consecutive floats share a 64-byte line, so each delivery serves 16 additions. Down a column, consecutive floats are 16 KiB apart, so each delivery serves one addition unless the line is still in cache when the next column comes past. The source’s program printed a 6.3× slowdown (row 28 ms, column 177 ms). But §02 showed its row loop is one float-add chain, whose floor is \(2^{24}\times 4/3.17\ \text{GHz} = 21\) ms; the row time measures the adder, not the memory. A row pass with eight independent accumulators took 7.5 ms, so against memory speed the column walk is about 22× slower. Walking down the columns sixteen at a time, so that every line delivered is used in full, brought it to 18–20 ms.

!The source’s 6× measures two things at once

Its “cache-friendly” baseline is slowed by the dependency chain of §08 to three times its memory-limited speed, which hides most of the effect it set out to show. The penalty is not a simple 16 either: a column sweep touches 4,096 lines, 256 KiB, which mostly survives in the 1 MiB L2 until the next column reuses it, so much of the column walk’s cost is per-access latency and address translation rather than DRAM bandwidth ([Ch16 s11]).

Tiling the matrix product

Sheet 02 defined \(C = AB\) by \(c_{ij} = \sum_k a_{ik}b_{kj}\). The work is a cube: one multiply-add for every triple \((i,j,k)\), \(n^3\) of them. The three matrices are the cube’s three faces: \(A\) is indexed by \((i,k)\), \(B\) by \((k,j)\), \(C\) by \((i,j)\). A loop order is a path through the cube, and the traffic it causes depends on how much face it must fetch for the volume it covers.

Tiling (cache blocking) cuts the cube into \(b\times b\times b\) blocks and finishes each block before moving on. A block needs a \(b\times b\) tile of each face and does \(2b^3\) FLOPs. Keep the \(C\) tile resident while the \(k\)-blocks stream past and each step fetches \(2b^2\) floats, so

$$I_{\text{tile}} = \frac{2b^{3}\ \text{FLOP}}{2b^{2}\times 4\ \text{B}} = \frac{b}{4}\ \text{FLOP/B}, \qquad \text{words fetched} \approx n^{2} + \frac{2n^{3}}{b}.$$
✓Identity: intensity is volume over surface

The work a tile does grows with its volume, the material it needs with its faces: \(I\) is a characteristic length, \(V/A\), the same ratio that sets the Biot number of a lumped body. Double the tile edge and the intensity doubles. And for a block \(a\times b\times c\) with a fixed amount of face that fits in the cache (\(ab + bc + ca\) fixed), the largest volume is the cube \(a = b = c\), by Lagrange multipliers or by the verifier’s random search ([Ch16 s07]). A theorem of Loomis and Whitney (reported) makes this general: no traversal of the cube gets more work out of a given amount of face.

✓Same structure: kitting at the machine

Staging a kit at the machine so that many operations happen per trip to the stores is the whole idea. The kit must fit the rack: three float tiles fit a 32 KiB L1 while \(12b^2 \le 32{,}768\), so \(b \le 52\). The intensity it buys must clear the ridge of §06: \(b/4 \ge I^*\), so \(b \ge 4I^*\). §12 does that calculation for the build machine.

!Where kitting breaks

A kit is consumed; a tile is reused. The same \(A\) tile serves every \(B\) tile in its row, and that reuse is where \(b/4\) comes from. And no planner chooses what leaves the rack: the cache evicts the least recently used line by itself. The lab shows the consequence. At exactly the capacity of three \(8\times8\) tiles (192 words) LRU fetches 12,240 words, not the formula’s 9,216, because it sometimes evicts a line it needs next. With room to spare it matches the formula to the word.

Little’s law runs the core

src 03. x86 and AVX ↗

Sheet 13 used Little’s law, \(L = \lambda W\): average work in process equals throughput times average time in the system. Apply it to a closed line holding \(w\) jobs, each needing a raw process time \(T_0\) when nothing waits, with a bottleneck station of rate \(r_b\). Every job takes at least \(T_0\) to go round, so throughput \(= w/\text{(time in system)} \le w/T_0\). And no line beats its bottleneck, so throughput \(\le r_b\). Together:

$$\text{TH}(w) \le \min\!\left(\frac{w}{T_0},\ r_b\right), \qquad w_0 = r_b\,T_0 .$$

Below the critical WIP \(w_0\), throughput grows in proportion to the work in process and nothing waits. Above it, throughput is flat and every extra job only lengthens the queue: time in system grows as \(w/r_b\). Hopp and Spearman call the equality case the best-case performance of a CONWIP line (the name is reported; the two lines above are the derivation). Sheet 13 part 2 showed that a counting semaphore is a kanban card count; here the cards are registers and outstanding memory requests.

Accumulators are the cards in the FMA loop

A dot product adds \(a_ib_i\) into an accumulator with a fused multiply-add. Each FMA on this core takes \(T_0 = 4\) cycles to produce its result, and the core has two FMA units, each accepting a new FMA every cycle: \(r_b = 2\) per cycle. An FMA that adds into an accumulator cannot start until that accumulator’s previous FMA has finished. So \(K\) independent accumulators are \(K\) jobs circulating in a closed loop, and

$$\text{TH}(K) = \min\!\left(\frac{K}{4},\ 2\right)\ \text{vector FMAs per cycle}, \qquad K_0 = 4 \times 2 = 8 .$$
✓Identity, measured: the FMA sweep

On the build machine, \(K\) independent chains of AVX2 FMAs ran at 0.26, 0.50, 1.02, 1.48, 1.86, 2.04, 2.05, 1.99 vector FMAs per cycle for \(K = 1, 2, 4, 6, 8, 10, 12, 16\). Below the knee the law holds to within 4%; above it the rate stops at 2. The knee is rounded: \(K = 8\) gave 1.6–1.9 across runs against the bound of 2, because the loop’s own bookkeeping competes for the same issue slots, just as real lines fall short of the best case near \(w_0\). The second container gave the same picture: 0.24 at \(K=1\), 2.0–2.1 at the top ([Ch16 s08]).

!The source’s explanation of its NEON dot product is wrong

File 02 says its float32x4_t sum_vec holds “4 independent accumulators (one per SIMD lane)”, so “the CPU can pipeline the FMAs”. The four lanes are independent of each other, but they live in one register, and every iteration’s FMA needs that register’s previous value: \(K = 1\). The same one-register loop, written in AVX2 as file 03 prints it, measured 0.30 vector FMAs per cycle, the 4-cycle latency. Its lanes make it four times (NEON) or eight times (AVX2) faster than a scalar chain; pipelining needs independent registers, and two FMA units with a 4-cycle latency need eight of them. File 03 gets this right in its “data dependencies” paragraph, which unrolls into four accumulators; Little’s law says why four is half of enough on this core.

A dot product has a third station. Every FMA needs two numbers loaded, and this core loads two per cycle, so the load ports cap a dot product at one FMA per cycle however many accumulators it has: measured 0.94–0.97 with eight. Matrix multiplication escapes that cap only by reusing loaded values in registers, the register-level version of §07’s tile. The compiler will not split a float chain on its own, because float addition is not associative: GCC’s report says the scalar dot product was “vectorized”, and its code does the eight multiplies in one instruction and then eight scalar adds in a row into one register ([Ch16 s10]).

Outstanding misses are the cards in the memory loop

The same law sets how fast one core can use memory. Follow \(K\) independent chains of pointers through 512 MB in random order: each chain must wait for its load to come back before it knows its next address. One chain took 210 ns per step, the round trip to DRAM. More chains overlapped their waits, and the time per line fell as \(210/K\) ns until it stopped near 14.4 ns, about 4.4 GB/s of random lines. Past that, each chain’s step time grew instead: 237 ns at \(K = 16\), 458 ns at \(K = 32\), which is \(K/r_b\).

$$w_0 = r_b\,T_0 = \frac{210\ \text{ns}}{14.4\ \text{ns}} \approx 14.6\ \text{lines in flight}.$$
✓Identity, measured: memory-level parallelism

A core can keep only so many cache misses outstanding, a fixed number of buffers for lines on their way in (reported at 10–12 per core for this family, with more requests issued by the hardware prefetchers). That buffer count is the card count of the loop, and Little’s law turns it into a bandwidth: \(\text{BW}_{\text{core}} \le (\text{cards} \times 64\ \text{B})/T_0\). This is why one core streamed only 9–12 GB/s from a memory system the source quotes at 50: the delivery station of §06 is itself a closed loop with a card limit. The second container gave \(T_0 \approx 207\) ns and about 17 lines in flight ([Ch16 s08]).

!Where it breaks

The law is a bound. Real stations vary, so measured throughput sits below it near the knee, and a memory system’s latency itself rises with load because the controller queues requests, which the simple model folds into \(r_b\). The card count is also not one number: sequential streams draw on prefetcher requests that random chases cannot, which is why the streaming 9–12 GB/s is higher than the 4.4 GB/s of random lines. The law tells you what to count; it does not count it for you.

ARM, NEON and the scalable extensions

src 02. ARM and NEON ↗

ARM processors run every phone, Apple’s laptops and a growing share of servers. ARM is a RISC design (Sheet 13 part 1): arithmetic works only on registers, and memory is reached only by explicit load and store instructions. Every AArch64 instruction is exactly 32 bits long, against x86’s 1 to 15 bytes, which makes decoding simple. There are 31 general-purpose 64-bit registers, x0 to x30 (the source says 32; the 32nd encoding is the stack pointer or a zero register), and 32 SIMD registers v0 to v31 of 128 bits.

NEON is ARM’s 128-bit SIMD: 4 float32, 8 float16 or int16, or 16 int8 lanes per register. Its intrinsics are C functions that map one-to-one to instructions: vld1q_f32 loads four floats, vaddq_f32 adds them, vfmaq_f32(c, a, b) computes \(c + a\times b\) with a single rounding, and vaddvq_f32 sums the four lanes. ReLU is one instruction per four floats, vmaxq_f32(x, zero), with no branch at all.

The build machine has no ARM processor, so the source’s ARM code was cross-compiled with clang for AArch64 and read, not run. Every NEON, I8MM and SVE snippet and all three ARM tasks compile. Reading the output confirms §08: dot_neon’s loop is a single fmla v0.4s into one register, one chain; dot_scalar keeps eight scalar fadd s0, s0, … in a row, the same order-preserving reduction GCC produces on x86 ([Ch16 s09]).

I8MM: four dot products per instruction

Quantised inference (Sheet 17) multiplies 8-bit integers and accumulates in 32 bits. ARMv8.6’s I8MM extension adds SMMLA: it treats one 16-byte register as a \(2\times8\) int8 matrix \(A\), another as a \(2\times8\) matrix \(B\), and adds \(AB^{\mathsf T}\), a \(2\times2\) block, into four int32 accumulators:

$$C_{2\times2} \mathrel{+}= A_{2\times8}\,B_{2\times8}^{\mathsf T}: \quad 2\times2\times8 = 32\ \text{multiply-accumulates per instruction.}$$

The source calls this “an 8-element dot product in a single instruction”; it is four of them. For comparison, the older SDOT does four 4-long dot products (16), and plain NEON needs about four instructions (two widening multiplies, two pairwise accumulates) for 16. So the instruction-count ratio is \(32/(16/4) = 8\), consistent with the source’s “4–8× faster” as an upper bound; the speed-up itself is reported, not measured here. The source’s comment “Load 8 bytes (2 rows of 4 elements)” contradicts the next line, which correctly loads 16 bytes as 2 rows of 8.

!Availability lists are reported, and two look wrong

Nothing about which chip has which extension can be computed here. Two of the source’s entries disagree with this sheet’s understanding, so treat both as unverified: it lists I8MM on “Apple M1+”, while I8MM is understood to have arrived with M2; and it lists SME on Neoverse V2 (Graviton4) and “not yet on Apple Silicon”, while Neoverse V2 is understood to have SVE2 without SME and Apple’s M4 to implement SME. On a Mac, sysctl hw.optional.arm lists the features your chip reports; on Linux, the Features line of /proc/cpuinfo.

SME: the outer product as one instruction

Sheet 02 showed that a matrix product is a sum of outer products, \(AB = \sum_k \mathbf a_k \mathbf b_k^{\mathsf T}\), column of \(A\) times row of \(B\). ARM’s Scalable Matrix Extension builds that into hardware. A 2-D accumulator, the ZA array, holds \(\text{SVL}_B \times \text{SVL}_B\) bytes, where \(\text{SVL}\) is the streaming vector length; at 512 bits that is \(64\times64 = 4{,}096\) bytes, four \(16\times16\) float32 tiles. One FMOPA instruction adds a full \(16\times16\) outer product into a tile: 256 multiply-adds ([Ch16 s09]). The source’s kernel does not compile as printed: SVL is never declared, and clang warns that its intrinsics are undefined outside a function marked as streaming with ZA state (__arm_locally_streaming, __arm_new("za")), which is the “smstart” the comments leave out. Part 2 meets the same outer product as a tensor core and a TPU’s systolic array.

SVE: a head whose spindle count is read at run time

NEON is fixed at 128 bits. SVE lets the hardware choose any multiple of 128 bits up to 2048, and the same compiled program runs on all of them. svcntw() returns the number of 32-bit lanes at run time, and svwhilelt_b32(i, n) builds a predicate that switches off the lanes past the end of the array. It is §05’s mask made the normal way of working: write the program for a drilling head of unknown spindle count, and let the last stroke remove its own spare drills. Part 3 takes this up for RISC-V’s vector extension, which is built the same way.

Apple silicon adds performance and efficiency cores, an undocumented matrix unit (also called AMX, unrelated to Intel’s) reached through Apple’s Accelerate library, unified memory shared by CPU and GPU, and a Neural Engine the source puts at about 30 TOPS; all reported. Unified memory removes the copy across the PCIe link that a separate GPU needs. That link’s speed is derivable: PCIe 4.0 signals 16 GT/s per lane (reported) with 128b/130b coding, so sixteen lanes carry \(16\times10^9 \times \tfrac{128}{130} / 8 \times 16 = 31.5\) GB/s each way, the source’s “~32 GB/s”.

Auto-vectorisation

Compilers vectorise simple loops by themselves: known trip count, no dependence between iterations, contiguous access. They report what they did (g++ -O3 -fopt-info-vec-optimized, clang++ -Rpass=loop-vectorize), and reading the report before writing intrinsics is the source’s best advice.

!Aliasing does not prevent vectorisation; it adds a check

The source says that without __restrict__ the compiler must assume the output might overlap an input, “preventing vectorisation”. GCC 13 vectorised the plain add_auto anyway and reported “loop versioned for vectorization because of possible aliasing”: it emits a vector version and a scalar one and chooses at run time by comparing the addresses. restrict removes the check, not a refusal. What does stop it is a true chain: a[i] = a[i-1] + b[i] was reported “couldn’t vectorize loop” ([Ch16 s10]).

x86: AVX, AVX-512 and AMX

src 03. x86 and AVX ↗

x86 widened its vectors in steps, each keeping the old registers as the low part of the new: MMX (64-bit, 1997), SSE (128, 1999), SSE2 (2001), AVX (256, 2011), AVX2 with FMA (2013), AVX-512 (512, 32 registers and mask registers, 2017), and AMX tiles (2023). The years are the source’s, reported. Intrinsics read _mm256_fmadd_ps: width (_mm 128, _mm256, _mm512), operation, then type (ps packed single, pd packed double, epi32 packed int32).

The AVX2 dot product is the NEON one at twice the width, with an untidier reduction at the end: add the upper 128 bits to the lower, then two horizontal adds. The source says it is “a 2× speedup over NEON for long vectors (ignoring memory bandwidth limits)”. Per cycle, with one accumulator each and equal FMA latency, that is right; but long vectors are exactly where memory binds, and §11 shows file 03’s own task landing on the memory station.

AVX-512 adds mask registers: _mm512_cmpgt_ps_mask makes a 16-bit mask and _mm512_maskz_mov_ps zeroes the lanes it excludes, which is ReLU, and the same mask handles the array’s tail. The source calls _mm512_reduce_add_ps a “built-in horizontal sum (no manual reduction!)”. It is built into the header, not the hardware: GCC expands it into 9 instructions, 4 of them adds, the \(\log_2 16 = 4\) halvings of §05 ([Ch16 s10]).

AMX: 8,192 multiply-adds per instruction

Intel’s Advanced Matrix Extensions add eight tile registers of up to 16 rows by 64 bytes, 1 KiB each. TDPBF16PS multiplies a \(16\times32\) tile of bfloat16 by a \(32\times16\) tile and accumulates into \(16\times16\) float32:

$$16 \times 16 \times 32 = 8{,}192\ \text{multiply-accumulates} = 512\ \text{AVX-512 FMAs}.$$

The source says “hundreds”. Two more details are missing from its four-line snippet. The \(B\) operand is not stored as a \(32\times16\) matrix but as 16 rows of pairs (Intel calls it the VNNI layout), so that each 64-byte row holds two consecutive \(k\) values for each of 16 columns; the verifier rebuilds \(A B\) exactly from that layout. And the tiles must be configured before use.

!The AMX snippet, run

The build machine has no AMX; the second container does, and the snippet was run there inside a minimal program. As printed, it died at once with SIGILL (illegal instruction): no tile configuration had been loaded. With a configuration (_tile_loadconfig: palette 1, 16 rows of 64 bytes for each tile) but without asking Linux for permission, SIGILL again: on Linux (from 5.16, reported) a process must request the 8 KiB of tile state with arch_prctl(ARCH_REQ_XCOMP_PERM, XFEATURE_XTILEDATA). With both, one TDPBF16PS reproduced the \(16\times16\) product exactly ([Ch16 s10]).

Alignment, measured both ways

§05 counted which loads split a line. Whether that costs time depends on which station binds. A dot product running from L1, where the load ports are the constraint, ran at 0.94 vector FMAs per cycle with aligned arrays and 0.46 with both arrays shifted by one float, so that half the 32-byte loads split: half the speed (1.07 against 0.73 on the second container). Streaming 64 MB from DRAM, where the delivery station binds, the same shift changed 10.8 GB/s to 10.6. Alignment matters when loads are the bottleneck and disappears when memory is. Allocate with aligned_alloc(64, bytes) or alignas(64) anyway; it is free.

The source’s other pitfalls are reported: the AVX–SSE transition penalty on pre-Skylake parts (use _mm256_zeroupper), and register pressure. AVX2 has 16 YMM registers. Eight accumulators and their operands fit comfortably; sixteen accumulators plus operands would not, and the compiler would spill some to memory, adding loads and stores to the loop. So §08’s critical WIP has to fit in the register file as well, and on this core it does with room to spare (AVX-512 doubles the file to 32). For profiling, perf stat reports cycles, instructions and cache misses, and Intel VTune goes deeper; neither was available in the build container.

File 01’s benchmark calls the same function on the same inputs 100 times and never reads the output. GCC noticed that one call gives the same result as a hundred and ran it once, so bytes for 100 passes were divided by the time of one: the printed bandwidth is exactly 100× too high (the verifier finds the ratio 83–100 across runs). File 03’s alignment loop accumulates into a sum that is never printed, so the whole loop was dead code. The cure for both is to use the result: print it, or pass it through an empty asm volatile barrier, which is what this sheet’s own measurements do.

!The counted bytes are not the bus’s bytes

c[i] = a[i] + b[i] counts 12 bytes per element. The bus carries 16: storing to a line that is not in cache first reads it (write-allocate), then writes it back. Streaming stores, which skip the read, raised the counted rate from 10.7–11.7 GB/s to 15.0–15.9 on the build machine, 1.34–1.41×, close to the 4/3 that a bus-bound core predicts. On the second container they gave 2.1×: there one core’s miss buffers, §08’s cards, bind before the bus does, so removing a third of the line requests freed more than a third of the time. The direction is the law; the size depends on which station binds.

To benchmark honestly: compute the floor before you run (latency chain, memory traffic, compute peak), use every result, time several runs and keep the best, and name the station you expect to bind. If the measurement beats the floor, the measurement is wrong.

Worked example: a tile for this machine, solved twice

src 01. hardware fundamentals ↗
The problem

A float32 matrix product with \(n = 4096\) on the build machine. One core can do two AVX2 FMAs per cycle (measured, §08) at 3.17 GHz and can draw about 10 GB/s from memory (measured 9–12). (a) What arithmetic intensity must the kernel reach to be limited by arithmetic rather than memory? (b) What tile edge \(b\) achieves it, and does the kit fit the 32 KiB L1? (c) Repeat for all four cores sharing about 20 GB/s (measured 16–26).

Solved as a production line

The machining station’s capacity is \(2 \times 8 \times 2 \times 3.17 = 101.4\) GFLOP/s: two FMA units, eight lanes, two operations per FMA. The delivery station supplies 10 GB/s. The line balances at the product mix where both stations are equally loaded, \(101.4/10 = 10.14\) FLOP per byte. A kit of three \(b\times b\) tiles, with the output tile kept at the machine, yields \(b/4\) FLOP per byte delivered (§07), so the kit must have \(b/4 \ge 10.14\): \(b \ge 41\). Three such tiles are \(3 \times 41^2 \times 4 = 20{,}172\) bytes, 19.7 KiB, which fits the 32 KiB rack beside the machine.

Now four machines draw from the same stores. Machining capacity is 405.8 GFLOP/s, delivery about 20 GB/s, so the balance point moves to 20.3 FLOP/B and the kit to \(b \ge 82\): three tiles are 79 KiB, more than the rack holds. So the kit is staged in two steps, the way a cell buffer feeds line-side racks: an \(82\times82\) (or larger) kit in each core’s 1 MiB L2 sets the traffic from the warehouse, and smaller tiles inside it, cut to fit L1, feed the machine from the cell buffer, whose own delivery rate is far higher (reported). Inside the machine, §08 adds the last requirement: at least eight independent accumulators.

Solved as a roofline

Peak \(= 101.4\) GFLOP/s, \(\text{BW} = 10\) GB/s, ridge \(I^* = 10.14\) FLOP/B. A naive loop at \(I = 0.25\) attains \(\min(101.4,\ 10\times0.25) = 2.5\) GFLOP/s, 40 times below the roof. A tiled loop at \(I = b/4\) attains \(\min(101.4,\ 2.5\,b)\), which reaches the roof at \(b = 40.6\); at \(b = 41\) the delivery term is 102.5, so the kernel is compute-bound by 1%. With four cores the roof is 405.8, the ridge 20.3, and the tile edge 82, and the L1 footprint test fails exactly as above ([Ch16 s12]).

The two solutions are one calculation in two vocabularies. What the shop language adds is the reason the answer has the shape it has: a balanced line, a kit sized by a volume-to-surface ratio, and a bottleneck that moves when machines are added. NumPy’s BLAS reached 395 GFLOP/s on these four cores in §01, using AVX-512 and several levels of tiling; the library is this worked example done carefully.

Question bank

24 prompts

Eight to recall, eight to apply, eight to judge. Answer before opening. The numerical answers in the apply tier are recomputed by the verifier under [Ch16 s14].

Recall

01Why does an \(n\times n\) matrix product cost \(2n^3\) FLOPs, and what is it for \(n = 4096\)?

\(n^2\) outputs, each a dot product of length \(n\): \(n\) multiplies and \(n-1\) adds, conventionally \(2n\). For 4096 that is 137,438,953,472, the source’s “137 billion”.

02State the roofline and define the ridge point.

Attainable \(= \min(\text{Peak}, \text{BW}\times I)\), with \(I\) the FLOPs per byte moved. The ridge \(I^* = \text{Peak}/\text{BW}\) is the intensity at which the two limits are equal: the product mix that balances a two-station line.

03What is a fused multiply-add, and how many FLOPs is it?

\(c \leftarrow c + a\times b\) in one instruction with one rounding. Two FLOPs, the convention that matches counting a matmul as \(2n^3\). Counting it as one, as the source’s peak does, halves every ridge point.

04How many float32 lanes do 128-, 256- and 512-bit registers hold?

4, 8 and 16 (2, 4 and 8 float64). SVE chooses any multiple of 128 bits up to 2048 at run time.

05What is a mask, and what does it replace?

A per-lane on/off pattern. It replaces the scalar cleanup loop at an array’s end and implements if by computing both branches and selecting per lane: the drilling head with some drills removed.

06State the best-case bound for a closed line and its critical WIP.

\(\text{TH}(w) \le \min(w/T_0, r_b)\), from Little’s law and the bottleneck. Critical WIP \(w_0 = r_bT_0\): below it throughput rises in proportion to WIP; above it only the queue grows.

07What is write-allocate, and what does it do to a bandwidth count?

Storing to a line not in cache first reads the line in. So c = a + b moves 16 bytes per element on the bus, not the 12 the program counts. Streaming stores skip the read.

08Why will a compiler not split a float sum into several partial sums by itself?

Float addition is not associative, so a different order gives a different answer. Without permission (-ffast-math or explicit partial sums in the code) the compiler keeps the single chain, as GCC’s eight scalar adds in a row showed.

Apply

09A core runs at 3 GHz with 16 lanes and two FMA units, and has 25 GB/s. Peak and ridge?

\(3\times10^9\times16\times2\times2 = 192\) GFLOP/s; ridge \(192/25 = 7.68\) FLOP/B.

10On that core, a kernel does 2 FLOPs per element and moves 12 bytes per element. Attainable rate?

\(I = 2/12 = 0.167\) FLOP/B, far below 7.68: delivery-bound at \(25\times0.167 = 4.17\) GFLOP/s, 2% of peak. Wider vectors cannot help; fusion or reuse can.

11An FMA has a 5-cycle latency and the core has two FMA units. How many accumulators does a reduction need?

\(w_0 = r_bT_0 = 2\times5 = 10\).

12A DRAM round trip takes 100 ns and a core can keep 10 line requests outstanding. Best random-access bandwidth?

Little’s law: \(10\times64\ \text{B}/100\ \text{ns} = 6.4\) GB/s, whatever the memory chips could deliver.

13100 holes on a 16-spindle head, all alike. Strokes and utilisation?

\(\lceil100/16\rceil = 7\) strokes; \(100/112 = 89.3\%\) of spindle-strokes cut.

14Eight cores at the power of one fast core, cube law. Gain if fully parallel, and the break-even serial fraction?

\(8^{2/3} = 4\times\). Break-even \(s^* = (8^{-1/3} - 1/8)/(1 - 1/8) = 0.429\).

15What tile edge clears the ridge of question 9, and how much L1 do three such tiles take?

\(b \ge 4\times7.68 = 30.7\), so 31; \(3\times31^2\times4 = 11{,}532\) bytes, 11.3 KiB.

1664-byte AVX-512 loads over an array that starts 8 bytes past a line boundary: what fraction split? And at 64 bytes past?

All of them, since \(W/64 = 1\); none at an offset of 64, a multiple of \(W\).

Judge

17A colleague’s benchmark shows 900 GB/s from a desktop’s memory. What do you check first?

Whether the work happened. Compare with the floor: no desktop memory does that. Then look for an unused result or a repeated identical call the optimiser could collapse, exactly file 01’s fault, and for data that fits in cache.

18Your kernel reaches 30% of peak and the roofline places it left of the ridge. Is hand-written AVX-512 the fix?

No. It is delivery-bound; more machining capacity changes nothing. Raise the intensity (tile, fuse, reuse in registers) or cut the bytes (lower precision). Intrinsics help only right of the ridge.

19A tiled matmul halves its time from one core to two but barely improves from four to eight. Why?

The ridge moved. Peak scales with cores and bandwidth does not, so at some core count the ridge passes the kernel’s intensity and memory becomes the constraint: Goldratt’s fifth step. Bigger tiles, staged in L2, move it back.

20Is SIMD a multi-spindle automatic lathe?

No. The automatic indexes different parts through different operations at once, a pipeline. SIMD is the multi-spindle drilling head: one feed, identical tools, many holes in one stroke.

21A dot product with eight accumulators runs at one FMA per cycle on a core with two FMA units. Add accumulators?

No. The FMA loop is already past its critical WIP; the load ports bind, two loads per FMA at two loads per cycle. Only reuse of loaded values (a matrix product, not a dot product) gets past that station.

22Does alignment matter?

When loads are the bottleneck, yes: it halved an L1-bound dot product here. When memory is, no: 10.8 against 10.6 GB/s. It costs nothing to align, so align.

23How would you test the claim that NumPy multithreads a * b without reading NumPy’s code?

Time it with both a CPU-time clock and a wall clock. A ratio near 1 means one thread; near the core count means all of them. It read 1.00 here, against 3.9 for a matmul.

24Does the cube law mean many slow cores always beat one fast one?

No. It ignores leakage, which dominates at low voltage, and the serial fraction: at equal power, four cores lose once more than 51% of the work is serial, sixteen once more than 36%.
